# Тестовое защищаемое приложение

Обычный HTTP-сервис, ничего не знающий про WAF: то самое «Приложение (upstream)» из
[docs/architecture.md](../architecture.md). Существует не для того, чтобы что-то защищать
по-настоящему, а чтобы модулю было что проксировать -- на нём проверяется прохождение запроса и
ответа через `proxy_pass`, а не логика вердиктов. Логику вердиктов проверяют
инспекторы `ip` и `modsec` на других маршрутах того же nginx.

Язык -- TypeScript, исполняемый node напрямую, без шага сборки: правится и
перезапускается это чаще, чем требуется отдельный шаг компиляции.
Framework-зависимостей нет: маршруты и параметры разбираются вручную в
[`src/routes.ts`](../../backend/src/routes.ts) поверх `node:http`, потому что 10 маршрутов
не тот масштаб, на котором Express или Fastify окупаются.

## Эндпоинты

| Маршрут | Что делает |
| --- | --- |
| `GET /` | Справочная страница: имя сервиса, hostname контейнера, pid, uptime, этот же список маршрутов |
| `ANY /echo` | Отражает метод, URL, заголовки и тело запроса тем же JSON -- проверить, что на самом деле доехало через прокси |
| `GET /status/:code` | Отвечает заданным кодом 100..599, вне диапазона -- 400 |
| `GET /error` | Бросает необработанное исключение -- 500 через generic catch, отличается от `/status/500` тем, что это настоящий сбой обработчика, а не намеренный ответ |
| `GET /delay/:ms` | Отвечает 200 после задержки; больше `BACKEND_MAX_DELAY_MS` -- обрезается |
| `GET /hang` | Не отвечает вовсе, соединение остаётся открытым. Имитация зависшего апстрима -- проверяет `proxy_read_timeout` на стороне nginx и `waf_deadline` с другой стороны, чем `verdict: silent` у инспектора: там висит инспекция, здесь висит само приложение |
| `GET /large` | Тело заданного размера, `?bytes=` (по умолчанию 1 000 000, потолок `BACKEND_MAX_LARGE_BYTES`) |
| `GET /stream` | Ответ чанками, `?chunks=&interval_ms=` (по умолчанию 10 чанков по 100мс) -- проверка потоковой отдачи и буферизации |
| `GET /redirect` | 3xx с `Location`, `?to=&status=` (по умолчанию `/` и 302; статус не из `{300,301,302,303,304,307,308}` откатывается на 302) |
| `GET /set-cookie` | `Set-Cookie` в ответе, `?name=&value=` -- cookie самого приложения, в отличие от `waf_chal` у модуля |
| `GET /healthz` | Быстрый `200 ok`, используется контейнерным healthcheck |
| всё остальное | `404` JSON `{"error": "not_found", "path": "..."}` |

## Запуск

Локально:

```sh
cd backend
npm install
PORT=8099 npm start
```

В контейнере, вместе с окружением:

```sh
cd deploy
docker compose up -d --wait
```

Поднимается как `backend` и слушает `8080` внутри сети окружения; наружу порт открыт на `8083` --
для сравнения ответа напрямую и через модуль:

```sh
curl http://localhost:8083/echo             # напрямую, минуя nginx и модуль
curl http://localhost:8081/app/echo         # тот же маршрут через HAProxy → nginx с модулем
```

## Проксирование через nginx

`location /app/` в [`deploy/nginx/nginx.conf`](../../deploy/nginx/nginx.conf) снимает префикс `/app` в
`proxy_pass`, поэтому `/app/status/418` на апстриме -- это `/status/418` из таблицы выше. Вердикт
на `/app/` -- `ip`: частная сеть проходит, адрес из blocklist -- нет.

```sh
curl -H 'X-Forwarded-For: 203.0.113.10' http://localhost:8081/app/echo  # 403, до апстрима не дошло
curl http://localhost:8081/app/status/500                                # 500, вердикт allow, ответил апстрим
```

## Переменные окружения

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PORT` | `8080` | Порт HTTP-сервера |
| `BACKEND_NAME` | `backend` | Имя сервиса в `/` и в логах |
| `BACKEND_LOG` | `info` | `debug`, `info`, `warn`, `error` |
| `BACKEND_MAX_DELAY_MS` | `60000` | Потолок задержки `/delay` |
| `BACKEND_MAX_HANG_MS` | `600000` | Через сколько `/hang` сам закроет соединение -- страховка от утечки, не сценарий проверки |
| `BACKEND_MAX_LARGE_BYTES` | `52428800` (50 МиБ) | Потолок размера тела `/large` |

## Тесты

```sh
npm test        # разбор маршрута и параметров, без сокета
npm run typecheck
```

Тесты проверяют только [`src/routes.ts`](../../backend/src/routes.ts) -- разбор пути, границы параметров, сборку
тела `/echo`. Всё, что требует настоящего сокета или таймера (`/hang`, `/stream`, `/large`,
здоровье под нагрузкой), проверяется end-to-end через [`tests/e2e`](../tests/e2e/README.md) и
вручную через curl -- в этом разделение то же, что у инспектора: чистая логика отдельно от
транспорта.

## Устройство кода

| Файл | Назначение |
| --- | --- |
| [`src/routes.ts`](../../backend/src/routes.ts) | Разбор маршрута и параметров, сборка тела `/echo` -- без I/O |
| [`src/main.ts`](../../backend/src/main.ts) | HTTP-сервер: сокет, таймеры, чанки, дренаж по сигналу |
| [`src/config.ts`](../../backend/src/config.ts), [`src/log.ts`](../../backend/src/log.ts) | Окружение и лог в JSON, тот же формат, что у инспектора |

## Ограничения

- Не TLS-терминатор и не апстрим для gRPC/WebSocket -- только обычный HTTP/1.1, этого достаточно
  для проверки `proxy_pass`.
- `/large` и `/hang` ограничены сверху переменными окружения намеренно: без потолка шальной запрос
  либо исчерпывает память контейнера, либо копит открытые сокеты.
