# Поставка: ветка на компонент, образ из git

Документ отвечает на три вопроса: что обязано лежать в каталоге компонента, чтобы его образ
собрался без монорепозитория; как этот каталог становится веткой, из которой собирает `docker
build`; какими командами это делается и что проверить перед публикацией.

Соседи по теме: раскладка на `core`, `shared` и компоненты — [repos.md](repos.md), топология
установки — [deployment.md](deployment.md), установка с нуля — [install.md](install.md), адреса
инфраструктуры и умолчания — [env.md](env.md), стенд — [deploy/README.md](deploy/README.md).

Первый разложенный компонент — инспектор действий (`inspectors/action`): на нём документ и
проверен, команды ниже выполнялись.

## Зачем ветка

Сегодня образ собирается из рабочего каталога: `deploy/docker-compose.yml` называет
`context: ../inspectors/action`, и `docker compose build` берёт файлы с диска. Для стенда этого
достаточно, для поставки — нет.

- **Сборщику нужен весь монорепозиторий.** Он приватный, и в дереве лежат настоящие секреты
  (`deploy/secrets/*`), дампы базы и веса моделей. Выдавать доступ ко всему этому ради
  сорокамегабайтного образа отправителя нечем оправдать.
- **У компонента нет своей версии.** Коммит монорепозитория называет состояние всего контура;
  «какой `action` стоит в проде» из него не выводится.
- **Наружу отдать нечего.** `ip` уже уехал в отдельный репозиторий (`github.com/exemt/waf-ip`)
  ручным переносом; каждый следующий компонент повторяет ту же работу заново.

Поставочная ветка `deliver/<компонент>` — тот же каталог, поднятый в корень ветки, с историей
только своих коммитов. Из неё собирается образ, из неё же наполняется отдельный репозиторий
компонента.

Ветка **производная**. Правится всегда `main`, ветка пересобирается из неё одной командой и
никогда не правится напрямую: правка в ветке потеряется на следующем пересборе.

## Правило: каталог компонента самодостаточен

Всё, что нужно контейнеру и сборке, лежит **под каталогом компонента**. Корневых файлов
монорепозитория в ветке не будет — в корне ветки лежит сам компонент.

Это правило уже соблюдено в коде (модуль Go самостоятелен, `deploy/Dockerfile` ничего не берёт
выше по дереву), но на трёх файлах нарушалось молча, потому что они живут в корне
монорепозитория и в ветку не попадают:

| Файл | Что теряется в ветке без своей копии |
| --- | --- |
| `.gitattributes` | `* text=auto eol=lf`. Клон ветки на Windows получает CRLF, и всплывает это потом — то в скрипте сборки, то в YAML профиля |
| `.gitignore` | собранный `go build` бинарь (`inspectors/*/inspector` в корневом файле) попадёт в коммит ветки |
| `.dockerignore` | в контекст и в образ уезжает лишнее: README, собранный на хосте бинарь. Файлы тестов исключать нельзя — сборка их запускает. Стендовое им не спрятать: при сборке из git-адреса BuildKit `.dockerignore` не применяет (проверено 13.09.2026) |

Проверка правила одна и она честная: собрать образ из checkout **одной только ветки**, без
монорепозитория рядом (раздел «Сборка образа»).

## Что лежит в ветке action

Полсотни файлов, 40,8 МБ образ на выходе.

| Путь в ветке | Зачем | В образ |
| --- | --- | --- |
| `go.mod`, `go.sum` | модуль `github.com/exemt/placitum-action`; общий код из `placitum-shared` | нет (только слой `go mod download`) |
| `cmd/inspector/` | точка входа: подписка, конвейер, ответ на каждом пути | бинарь |
| `internal/` | 16 пакетов: профили и условия, очередь, пульс, аудит, журнал, обменник, зеркало наборов, кодер гео | бинарь |
| `profiles/default.yaml` | профиль из образа: `mode: enforce`, `rules: []` — правил нет, их привозит поколение контроллера | да |
| `inspector.conf` | очередь (`queue_max`, `queue_full`, `queue_expand`) и блок `redis` с адресами обменника и внутреннего Redis | да |
| `deploy/Dockerfile` | двухстадийная сборка: `golang:1.25-alpine` → `alpine:3.22`, `CGO_ENABLED=0`, непривилегированный `action` (uid 10001) | — |
| `README.md` | формат профилей, условия, окружение, коды отказов | нет (`.dockerignore`) |
| `.dockerignore`, `.gitattributes`, `.gitignore` | см. правило выше | — |

Чего в ветке **нет** и не должно быть:

- **Общие спеки контура.** `docs/inspector-actions.md` (канал действий), `verdict-protocol.md`,
  `audit.md`, `lists.md` остаются в платформе: у документа один хозяин. Ссылки из README ведут
  в монорепозиторий. Так же сделано при переносе `ip`.
- **Compose стенда.** `deploy/docker-compose.yml` описывает контур целиком, а не компонент.
- **Стендовые профили.** `stand-rewrite` для e2e модификатора лежит в `deploy/action/profiles`
  платформы, стенд монтирует каталог поверх образа. Исключение в `.dockerignore` не спасало:
  образ, собранный из git-адреса, профиль всё равно вёз (пре-прод, 13.09.2026).
- **Секреты.** В `inspectors/action` их нет — проверено `grep` по `-----BEGIN`, `AKIA`,
  `password|secret|token`; совпадения — только имена полей протокола и текст ошибки. Для
  каждого следующего компонента проверять заново, дерево монорепозитория секреты содержит.

### Документация: кто хозяин

Документ живёт там, где живёт его хозяин. Устройство компонента — в репозитории компонента
(`docs/` рядом с кодом): что он создаёт в базе, какие у него ручки, как он устроен внутри.
Контракт контура — в платформе: формат сообщений шины, дорога журнала, протокол вердикта,
модель волн. Компонент на них ссылается, но не копирует: у документа один хозяин, иначе копии
расходятся так же тихо, как код.

Пока монорепозиторий приватный, **публичная репа на него не ссылается**: вместо ссылки два
предложения пересказа. Когда платформа станет публичной, ссылки проставляются одним проходом —
это дешевле, чем публичный репозиторий с битыми ссылками.

Открытые решения владельца: класть ли в ветку копию `LICENSE.md` (нужна, если ветка станет
публичным репозиторием) и файл CI. Workflow ложится в каталог компонента — `.github/workflows/`
внутри `inspectors/action`: в монорепозитории GitHub его не видит (читает только корневой
`.github`), а в поставочной ветке он окажется в корне и будет запускаться на push этой ветки.
Содержимое — как у `waf-ip`: `gofmt`, `vet`, `test`, `test -race`, `staticcheck`.

## Как получается выкладка

Репозиторий компонента — производный, но не копия истории платформы: его коммиты нанизываются
на `develop` поверх того, что там уже лежит, а внутри каждого — дерево каталога компонента, каким
оно лежит в рабочем каталоге платформы. Так push всегда идёт перемоткой, а платформа коммитится
отдельно и своими словами.

`git subtree split` для этого не годится: он переписывает историю платформы, и с уже
опубликованным `develop` она не сходится.

Всё делает [`deploy/deliver.mjs`](../deploy/deliver.mjs):

```bash
node deploy/deliver.mjs list                  # что выложено, где есть невыложенные правки
node deploy/deliver.mjs tree core             # дерево компонента против develop, по файлам
node deploy/deliver.mjs build crypto          # собрать образы из дерева, ничего не выкладывая
node deploy/deliver.mjs publish core -m msg   # проверить, закоммитить, вытолкнуть, собрать из клона
node deploy/deliver.mjs publish --all         # то же по всем компонентам, с отчётом
node deploy/deliver.mjs release core          # main репозитория = develop, только перемоткой
```

`publish` по дороге: ставит бит исполнения скриптам по shebang (на Windows `chmod` в дерево не
попадает), ищет в дереве приватные ключи и реквизиты, гоняет `gofmt -l` в контейнере (CI каждой
репы держит этот шаг, а правки скриптами его ломают незаметно), выталкивает и **собирает образы
из свежего клона** — единственная честная проверка, что репозиторий самодостаточен. Без `-m`
сообщение — «Выкладка из платформы <sha>» и список изменённых путей.

**Дерево берётся из рабочего каталога, не из коммита платформы.** Это удобно и опасно
одновременно: выложить можно и незакоммиченное, и в сообщении по умолчанию это будет отмечено.
Порядок правильный — сначала коммит платформы, потом `publish`.

## Ветки: develop разрабатывается, main выкачен

Четыре ветки на две стороны, у каждой один смысл.

| Где | Ветка | Что это |
| --- | --- | --- |
| Платформа | `main` | состояние платформы; правится только здесь |
| Платформа | `deliver/<компонент>` | производная поставочная ветка: её делает split, руками не правят |
| Репозиторий компонента | `develop` | то, что разрабатывается; сюда едет каждая выкладка |
| Репозиторий компонента | `main` | выкаченные сборки: наполняется в момент релиза и тегируется |

Правило простое: **`main` компонента — то, что можно ставить.** Всё, что ещё проверяется, живёт
в `develop`, и `sources.env` установки по умолчанию смотрит на `main`. Пока компонент не выкачен
ни разу, `develop` стоит сделать веткой по умолчанию в его репозитории — тогда человек, открывший
репозиторий, видит работу, а не пустоту.

```bash
node deploy/deliver.mjs publish core -m сообщение.txt    # в develop
node deploy/deliver.mjs release core                      # main = develop, только перемоткой
```

В репозитории компонента **руками не правят ничего**: обе ветки производные от платформы, и
правка, сделанная там, потеряется на следующей выкладке.

## Модель поставки: собирает установка

Готовые образы никто не раздаёт — **установка собирает их сама**, выкачав репозиторий
компонента. Реестр появится позже и ничего в разложении не поменяет: сменится источник образа,
а всё остальное — ветка, Dockerfile, метки, чек-лист — останется тем же.

Отсюда два следствия, которые стоит держать в голове при каждом решении ниже:

- **Ветка обязана собираться у чужого человека на чужой машине**, а не только здесь. Ровно это
  и проверяет правило самодостаточного каталога.
- **Сборке нужна сеть**: базовые образы, `go mod download`, npm у панели. Установка в
  изолированном контуре потребует либо `vendor/` в репозиториях, либо своего зеркала модулей.
  Решать это надо до первой такой установки, а не после.

**Тяжёлое чужое с собой не тащим.** Веса модели `vlai` (около 1,4 ГБ, CC-BY-4.0) и выгрузка
GeoLite2 (сотня мегабайт, своя лицензия) не лежат ни в репозиториях, ни в образах. Веса процесс
берёт сам при первом старте, в свой том, по запиненной ревизии; каталог гео заливает оператор.
Изолированному контуру и то и другое кладут в тома заранее — это шаг установки, а не сборки.

Compose умеет брать контекст сборки прямо из git, поэтому установка — это `up -d --build` над
файлом, где у каждого компонента `build.context` смотрит в его репозиторий
([core/README.md](../core/README.md#компоненты-собираются-при-установке-а-не-скачиваются-готовыми)).

## Сборка образа

Три формы, все три проверены здесь. Третья — ответ на вопрос «а нужна ли ветка вообще».

**Из рабочего каталога** — как сейчас на стенде, годится для правки на ходу:

```bash
cd inspectors/action && docker build -f deploy/Dockerfile -t waf-action:dev .
```

Путь к Dockerfile здесь считается от текущего каталога, а не от контекста, — отсюда `cd`.
У git-контекста ниже наоборот: там `-f` считается от корня выкачанной ветки.

**Из поставочной ветки** — то, ради чего всё затевалось. Контекст — git-URL, `-f` считается от
корня ветки:

```bash
docker buildx build -f deploy/Dockerfile -t waf-action:0.1.0 \
  "https://github.com/exemt/AWaf.git#deliver/action"
```

**Из подкаталога `main`** — без ветки вообще, BuildKit умеет и так:

```bash
docker buildx build -f deploy/Dockerfile -t waf-action:dev \
  "https://github.com/exemt/AWaf.git#main:inspectors/action"
```

Третья форма работает и стоит ноль подготовки — но контекст она берёт из приватного
монорепозитория, то есть сборщику по-прежнему нужен доступ ко всему дереву, и версии у образа
по-прежнему нет. Она годится для быстрой пересборки своими руками, не для поставки.

Приватный репозиторий в первых двух формах требует реквизитов. По HTTPS BuildKit читает секрет
`GIT_AUTH_TOKEN`, по SSH — агента:

```bash
docker buildx build --secret id=GIT_AUTH_TOKEN,env=GH_TOKEN \
  -f deploy/Dockerfile -t waf-action:0.1.0 "https://github.com/exemt/AWaf.git#deliver/action"
```

Это единственное место в документе, **не** проверенное здесь: локальная проверка шла против
своего `git://`-демона, где реквизитов нет. Проверяется первым же push ветки.

## Версия образа

Сам себя образ не подписывает. Меток не будет, если их не написать в Dockerfile (проверено:
у собранного из git-контекста образа `Config.Labels` был пуст), а `.git` BuildKit в контекст не
кладёт — поэтому и штампа Go (`vcs.revision`) в бинаре нет. Версию называет сборщик, руками.

Dockerfile принимает два аргумента и кладёт их в метки OCI:

```bash
docker buildx build \
  --build-arg VERSION=0.1.0 \
  --build-arg REVISION=$(git rev-parse --short deliver/action) \
  -f deploy/Dockerfile -t placitum/action:0.1.0 \
  "https://github.com/exemt/AWaf.git#deliver/action"

docker image inspect placitum/action:0.1.0 \
  --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'
```

Имя образа — то же, что у репозитория и у пути модуля: `placitum/<компонент>`
([repos.md](repos.md#имена)). Теги: `placitum/action:<семвер>` для поставки и
`placitum/action:git-<короткий sha>` для всего остального. `latest` не ставить — на контуре из
десятка машин он означает «никто не знает, что там».

Чего пока нет: версия не видна **изнутри** — ни в журнале при старте, ни в кадре пульса. Это
следующий шаг (переменная `main.version`, `-ldflags -X`, поле в `pulse.Message`), и он же даст
странице «Состояние» колонку версии на процесс.

## Чек-лист готовности компонента

Мерка одна на всех; справа — как с ней у `action` на 12.09.2026.

| Пункт | action |
| --- | --- |
| Каталог самодостаточен, образ собирается из одной ветки | да, проверено |
| `.dockerignore`, `.gitattributes`, `.gitignore` свои | да, заведены |
| Тесты идут в сборке образа (`RUN go test ./...`) | да, заведены; прогон зелёный |
| Секретов в дереве нет | да, проверено |
| Метки версии и ревизии в образе | да, `--build-arg` |
| Проба и `HEALTHCHECK` | **нет** — единственный Go-инспектор без `cmd/probe`; контейнер считается здоровым, пока процесс жив |
| Версия видна изнутри (журнал, пульс) | нет, у всех |
| CI на ветке | нет, у всех |
| Копия лицензии в ветке | нет, решение владельца |

Про пробу подробнее: у восьми инспекторов `HEALTHCHECK` шлёт обычное сообщение по шине и ждёт
`deny` — так проверяются разом шина, подписка, профили и пул воркеров, чего TCP-пинг не
проверяет. У отправителя вердикта, кроме `allow`, нет, поэтому ждать надо не `deny`, а либо
`verdict: error` с `ACTION_UNKNOWN_PROFILE` на заведомо чужой профиль (проверит шину и конвейер),
либо действие в ответе на профиль `_probe` из образа (проверит ещё и разбор профилей — честнее,
и так уже сделано у counter/json/rewrite, см. память про `_probe`).

## Как разложить компонент: порядок действий

Порядок проверен на восьми компонентах и повторяется дословно. Шаги не переставлять: каждый
следующий опирается на проверку предыдущего.

**0. Репозиторий.** Пустой публичный `placitum-<имя>`. Первый push создаёт `develop`, и она же
становится веткой по умолчанию.

**1. Путь модуля.** `github.com/nginx-waf/<старый>` → `github.com/exemt/placitum-<имя>` по всем
`*.go` и `go.mod`. **Сгенерированный protobuf трогать нельзя**: в `*.pb.go` дескриптор лежит
строкой с байтами длины, и замена пути на более длинный роняет пакет при инициализации
(`slice bounds out of range`). Если такой файл в компоненте есть — либо он уезжает в `shared`,
либо его регенерируют `protoc`, а не правят.

**2. Общий код.** Сверить с `shared`:

```bash
diff -rq --ignore-matching-lines='nginx-waf|placitum' shared/<пакет> inspectors/<имя>/internal/<пакет>
```

Совпало — снести копию, импорт заменить на `github.com/exemt/placitum-shared/<пакет>`. Обычно
совпадают `host`, `loglevel`, `flow`, `netinfo`, `geopb`, `pulse`.

Кадр присутствия шире общего (живые наборы у `ip`, счётчики у `captcha`) — не повод оставлять
копию: свой тип со встроенным `pulse.Message` и отправка `pulse.PublishFrame` дают ту же форму
на проводе.

**3. `GOWORK=off go mod tidy`.** Обязательно: `go.work` находит модуль на диске и прячет
отсутствующий `require`, а сборка образа падает на `no required module provides package`.

**4. Проверка кода.** В контейнере, а не на хосте:

```bash
docker run --rm -e GOWORK=off -v waf-gomod:/go/pkg/mod -v "$PWD:/src" -w /src/inspectors/<имя>   golang:1.25-alpine sh -c "go build ./... && go vet ./... && go test ./..."
```

**5. Dockerfile.** `COPY go.mod go.sum` и `go mod download` (не `tidy`: сборка обязана повторять
`go.mod`, а не переписывать его), `RUN go test ./...`, `ARG GOPROXY`, `ARG VERSION`/`REVISION` и
метки OCI, `CMD` вместо `ENTRYPOINT`. `GOSUMDB=off` снять, если он там есть.

**6. Обвязка репозитория.** `.dockerignore` (тесты **не** исключать — сборка их запускает),
`.gitattributes` (`* text=auto eol=lf`), `.gitignore`, `LICENSE.md`, `LICENSE.ru.md`,
`.github/workflows/ci.yml`.

**6а. Профили — из контроллера.** Решение владельца 12.09: компонент профилей оператора не везёт
— ни в репозитории, ни в образе, их доставляет контроллер поколением. Демо-профили стенда живут в
платформе (`deploy/<имя>/profiles`, стенд монтирует их поверх образа), тест, которому нужен
реальный каталог, ищет его вверх по дереву и пропускается вне платформы. В образе остаётся пустой
каталог под `WAF_<ИМЯ>_PROFILES`, если загрузчик требует его существования. **Исключение —
служебный `_probe`**: профиль healthcheck — свойство образа, а не конфигурация оператора, и без
него контейнер краснеет после первого же поколения.

**7. README и INSTALL.** README короткий: что делает, схема, сборка, ссылки. INSTALL: что нужно
рядом, таблица переменных с умолчаниями, compose-пример, проверка после запуска, грабли.

**8. Документация.** `docs/inspectors/<имя>/**` → `inspectors/<имя>/docs/`. Внутри перенесённых
ссылки пересчитать относительно нового места; ссылки наружу (спеки платформы) превратить в
упоминания без ссылки — платформа приватна. Ссылки платформы на эти доки — на URL публичной репы
`https://github.com/exemt/placitum-<имя>/blob/develop/docs/...`.

**9. Секреты.** `grep -rInE -e '-----BEGIN' -e 'AKIA' -e 'aws_secret_access_key=' <каталог>`.
Совпадения в тестах (сгенерированный ключ, фиктивные реквизиты) — не находка.

**10. Образ.** Собрать из каталога, затем **из чистого клона репозитория** — это и есть проверка
самодостаточности.

**11. Выкладка.** Одной командой, после коммита в платформе:

```bash
node deploy/deliver.mjs publish <имя> -m сообщение.txt
```

Она сама проверит секреты и `gofmt`, поставит бит исполнения скриптам, вытолкнет в `develop`
поверх того, что там лежит, и соберёт образы из свежего клона. Новый компонент сначала
добавляется в реестр `COMPONENTS` в начале скрипта: каталог, репозиторий, образы.

**12. Стенд.** `image: placitum/<имя>` в `deploy/docker-compose.yml`, пересобрать и перезапустить
сервис, дождаться `healthy` и проверить, что кадр присутствия идёт.

**13. Реестр.** Строка в `deploy/deliver.mjs` (`repo`, `ready: true`), строка в таблице выше,
строка в `core/sources.env`.

### Если сессий несколько

Компоненты независимы, но четыре файла общие, и править их надо по одной строке, без
переформатирования: `deploy/docker-compose.yml`, `deploy/deliver.mjs`, `docs/delivery.md`,
`core/sources.env`. `go.work` инспекторы не трогают — их пути не меняются.

Стенд один на всех: одновременный `docker compose up --build` из двух сессий подерётся за демон.
Пересобирать только свой сервис и по очереди.

## Грабли

- **Сборке нужна сеть до `proxy.golang.org`.** `RUN go mod download` — первое, что падает в
  изолированном контуре. Лечится либо `vendor/` в ветке (образ собирается офлайн, ветка тяжелеет),
  либо своим прокси модулей (`GOPROXY`). Решать до первой промышленной сборки, не после.
- **DNS у BuildKit на Docker Desktop отваливается.** Здесь это случилось дважды из пяти сборок:
  `dial tcp: lookup proxy.golang.org … i/o timeout` при полностью живом DNS у `docker run`.
  Повтор сборки помогает; кеш слоёв при этом не теряется.
- **`git subtree split` смотрит на историю, а не на диск** — см. выше про коммит перед split.
- **Ветка переписывает хеши.** `deliver/*` нельзя мержить обратно в `main`: это другая история
  тех же файлов. Обратная дорога — правка в `main` и пересборка ветки.
- **Профили в образе и на стенде — разные вещи.** Стенд монтирует каталог профилей поверх
  образа, поэтому «на стенде работает» не означает «в образе лежит». Проверяется запуском образа
  без монтирований.
