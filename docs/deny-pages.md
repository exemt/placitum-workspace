# Страницы отказа

Модуль отвечает статус-кодом, а содержимое страницы отдаёт nginx штатным механизмом `error_page`
через именованный location с включённым SSI. Модуль экспортирует переменные (`$waf_ray`,
`$waf_deny_name` и т.д.), SSI подставляет их в шаблон, и клиент получает готовый ответ. Тот
же механизм работает для HTML, JSON и любого другого формата: SSI обрабатывает содержимое
любого типа при `ssi_types *;`.

Отдельный шаблонизатор в модуле не нужен. SSI уже есть в стандартной поставке nginx и умеет
всё, что здесь требуется: подстановку переменных и условные блоки. Модуль занят только тем,
что ему положено: выносит вердикт, ставит переменные и возвращает код ответа.

## Общая схема

```
Access-фаза           nginx                Named location
┌──────────┐          ┌───────────┐        ┌──────────────────────┐
│ модуль   │ return   │ error_page│        │ @waf_deny            │
│ WAF      │──403───► │ 403 =403  │──────► │   ssi on             │
│          │          │ @waf_deny │        │   try_files           │
│ ставит:  │          └───────────┘        │   /$waf_deny_name.   │
│ $waf_ray │                               │   html → fallback    │
│ $waf_deny│                               │                      │
│ _name    │                               │ SSI подставляет      │
│ ...      │                               │ <!--# echo var=... -->│
└──────────┘                               └──────────────────────┘
```

1. Обработчик access-фазы возвращает `(ngx_int_t) dr->status` — как и раньше.
2. Директива `error_page` на уровне server или location перенаправляет в именованный
   location.
3. Именованный location обслуживает шаблон из `/usr/share/waf/pages/` (стандартный) или из
   store-объекта (кастомный), подставляя переменные через SSI.

Контекст модуля (`ngx_http_waf_ctx_t`) переживает internal redirect: переменные доступны
в именованном location, поэтому SSI-директивы `<!--# echo var="waf_ray" -->` разрешаются
корректно.

## Переменные модуля

Все переменные readonly и `NOCACHEABLE`. Доступны после фазы доступа, включая internal
redirect через `error_page`. Значение пустой строки означает, что контекст WAF отсутствует
(запрос не прошёл через модуль).

| Переменная | Источник в `ctx` | Описание | Пример |
| --- | --- | --- | --- |
| `$waf_ray` | `ray_hex` | Сквозной идентификатор запроса (UUID v4). По нему оператор находит инцидент в аудите | `a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d` |
| `$waf_rid` | `rid_hex` | Идентификатор слота ожидания (hex). Техническая деталь, на странице обычно не нужен | `0000001a00000003` |
| `$waf_reason` | `decisive->reason_code` / `SCORE_THRESHOLD` / `local_rule` | Код причины отказа | `SQLI_DETECTED` |
| `$waf_deny_name` | имя записи каталога из `ngx_http_waf_deny_entry()` | Имя записи `waf_deny_response`, по которой отвечает модуль | `blocked` |
| `$waf_deny_status` | `dr->status` | HTTP-статус отказа | `403` |
| `$waf_score` | `score` | Накопленный счёт фазы | `120` |
| `$waf_node_id` | `wmcf->node_id` | Идентификатор узла | `edge-07` |
| `$waf_deny_message` | `message=` записи каталога | Текст оператора для клиента. Встроенные страницы его не печатают, см. ниже | `Доступ с этого адреса закрыт` |
| `$waf_deny_scope` | `reason.scope` ответа | Что закрыто: `address`, `network`, `country`, `asn`, `session`, `request` | `network` |
| `$waf_deny_subject` | `reason.subject` ответа | Чем это названо | `203.0.113.0/24` |
| `$waf_deny_retry` | `reason.retry` ответа либо `ttl=` у `waf_local_rate` | Через сколько секунд повторять | `600` |
| `$waf_deny_ray` | `ray_hex`, под гейтом `params=` | Клиентская копия `$waf_ray` | тот же UUID |
| `$waf_deny_addr` | адрес соединения, под гейтом `params=` | Адрес клиента, как его видит контур (после real_ip) | `203.0.113.47` |

`$waf_deny_name` определяется тем же алгоритмом, что и текущее поведение: локальный отказ
берёт запись из правила или `waf_deny_response_default`, отказ по порогу —
`score_deny_response` или default, инспекторный — из ответа или default.

## Публичная причина

Первые семь переменных — диагностика: они для оператора, и стандартная страница их не печатает.
`$waf_reason` тем более: код вроде `IP_LIST` ничего не говорит человеку в браузере, а
`waf_local_check` подставляет туда имя набора, которое выбрал оператор, — то есть словарь там
открытый, и ветвиться по нему шаблон не может.

Последние четыре — наоборот, только для клиента. Это и есть ответ на «за что меня закрыли»:

```
                     что закрыто        чем названо        когда отпустит
                  ┌──────────────┐  ┌─────────────────┐  ┌──────────────┐
  reason.scope ──►│ network      │  │ 203.0.113.0/24  │  │ 600          │
                  └──────────────┘  └─────────────────┘  └──────────────┘
                          ▼                  ▼                   ▼
       «Закрыта сеть 203.0.113.0/24 — в неё входит ваш адрес.
        Повторить запрос можно через 600 с.»
```

Словарь `$waf_deny_scope` закрыт — шесть значений, под которые в шаблоне написаны ветки:

| Значение | Что показывает страница | Нужен `subject` |
| --- | --- | --- |
| `address` | Закрыт адрес `<subject>` | да |
| `network` | Закрыта сеть `<subject>`, в неё входит ваш адрес | да |
| `country` | Запросы из вашего региона не принимаются | нет |
| `asn` | Запросы из сети `<subject>` не принимаются | да |
| `session` | Ограничение действует на вашу сессию | нет |
| `request` | Закрыт сам запрос, а не отправитель | нет |

Область, которую нечем назвать, модуль не публикует: у SSI нет вложенных условий, и ветка «закрыта
сеть» без сети дала бы клиенту «Закрыта сеть .». Проверки полей — в
[verdict-protocol.md](verdict-protocol.md#публичная-сторона-причины).

`$waf_deny_message` встроенные страницы не печатают, и панель это поле у `type=http` не
показывает: текст отказа — свойство самой страницы (её правят в «Данных»), а вторая фраза под тот
же случай расходилась бы со страницей молча. Раньше ветка с ним стояла первой в цепочке и отменяла
разбор причины целиком.

Переменная и опция остались: у `type=grpc` и `websocket` `message=` — единственный способ что-то
сказать (это grpc-message), а своя страница, написанная руками, по-прежнему может её напечатать:

```nginx
waf_deny_response spoken type=grpc status=7
                  "message=Доступ закрыт. Обратитесь в поддержку с Event ID.";
```

### Гейт params=

Всем семейством `$waf_deny_*` распоряжается запись каталога: `params=` у `waf_deny_response`
перечисляет, что именно запись отдаёт клиенту (`ray`, `addr`, `scope`, `subject`, `retry`).
Нет перечня — открыто всё; запертая переменная становится not_found, и страница прячет её блок
целиком, вместе с подписью.

Ради этого у `$waf_ray` и `$remote_addr` появились клиентские копии `$waf_deny_ray` и
`$waf_deny_addr`, и страницы печатают именно их: у копий другой хозяин. Оригиналами живут логи и
аудит, и одна директива, режущая и страницу, и журнал, латала бы страницу дырой в журнале.

Гейт стоит на записи, а не на маршруте: одна страница может отвечать и болтливо
(`blocked` без `params=`), и глухо (`blocked_quiet params=ray`) — различаются они записью,
которую назвало правило. См. [deny_response.md](directives/list/deny_response.md).

### Чего пока нет

`address` и `network` умеет только IP фильтр. Локальный слой их не заполняет: имя набора
выбирает оператор, значение проверки — это адрес самого клиента, и ни то, ни другое не объяснение,
которое стоило бы печатать. Совпавший префикс локальный слой не возвращает вовсе.

`$waf_deny_retry` заполняет `waf_local_rate` с `list=` (срок известен — это `ttl=` правила) и любой
инспектор, приславший `reason.retry`. IP фильтр его пока не шлёт: срок бана назначает
инициатор по исходу, а не то правило, которое сработало на этом запросе.

## Формат шаблонов

Шаблон — обычный файл (HTML, JSON, XML, plain text) с SSI-директивами:

```html
<p>Event ID: <!--# echo var="waf_ray" --></p>
```

```json
{"error":"denied","ray":"<!--# echo var='waf_ray' -->"}
```

Условные блоки для SSI:

```html
<!--# if expr="$waf_deny_name = suspicious" -->
<p>If you believe this is an error, contact support with the reference above.</p>
<!--# endif -->
```

Ограничения SSI существенны: это не полноценный шаблонизатор, и ему достаточно подстановки
переменных и простых условий. Вложенные include, вычисления и циклы здесь не нужны и не
поддерживаются.

## Стандартные страницы

Лежат в образе по пути `/usr/share/waf/pages/` и, кроме `ratelimited`, заводятся набором вида
`content` в каждом пространстве — см. [встроенные страницы в каталоге](#встроенные-страницы-в-каталоге).

| Имя | Статус | Схема | Назначение |
| --- | --- | --- | --- |
| `blocked` | 403 | WAF ✕ приложение | Заблокировано правилом инспектора |
| `suspicious` | 403 | WAF ✕ приложение | Блокировка по порогу счёта |
| `too_many` | 429 | поток ⇥ WAF | Превышение частоты запросов |
| `ratelimited` | 429 | то же | Второе имя `too_many`; только файл образа |
| `malformed` | 400 | клиент ✕ WAF | Неразобранный запрос |
| `error` | 502/503 | сбой на WAF | Ошибка контура (шина, хранилище, таймаут с `block`) |
| `auth_required` | 401 | калитка | Нет второго фактора: [калитка auth](inspectors/auth/README.md) отвечает так всему, что не является навигацией |
| `captcha_required` | 403 | калитка | Нет клиренса капчи; фронтенд читает адрес задания из JSON-близнеца |

У каждой — HTML и JSON под тем же именем. JSON несёт те же значения полями: `scope`, `subject`,
`retry_after` печатаются условно, поэтому хвостовой запятой не появляется ни при какой комбинации
веток.

### Из чего собрана страница

```
   ┌───────────────────────────────────────────┐
   │      ┌────┐      ┌────┐      ┌────┐       │  схема: где остановился
   │      │ 🖥 │─────►│ 🛡 │──✕──►│ 🗄 │       │  запрос. Горит тот узел,
   │      └────┘      └────┘      └────┘       │  который его остановил
   │      Клиент       WAF     Приложение      │
   │                                           │
   │  [HTTP 403]                               │  $waf_deny_status
   │  Доступ закрыт                            │
   │  Запрос отклонён системой защиты.         │
   │  ┌─────────────────────────────────────┐  │
   │  │ Закрыта сеть 203.0.113.0/24 — в неё │  │  публичная причина:
   │  │ входит ваш адрес.                   │  │  ветка по $waf_deny_scope
   │  │ Повторить можно через 600 с.        │  │  + $waf_deny_retry
   │  └─────────────────────────────────────┘  │
   │  EVENT ID     a1b2c3d4-e5f6-4a7b-…        │  $waf_deny_ray
   │  ВАШ АДРЕС    203.0.113.47                │  $waf_deny_addr
   └───────────────────────────────────────────┘
```

Правила у всех восьми одни:

- Чистый HTML5 без внешних зависимостей: CSS в `<style>`, схема — inline SVG, ни одного запроса
  наружу. Страница стоит перед приложением, и загружать с неё что-либо означало бы вести
  заблокированного клиента ещё куда-то.
- Ни строки JS — по той же причине, что и у формы входа.
- Светлая и тёмная тема через `prefers-color-scheme`, адаптив от 320px.
- Тон (красный, янтарный, синий, серый) — одна переменная CSS на файл: «запрещено», «придержано»,
  «нужно действие», «сломались мы» читаются цветом до чтения текста.
- Ray выводится как «Event ID» — по нему оператор ищет запрос в аудите.
- Внутренние детали (`$waf_reason`, `$waf_score`, `$waf_node_id`) **не** показываются: они
  доступны для отладочных вариантов, но стандартная страница не раскрывает устройство защиты.
- Текст — клиенту, а не разработчику. Внутренних слов контура («калитка», «клиренс», «инспектор»,
  «счёт признаков») на странице нет: читатель о них не знает. Нет и объяснений устройства — почему
  не-навигации отвечают кодом, а не редиректом, и как сложился отказ: клиенту это не помогает
  ничего сделать. Остаётся четыре части: что случилось (заголовок и фраза под ним), публичная
  причина, что делать, опознавательные данные внизу (`098_deny_pages_client_text.sql`).

Без `ssi on` файл остаётся валидным HTML: SSI-директивы — обычные комментарии. Видны при этом будут
все ветки сразу, поэтому `ssi on` в именованном location обязателен.

## Встроенные страницы в каталоге

Семь страниц (все, кроме `ratelimited`) заводятся в каждом пространстве миграцией
`062_default_deny_pages.sql` — наборами вида `content` в разделе «Данные → Файлы», рядом с формой
входа. До этого их было не видно: оператор узнавал о них из документации, а свою заводил с чистого
листа.

Встроенная страница — **образец**, а не объект настройки: она заперта целиком. Ручка отвечает
`400 builtin_locked` и на удаление, и на переименование, и на правку тела.

Имя тут не косметика: это имя записи каталога `waf_deny_response`, по которому страницу ищет
`try_files /$waf_deny_name.html`. Переименованная перестала бы находиться, удалённая увела бы отказ
в fallback образа, а правленый образец перестаёт быть образцом — сверить свою страницу станет не с
чем.

Свой вариант получают кнопкой **«Скопировать»**: она спрашивает имя и заводит обычный набор с тем же
телом. Дальше он живёт своей жизнью, и править его можно как угодно. Ненужную встроенную страницу не
удаляют — её просто не называют ни в одной записи каталога.

Копия — единственный способ дать записи собственный текст: `message=` у `type=http` панель не
пишет (см. [Публичная причина](#публичная-причина)). Запись без своей страницы уезжает в
`/blocked.html` и показывает его текст; нужна другая фраза — копируется `blocked` под именем этой
записи, и текст правится в копии.

Файлы в образе остаются и меняют роль на ту же, что у формы входа: аварийный запас для контура без
контроллера. То, что правит оператор, лежит в базе; то, что зашито в образ, никто не ищет.

JSON-близнецов в каталоге нет. Имя набора уникально в пространстве, а имя файла на ноде считается
как имя набора плюс расширение по типу содержимого, — то есть `blocked.html` и `blocked.json` одним
пространством не выражаются. Пока это так, машиночитаемые ответы остаются файлами образа.

## Конфигурация nginx

### HTML

```nginx
server {
    error_page 400 =400 @waf_deny;
    error_page 403 =403 @waf_deny;
    error_page 429 =429 @waf_deny;

    location @waf_deny {
        waf off;
        ssi on;
        ssi_types *;
        root /usr/share/waf/pages;
        try_files /$waf_deny_name.html /blocked.html;
    }

    location / {
        waf on;
        proxy_pass http://app;
    }
}
```

`try_files /$waf_deny_name.html` ищет `/usr/share/waf/pages/<name>.html`. Если файла с таким
именем нет, отдаётся `/blocked.html` как fallback. `=403` в `error_page` форсирует статус
ответа: без него nginx отдал бы 200, потому что `try_files` нашёл файл.

### JSON (API)

```nginx
server {
    error_page 400 =400 @waf_deny_json;
    error_page 403 =403 @waf_deny_json;
    error_page 429 =429 @waf_deny_json;

    location @waf_deny_json {
        waf off;
        ssi on;
        ssi_types application/json;
        default_type application/json;
        root /usr/share/waf/pages;
        try_files /$waf_deny_name.json /blocked.json;
    }

    location /api/ {
        waf on;
        error_page 403 =403 @waf_deny_json;
        error_page 429 =429 @waf_deny_json;
        proxy_pass http://api;
    }
}
```

На API-маршруте `error_page` переопределяется на JSON-версию. Шаблоны лежат рядом с
HTML-версиями, в том же каталоге.

### Смешанная конфигурация

HTML для браузерных маршрутов, JSON для API — в одном server. Директива `error_page` на
уровне location переопределяет серверную; это штатное поведение nginx.

```nginx
server {
    # По умолчанию для server — HTML
    error_page 403 =403 @waf_deny;
    error_page 429 =429 @waf_deny;

    location @waf_deny {
        waf off;
        ssi on;
        root /usr/share/waf/pages;
        try_files /$waf_deny_name.html /blocked.html;
    }

    location @waf_deny_json {
        waf off;
        ssi on;
        ssi_types application/json;
        default_type application/json;
        root /usr/share/waf/pages;
        try_files /$waf_deny_name.json /blocked.json;
    }

    location / {
        proxy_pass http://app;
    }

    location /api/ {
        error_page 403 =403 @waf_deny_json;
        error_page 429 =429 @waf_deny_json;
        proxy_pass http://api;
    }
}
```

### Путь, который отвечает сам

`error_page` ловит и тот код, который вернула не проверка, а сам путь. Обработчик
`return` в панели («Пути» -> «Обработчик») печатает пару строк:

```nginx
location = /fail/500 {
    error_page 500 =500 @deny_500;
    return 500;
}
```

Страницу собирает тот же именованный location, что и для отказов модуля, поэтому
свободного тела у `return` в панели нет: строкой туда уехала бы копия страницы --
в конфигурацию, без SSI, то есть без `$waf_ray`. Оператор выбирает именованный
путь селектором, а `=<код>` компилятор ставит сам.

Исключение -- 3xx: там второй аргумент `return` не тело, а адрес в `Location`, и
страницы у него быть не может. Панель на таком коде показывает вместо селектора
поле адреса.

## Кастомные страницы

### Переопределение стандартных

Оператор заводит страницу в контроллере на разделе данных (`/datasets/files`, «Файлы») — это
набор вида `content`, тот же объект, что и любой другой файл пространства
(`POST /api/<scope>/datasets` с `kind=content`, тело — `PUT /datasets/<uuid>/content`).
Отдельной сущности под страницу нет намеренно: страница — частный случай содержимого,
и второе хранилище означало бы два места, где лежит одно и то же.

Имя набора совпадает с именем записи каталога `waf_deny_response`, файл на ноде
называется `<имя>.html` — тем самым его находит `try_files /$waf_deny_name.html`.
Расширение даёт тип содержимого: `html`, `json`, `xml`, `text`; у двоичного его нет,
и имя файла — имя набора.

Каталог страниц ноды адресуется ссылкой `pages:` — как `store:<uuid>`, но без uuid:
страницы различаются именем файла, и шаблон не обязан знать, куда нода их положила.

```nginx
location @waf_deny {
    waf off;
    ssi on;
    ssi_types *;
    root pages:;
    try_files /$waf_deny_name.html /blocked.html;
}
```

Агент заменяет `pages:` на свой каталог (`/var/lib/waf/store/pages` при
`store_dir /var/lib/waf/store`) и раскладывает туда файлы поколения. Каталог заменяется
целиком, поэтому страница, убранная из пространства, исчезает и с ноды.

Смешивать со стандартными путями можно тем же `try_files`: перечисленное после ссылки
проверяется дальше по списку, включая `/usr/share/waf/pages/...` из образа.

### Добавление новой записи каталога

Чтобы добавить запись каталога с собственной страницей — например, `av_found` для антивируса —
достаточно положить файл `av_found.html` в `/usr/share/waf/pages/` или загрузить через
контроллер. `try_files /$waf_deny_name.html` найдёт его автоматически.

### Требования к кастомной странице

Единственное требование: SSI-синтаксис для переменных, если они нужны. Остальное — на
усмотрение оператора: он может прислать страницу без SSI вовсе (статическую), страницу с
логотипом компании, инструкцией на любом языке и ссылкой на свою поддержку.

## Дистрибуция

### Стандартные страницы

Входят в Docker-образ nginx или в deb/rpm-пакет. Каталог `/usr/share/waf/pages/` — read-only,
обновляется с версией пакета.

### Кастомные страницы

Тем же контуром, что и конфигурация, но **не** store-объектами: страница уезжает клиенту,
и шифровать её ключом контура значило бы только, что её нельзя посмотреть в каталоге
контроллера. Формат — как у файлов правил: тело в Redis по `sha256`, в манифесте имя и хеш.

1. Оператор заводит набор вида `content` на разделе данных (`/datasets/files`, «Файлы»).
2. `POST /api/<scope>/config/send` пакует **всё** содержимое пространства в секцию
   `pages` и кладёт тела в Redis рядом с телом шаблона. Не по ссылкам: каталог на ноде
   заменяется целиком, и объект, убранный из пространства, исчезает с ноды.
3. Агент забирает тела по хешу, пишет их в свой каталог страниц (`0644`) и подставляет
   `pages:` в шаблоне.
4. Каталог заменяется целиком и атомарно, вместе с деревом конфигурации: `nginx -t`
   проходит по staging, `reload` — уже по применённому.

```json
{
  "v": 1,
  "kind": "nginx-pack",
  "rev": 44,
  "sha256": "sha256:...",
  "config": "sha256:...",
  "store": {
    "cert-uuid": { "hash": "sha256:...", "type": "certificate" }
  },
  "pages": {
    "blocked.html": "sha256:...",
    "malformed.html": "sha256:...",
    "error.html": "sha256:..."
  }
}
```

Что остаётся у store — секреты: сертификат, ключ, цепочка, CRL. Их контроллер видит только
шифротекстом, а расшифровывает ключом контура агент, см.
[config-distribution.md](config-distribution.md).

## Что не меняется

- `waf_deny_response` — синтаксис не трогается. Опция `page=` остаётся parsed, модуль её
  не использует: страница выбирается через `$waf_deny_name` и `try_files` в конфигурации
  nginx, а не через internal redirect из модуля.
- `waf_deny_response_default` — без изменений.
- `ngx_http_waf_deny()` — возвращает `(ngx_int_t) dr->status`, как и раньше.
