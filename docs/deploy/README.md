# Локальное окружение

Контур из `docs/architecture.md` плюс контроллер: три edge nginx с модулем и агентом,
NATS, Redis, HAProxy, тестовое приложение, инспекторы и Postgres. Одна команда.

```
deploy/
├── docker-compose.yml
├── deliver.mjs               поставочные ветки и образы компонентов (../delivery.md)
├── secrets/                  ключ контура: node gen.mjs; *.key/*.pub не в git
├── core-infra.env            что стенд подкладывает в инфраструктуру core (../../core/README.md)
├── (haproxy)                 балансировщик: образ agents/haproxy, конфиг ведёт панель (/config/haproxy)
├── loadgen/                  k6: burst, modsec, ip, vlai, chain, lists
└── nginx/
    ├── nginx.conf            монтируется в контейнер, правится без пересборки
    ├── nodes/                waf_node_id и имя на шине на каждую ноду
    └── www/                  статика для проверочных маршрутов
```

E2E-прогоны — [../tests](../tests/README.md), в контейнерах смонтированы как `/t`.

## Три инспектора

На стенде три живых инспектора, не заглушки. `ip` и `modsec` поднимаются всегда:
дешёвый адрес и CRS. `vlai` -- за профилем compose, модель тяжёлая.

Волны без отдельных контейнеров: в `nginx.conf` те же процессы объявлены под
другими именами (`crs` после `ip`, `model` после `crs`). Очередь NATS общая,
меняется только ребро графа. Прогон -- `t/combo/combo.sh`.

## Что из этого пока не используется модулем

Инспекторы фазы ответа в `nginx.conf` не объявлены: фильтров ответа модуль ещё не ставит, и
`nginx -t` предупредил бы о непроверяемом наборе.

`redis-agent` и `redis-internal-agent` -- отдельные от хранилищ наблюдатели, по одному на
экземпляр Redis: пульс `WAF_STATUS.store.redis.<id>` (health, память, ключи) на странице
Состояние, различаются именем из `WAF_REDIS_NAME`. Туда же едут агенты, инспекторы и сервисы
(`WAF_STATUS.service.logger.<id>`, `WAF_STATUS.service.geo.<id>`). Сам обменник к модулю
подключён, маршруты `/body/*`.

## Тестовое защищаемое приложение

`backend` -- обычный HTTP-сервис, ничего не знающий про WAF: то самое «Приложение (upstream)» из
[docs/architecture.md](../architecture.md). На нём проверяется само проксирование запроса и
ответа через `proxy_pass` -- заголовки, тело, коды, потоковая отдача, зависшее соединение, -- а не
вердикты: их проверяют маршруты `ip` и `modsec`. Заведён как отдельный
[`backend`](../backend/README.md), а не в `inspectors/`, потому что это не участник шины NATS и не
голосует -- обычный апстрим за модулем.

## Запуск

```sh
cd deploy
node secrets/gen.mjs          # раз, если ещё нет contour.key / contour.pub
docker compose up -d --wait --build controller
```

Ключ контура один на окружение. Приватный (`contour.key`) монтируется только
агентам как `WAF_NODE_KEY`. Публичный (`contour.pub`) — только контроллеру;
его отдаёт `GET /api/<scope_uuid>/crypto`. Без файлов compose не поднимется:
секреты требуют существующий файл, а не пустой каталог.

`VITE_CONTOUR_FINGERPRINT` зашивается в сборку UX (`controller/Dockerfile`,
цель `ux`) и используется `checkFingerprint`
(`controller/ux/src/crypto/seal.ts`) для сверки с тем, что вернёт
`GET /api/<scope_uuid>/crypto` в браузере — защита от подмены публичного
ключа скомпрометированным контроллером/XSS, см. `docs/security.md`.

`gen.mjs` прописывает переменную в `deploy/.env` сам, а compose подхватывает
этот файл автоматически -- экспортировать её в шелл не нужно. Файл в git не
лежит: значение зависит от `contour.pub`, который у каждого окружения свой.
Без переменной сборка не откажет, но страница «Сертификаты» покажет жёлтое
предупреждение «пин не задан, сверь вручную», то есть защита от подмены ключа
будет выключена.

`node secrets/gen.mjs --fingerprint` печатает fingerprint уже существующего
`contour.pub`, ничего не трогая. После смены ключа (`--force`) `.env`
переписывается автоматически, но `controller` нужно пересобрать: пин попадает
в бандл на этапе сборки, а не читается в рантайме.

Dev-сервер UX (`npm run ux`, порт 5173) `deploy/.env` не читает -- он
запускается из `controller/ux` и знает только про свои `.env`. Держать там
вторую копию значения не нужно: `controller/ux/vite.config.ts` считает
fingerprint прямо из `deploy/secrets/contour.pub`, поэтому в dev пин не может
разойтись с ключом. Приоритет источников -- `controller/ux/.env`, затем
переменная окружения (сборка образа), затем сам ключ.

Сборка модуля идёт из `../nginx/module` по цели `runtime`: тот же `Dockerfile`, что и в CI, только
вместо выгрузки `.so` кладёт его в официальный образ nginx. Версия nginx задаётся переменной
`NGINX_VERSION` и по умолчанию равна `1.28.0`; она общая для сборки модуля и для базового образа,
потому что модуль, собранный против других исходников, даёт порчу памяти, а не ошибку загрузки.

| Адрес | Что это |
| --- | --- |
| `http://localhost:8080` | контроллер: UX на `/`, API на `/api` |
| `http://localhost:8081` | nginx с модулем через HAProxy |
| `http://localhost:8082` | nginx-1, весь контур в пассивном режиме |
| `http://localhost:8404` | страница статистики HAProxy |
| `nats://localhost:4222` | шина |
| `http://localhost:8222` | мониторинг NATS: `/healthz`, `/varz`, `/jsz` |
| `redis://localhost:6379` | боевой обменник заголовков, query и тела: `waf_store` |
| `redis://localhost:6380` | внутренний Redis контура: блобы поколений, корзины, роастер калиток |
| `postgres://waf:waf@localhost:5432/waf` | база контроллера, не горячего пути |

Порта у `nats-box` нет: это не сервер, а клиент шины, живущий `sleep infinity` ради `exec`. Держать
его контейнером, а не запускать разово, стоит из-за наборов данных -- их прогон публикует снапшоты и
дельты, а в контейнере nginx клиента шины нет.

Так же устроен `minio-mc` -- клиент архива. При старте он ставит бакетам правила удаления
(`core/config/minio/lifecycle.json`, по одному на каждый `ttl=` из конфигурации), и `healthy` у него означает, что правила
стоят. Нужны они не только для уборки: с ними хранилище называет срок объекта в ответе на `PUT`,
агент кладёт его в локатор записи, и карточка инцидента отвечает «удалён по сроку хранения», не
ходя в S3 за пустотой.

```sh
docker compose exec -T minio-mc mc ls --recursive waf/waf-bodies
docker compose exec -T minio-mc mc ilm rule ls waf/waf-headers
```

## Край с хоста

`:8080` на хосте занят контроллером. Nginx по-прежнему слушает 8080 внутри сети compose;
e2e ходит туда из контейнера. С хоста модуль — `http://localhost:8081` (HAProxy).

HAProxy на `:8081` раскладывает запросы roundrobin по `nginx-1` / `nginx-2` / `nginx-3`. У каждого
свой `waf_node_id` (`edge-01` … `edge-03`) и свой агент; demo-пульсы контроллера здесь выключены
(`CONTROLLER_FLEET_DEMO=0`). Карточка флота — `http://localhost:8080/fleet`. Статистика балансировщика —
`:8404`.

Короткий прогон k6 по этому же стенду — кнопка **Трафик** в UX (`/traffic`). Сценарии:
ступенчатый прогон модуля (тела 1 KB…1 MB), CRS по `/modsec*`, VLAI по `/vlai*`
и combo ip → CRS → AI. На CRS / модели / combo размер тел
задаётся отдельно: `orig` оставляет корпус, корзины `1k`…`1m` добирают POST.
Ступени, состав и rps задаются на странице; генератор бьёт в HAProxy, nginx не пересоздаётся.

wrk живёт в контейнере `loadgen` и бьёт в `http://haproxy:8080` внутри сети
compose. Кнопка **Трафик** ходит туда через контроллер
(`CONTROLLER_LOADGEN_URL=http://loadgen:8090`). Ступень — число соединений wrk,
корпус сценария (CRS, IP, тела) тот же, что был у k6.

Отдельный нагрузочный стенд в `nginx/tests/load` для методики и длительных сценариев: там
`run.ps1` каждый раз поднимает свой compose.

## Защищаемое приложение

Его сейчас нет. Прежние -- эхо-`backend`, DVWA и OWASP Juice Shop -- снесены вместе со стендом
`juice.waf.test`, а новое ещё не написано. Пока его нет, у пространства нет ни одного сервера:
конфиг собирается пустым (`http` с инспекторами, ответами отказа и обменником), каналы сходятся,
трафика нет. Это законное состояние контура, а не поломка.

Заводя новое приложение, вернуть сюда: сервис в `deploy/docker-compose.yml`, пул и сервер в
пространстве, маршруты. Оговорка из прошлого опыта, которая переживёт смену приложения: апстрим
приложению задают переменной с docker-resolver'ом, а не блоком `upstream` -- имя в `upstream` nginx
разрешает при старте, и остановленный контейнер приложения означал бы «host not found in upstream»,
то есть упавший край и весь стенд следом. По той же причине приложение не ставят краям в
`depends_on`. Хвост `$request_uri` оставляет апстриму исходную строку запроса: с переменной nginx
послал бы нормализованный `$uri`, а это как раз предмет проверки -- обход каталога, двойное
кодирование, `%00`.

Первый сюрприз на загрузках -- `waf_body_limit request 1m` на уровне `http`: тело крупнее модуль не
читает вовсе, а судьбу такого запроса решает второе слово директивы, по умолчанию `block`.

## Сквозной прогон

```sh
docker compose exec -T nginx-1 sh /t/e2e/e2e.sh
```

Проверяет то, что видит клиент: код ответа и `X-WAF-Debug`. Ожидаемые коды
выведены из профилей `ip` и `modsec` и настроек `nginx/nginx.conf`, поэтому
правка любого из них ломает прогон осознанно. Скрипт возвращает число
провалившихся проверок, пригоден для CI.

Отдельный блок проверяет проксирование на `/app/`: что вердикт `allow` не мешает ответу приложения
дойти до клиента, `deny` не даёт запросу добраться до апстрима, а код, редирект и cookie самого
приложения не подменяются модулем.

Инспектор правил проверяется вторым прогоном:

```sh
docker compose exec -T nginx-1 sh /t/modsec/modsec.sh
```

Он отделён от `e2e.sh` не для порядка: там ожидаемые коды выведены из `rules.json` и от содержимого
запроса не зависят, здесь наоборот -- решает CRS по полезной нагрузке, и обновление набора правил
может сдвинуть счёт. Поэтому и маршруты у него свои, `/modsec*`, где тестовых инспекторов нет вовсе.

Тот же корпус с CLI, если UX не нужен:

```sh
docker compose exec -T loadgen k6 run /app/modsec.js
```

Ступени, классы, профили и размер тел — `STEPS`, `KINDS`, `PROFILES`, `BODIES`
(`STEPS=100:60 KINDS=clean,sqli PROFILES=default,strict BODIES=orig,64k`).
С UX то же самое на `/traffic`, сценарий **CRS / ModSec**.

IP фильтр -- отдельный прогон с хоста. Probe кладёт `client_ip` в сообщение на шину.
HTTP идёт через модуль: на `/ip*` `realip` читает `X-Forwarded-For`.
Большой список (GeoLite2 `us`) и k6 — `../tests/ip/ip-large.sh` и `loadgen/ip.js`.

```sh
sh ../tests/ip/ip.sh
```

Инспектор vlai -- отдельный прогон: модель смотрит на русское описание, не на
HTTP-атаку, и в `e2e.sh` не входит. HTTP идёт через `/vlai*` (порог 100 и 50).
Точный score не фиксируем, только пороги и код.

```sh
docker compose exec -T nginx-1 sh /t/vlai/vlai.sh
docker compose exec -T loadgen k6 run /app/vlai.js
```

Ступени по умолчанию `10:15`: один GPU-инстанс отвечает ~15–30 мс на короткий
абзац. С UX то же на `/traffic`, сценарий **VLAI**.

Связка CRS → модель: волна 0 режет классику, волна 1 смотрит русское описание,
которого в CRS нет. Одни и те же тела на `/modsec/` проходят, на `/modsec-vlai/`
дают 403.

```sh
docker compose exec -T nginx-1 sh /t/modsec-vlai/modsec-vlai.sh
docker compose exec -T loadgen k6 run /app/chain.js
```

Все комбинации ip → CRS → модель сразу: соло и три цепочки
(`/ip-modsec/`, `/ip-vlai/`, `/ip-modsec-vlai/`). Полный корпус —
адрес, CRS, бюллетень. На цепочках заголовки, query и тело живут в
обменнике `log` 15 с и архивируются на любой исход. В S3 — только тело.

```sh
docker compose exec -T nginx-1 sh /t/combo/combo.sh
docker compose exec -T loadgen k6 run /app/combo.js
```

Ступени по умолчанию `50:20,200:20`. Размер тел — `BODIES` (`orig`, `1k`…`1m`).
С UX сценарий **ip → CRS → AI**.

Наборы данных проверяются третьим прогоном, и он идёт из `nats-box`, а не из nginx:

```sh
docker compose exec -T nats-box sh /t/dataset/dataset.sh
```

Скрипт сам создаёт поток, публикует снапшоты и дельты и сверяет ответы nginx через `curl`.

Списки через контроллер — отдельный прогон: три `active` набора, точечные
200/403, затем soak (200 rps, пул 2000 CIDR, сотни add/remove в секунду
на UA и ключ). Коды проверяются на всех трёх nginx.

```sh
docker compose exec -T nats-box sh /t/lists/lists.sh
```

Порядок в `dataset.sh` существенный: проверка после каждой публикации ждёт, пока обновление доедет, а разрыв
нумерации проверяется публикацией дельты через номер -- модуль обязан отвергнуть её и запросить
снапшот, а не применить поверх чужого основания.

Тело и хранилища -- четвёртым прогоном, снова из nginx:

```sh
docker compose exec -T nginx-1 sh /t/body/body.sh
```

`modsec` читает Redis: одно и то же тело с «union select» даёт 403 и на
`/body/inline/`, и на `/body/store/`. Размещение каждого объекта видно в debug
(`body=hot:redis/…`, `headers=hot:redis/…`, `args=hot:redis/…`). В конце прогон
сверяет `DBSIZE` с начальным -- ключей после вердиктов оставаться не должно.

`e2e.sh` гоняет модуль на живых `ip` и `modsec`: вердикты, порог счёта,
passive/shadow/ignore, локальный rate, прокси на backend.

## Маршруты

Дефолтный набор -- `ip`. Отказ задаётся `X-Forwarded-For` из blocklist
(`203.0.113.0/24`). Тело и CRS -- на `/body/*` и `/modsec*`.

| Маршрут | Режимы инспекторов | Что показывает |
| --- | --- | --- |
| `/` | `ip` | частная сеть проходит, `203.0.113.10` -- 403 |
| `/passive/` | `ip` пассивен | `deny` попадает в лог, но отдаётся 200 |
| `/shadow/` | `ip` активен, `modsec` пассивен | новый инспектор наблюдает рядом с работающим |
| `/ignored/` | `ip` ignore | на шину не уходит ни одного сообщения |
| `/local/` | `ip` | локальный слой: проверки по наборам и лимит 5r/s с всплеском 5 |
| `/local-pass/` | `ip` | лимит с `action=pass`: превышение в логе, запрос идёт дальше |
| `/local-waves/` | `ip` → `crs` | лимит по волнам, а не по запросам: 10r/s, всплеск 10 |
| `/lists/` | `ip` ignore | три списка контроллера: CIDR, UA, `X-E2E-Key`; без rate |
| `/waf/captcha` | `waf off` | цель редиректа: открывается и при мёртвом инспекторе |
| `/healthz` | `waf off` | эталон без модуля, на нём же healthcheck контейнера |
| `/app/` | `ip` | проксируется на `backend`: настоящий апстрим, а не статика -- см. ниже |
| `:8082/` | `ip` пассивен на уровне сервера | как выкатывают инспектора, не рискуя трафиком |
| `/modsec/` | только `modsec` | вердикт по настоящему CRS, профиль `default` |
| `/modsec-strict/` | только `modsec`, профиль `strict` | тот же инспектор, другой набор правил на маршруте |
| `/modsec-unknown/` | только `modsec`, профиля нет | расхождение конфигурации: `deny`, не откат на `default` |
| `/modsec-passive/` | `modsec` пассивен | находка в теневой сумме, трафик не тронут |
| `/modsec-deny/` | только `modsec`, профиль `deny` | фикстура: 403 на любой запрос, вмешательство самого движка |
| `/modsec-allow/` | только `modsec`, профиль `allow` | фикстура: 200 на любой запрос, движок выключен |
| `/modsec-api/` | только `modsec`, профиль `api` | CRS XSS/SQLi без протокола 920, плюс правила сверху |
| `/body/inline/` | `modsec` | тело в Redis, имя маршрута историческое |
| `/body/store/` | `modsec` | то же: локатор на Redis |
| `/body/oversize/` | `modsec` | `waf_body_limit` ниже тела, политика по умолчанию `block` |
| `/body/oversize-pass/` | `modsec` | та же недоступность с `waf_body_limit 1k pass` |
| `/body/truncate/` | `modsec` | размещается префикс, сумма считается по телу целиком |
| `/body/rate/` | `modsec` | отсечение локальным лимитом до волн: тело не читается вовсе |

Вердикт задаётся запросом:

```sh
curl -i -H 'X-Forwarded-For: 203.0.113.10' localhost:8081/   # 403 по адресу
curl -i -H 'X-Forwarded-For: 8.8.8.8' localhost:8081/        # 200
curl -i "localhost:8081/modsec/?id=1'+or+1=1--"              # 403 по CRS
curl -i -H 'X-Forwarded-For: 203.0.113.10' localhost:8081/passive/  # 200, вердикт в логе
```

`proxy_pass http://backend/;` в `/app/` режет префикс `/app`, поэтому `/app/status/500` на
апстриме -- это `/status/500` из таблицы маршрутов [backend/README.md](../backend/README.md).

```sh
curl -i -H 'X-Forwarded-For: 203.0.113.10' localhost:8081/app/echo  # 403, до апстрима не дошло
curl -i localhost:8081/app/status/500                               # 500, вердикт allow, ответил апстрим
```

Это окружение предназначено для отладки: логи идут в stdout, `error_log` стоит на уровне `info`,
`worker_connections` равен 1024. Под нагрузкой каждое из этих значений искажает результат, поэтому
нагрузочный стенд собирается отдельно и со своей конфигурацией узла, переиспользуя отсюда только
образ и настройки NATS: [nginx/tests/load](../../nginx/tests/load).

Собственная диагностика модуля пишется на уровне `info`, поэтому он и выставлен в `nginx.conf` --
причём дважды, в `http` и на верхнем уровне. Второе не дублирование: подключение к шине, подписки на
наборы данных и переходы предохранителя происходят вне запроса и идут в лог цикла, а он по умолчанию
отсекает всё ниже `error`, и успешная подписка выглядит как её отсутствие.

```sh
docker compose logs -f nginx-1 | grep 'waf:'
```

Построчная раскладка печатается на каждый запрос: итог, причина, и отдельной строкой каждый
инспектор, который решил не разрешать, наблюдал пассивно, был пропущен или не ответил. Разрешающие
ответы активных инспекторов в лог не идут -- иначе на разрешённом трафике раскладку не прочитать.

То же самое в ответе, когда включён `waf_debug_header`:

```sh
curl -sD - -o /dev/null -H 'X-Forwarded-For: 203.0.113.10' localhost:8081/ | grep -i x-waf-debug
```

## Локальный слой

Зона `waf_shm_zone waf 8m;` объявлена на уровне `http`: без неё ни одна директива локального слоя не
загрузится -- и это нарочно, потому что молча отключённый ограничитель частоты выглядит работающим
ровно до того дня, когда он понадобится.

Лимит на `/local/` низкий (5r/s, всплеск 5) именно затем, чтобы превышение проверялось руками:

```sh
for i in $(seq 12); do curl -s -o /dev/null -w '%{http_code}\n' localhost:8081/local/; done
```

Первые шесть ответов -- 200, дальше 429 из записи каталога `too_many`. Отдельная запись здесь не для
разнообразия кодов: `429` клиент может исправить сам, и разница между «запрос запрещён» и «слишком
часто» должна до него доходить.

На `/local-pass/` тот же лимит объявлен с `action=pass`: код остаётся 200, а превышение видно только
в логе. Числа там отличаются от `/local/` не случайно -- счётчики отделены подписью правила, в которую
входят ключ, частота, всплеск и способ счёта, но не маршрут: одинаково объявленный лимит на двух
маршрутах был бы одной корзиной на оба.

`/local-waves/` считает опубликованные волны, а не запросы. Решение там принимается по уже
накопленному, поэтому превышение сказывается на следующем запросе того же ключа, а не на том, который
его создал: волны этого запроса ещё не опубликованы, и отсекать его нечем.

Circuit breaker виден в логе, когда инспектор перестал отвечать. На стенде
молчание больше нечем задать: заглушки нет. Предохранитель открывается сам,
если `ip` или `modsec` падают, -- смотреть `docker compose logs nginx-1 | grep 'circuit breaker'`.

## Наборы данных

Наборы объявлены в `nginx.conf` (`blocklist`, `allowlist` -- сети, `badua` -- строки), но потока с
такими subject в окружении по умолчанию нет: без него наборы просто пусты, и проверки по ним ничего
не находят. Поток создаётся прогоном, либо руками:

```sh
docker compose exec -T nats-box sh /t/dataset/dataset.sh setup
```

`--max-msgs-per-subject=1` в его настройках -- то, на чём держится доставка состояния новому воркеру:
поднявшийся после `reload` воркер просит у keeper снапшот и хвост и работает с
действующим составом, а не ждёт следующей дельты ([keeper.md](https://github.com/exemt/placitum-keeper/blob/develop/docs/spec.md)).

Внести запись можно и вручную -- тем же событием с ответом, что шлют инспектора:

```sh
docker compose exec -T nats-box nats req waf.sets.blocklist.event \
    '{"v":3,"op":"add","value":"198.51.100.7","ttl":300,"origin":"operator","reason":"MANUAL"}'
```

Из PowerShell то же самое не работает: оболочка съедает кавычки, и модуль получает не JSON. Отсюда и
`nats-box` как контейнер -- прогон и публикации идут изнутри, где `sh` предсказуем.

Когда набор не приезжает, полезны отдельные команды того же скрипта: `names` показывает ответ
`$JS.API.STREAM.NAMES` -- тот самый запрос, которым воркер ищет поток по subject; `info` -- состояние
консьюмера (`Last Delivery: never` значит, что доставки не было вовсе); `sniff` и `inbox` слушают
запросы к API и доставку в инбоксы воркеров; `subs` показывает подписки соединения так, как их видит
сервер.

```sh
docker compose exec -T nats-box sh /t/dataset/dataset.sh names
docker compose exec -T nats-box sh /t/dataset/dataset.sh info
```

## Изменения без пересборки

`nginx.conf` и `www/` смонтированы в контейнер:

```sh
docker compose exec nginx-1 nginx -t && docker compose exec nginx-1 nginx -s reload
```

После `reload` стоит убедиться, что старые воркеры ушли, а не остались висеть на таймерах шины:
воркер с висящим неотменяемым таймером не завершается никогда, и снаружи это выглядит как медленный
`reload`. В образе нет `ps`, поэтому список читается из procfs:

```sh
docker compose exec -T nginx-1 sh /t/procs/procs.sh
```

UX контроллера в образ копируется на `docker build` (`controller/ux` → `ux/dist`).
Правка панели на хосте в `:8080` не попадёт, пока не пересобрать сервис:

```sh
docker compose up -d --build controller
```

Пересборка всего контура — после правки исходников модуля:

```sh
docker compose up -d --build
```

## Инспектор правил

`inspector-modsec` -- Coraza со встроенным CRS 4, вердикт из содержимого запроса.
Отдельные маршруты `/modsec*` в `nginx.conf`, порог `waf_score_deny 50` -- при
действующей калибровке это ровно порог самого CRS.

```sh
curl -i "localhost:8081/modsec/?id=1'+or+1=1--"          # 403 по счёту
curl -i "localhost:8081/modsec-passive/?id=1'+or+1=1--"  # 200: тот же вердикт, но в тень
docker compose logs -f inspector-modsec
```

`/modsec-deny/` и `/modsec-allow/` -- профили-фикстуры: отвечают одинаково на любой запрос и потому
проверяют доставку тега профиля и применение вердикта, а не детект. `tests/modsec` их не трогает.

Профили монтируются из `../inspectors/modsec/profiles`, после правки достаточно
`docker compose restart inspector-modsec`; набор, который не компилируется, не даёт инспектору
стартовать. Проверка вердикта пробой, минуя nginx:

```sh
docker compose exec inspector-modsec modsec-probe --uri "/?id=1%27+or+1%3D1--" --profile strict
```

`nginx` ждёт `healthy` и `modsec`, и `ip`: набор CRS компилируется секунды, и запрос,
пришедший раньше, увидел бы политику `waf_deadline`, а не вердикт. Подробности -- в
[inspectors/modsec/README.md](https://github.com/exemt/placitum-modsec/blob/develop/docs/README.md).

## Redis

Экземпляра два, и роли у них не пересекаются.

**`redis` -- боевой обменник.** Горячее размещение заголовков, query и тела: `waf_store
driver=redis` в `nginx.conf`. Поднят с `maxmemory-policy noeviction`: тихое вытеснение ключа под
памятью для WAF означает тихое отключение проверки тела, и в бою так настраивать нельзя, поэтому
даже в отладочном окружении стоит привыкать к правильной политике сразу.

```sh
docker compose exec redis redis-cli info memory
docker compose exec redis redis-cli monitor   # SET с PX и DEL после вердикта
docker compose exec redis redis-cli dbsize    # после прогона обязан быть нулём
```

Ключ -- `<node>:<rid>:req`, то есть по нему видно, какой узел разместил тело и какой запрос его
прислал. `DEL` приходит сразу после вердикта, а `PX` из `ttl=` -- только страховка на случай падения
воркера между размещением и удалением. Адрес обменника инспекторы получают через `REDIS_URL`,
агент -- из `redis.url` в `agent.conf`, модуль -- из `waf_store url=`, который контроллер печатает
из `CONTROLLER_REDIS_URL`.

**`redis-internal` -- внутренний Redis контура.** Отдельный контейнер (512 МБ, 400 МБ данных,
та же политика `noeviction`), на хосте порт `6380`. В обменник он не заглядывает, модуль про него
не знает.

Оба адреса каждый процесс держит в своём конфиге одной формой -- блоком `redis`:

```
redis {
    url       redis://redis:6379;           # общий обменник: тела, заголовки, строка запроса
    internal  redis://redis-internal:6379;  # внутренний: всё остальное
}
```

Так он пишется в `inspector.conf` у инспекторов и в `agent.conf` у краёв (там `;` можно не
ставить). Окружение перекрывает файл двумя именами: `REDIS_URL` -- `url`, `REDIS_INTERNAL_URL` --
`internal` (у агента `WAF_REDIS_URL` и `WAF_REDIS_INTERNAL_URL`). Контроллер берёт оба из
`CONTROLLER_REDIS_URL` и `CONTROLLER_REDIS_INTERNAL_URL`, панель показывает их на странице
пространства рядом с адресом шины. Ключ, которого инспектор не читает, -- ошибка старта: у ip нет
`url` (в обменник он не ходит), у json, rewrite и vlai нет `internal` (своего состояния нет). Без
`internal` процесс пишет свои ключи в обменник, как до разделения, и при старте говорит об этом
предупреждением `internal redis falls back to the exchange`; откуда взят адрес, видно в строке
`internal redis … from=…` его журнала.

С 11.09 блок включён во всех `inspector.conf`; env в compose пока дублирует те же адреса и
снимается отдельным шагом.

Кто и что туда кладёт:

| Ключи | Пишет | Читает | Срок |
| --- | --- | --- | --- |
| `waf.blob.<sha256>` -- файлы поколений nginx, правил и наборов ip | контроллер, `SET NX EX 300` на каждый `send`; keep-alive раз в минуту продлевает срок блобам опубликованных указателей | края (`agent.conf`), `inspector-modsec`, `inspector-ip` (`internal` блока `redis` в `inspector.conf`) | 300 с, но опубликованное поколение живёт, пока жив контроллер; старые поколения сгорают сами |
| `cap:bkt:<профиль>:<вид>:<субъект>` | `inspector-captcha`, `captcha-http` | они же | срок = время стока корзины |
| `cap:nonce:*`, `cap:img:*`, `cap:fail:*`, `cap:lock:*`, отзыв | `captcha-http`, `inspector-captcha` (роастер) | они же | TTL челленджа / окна отказов |
| `auth:nonce:*`, `auth:fail:*`, `auth:lock:*`, отзыв | `auth-http` (роастер) | он же | TTL формы / окна отказов |
| корзины счётчика | `inspector-counter` (`internal` блока `redis`, перекрывает `REDIS_INTERNAL_URL`) | он же | срок = время стока корзины |
| `waf:set:<набор>`, `:why`, `:meta` -- состав активных наборов (спецификация keeper — `docs/spec.md` его репозитория) | `keeper` (`REDIS_INTERNAL_URL`) | панель контроллера (`CONTROLLER_REDIS_INTERNAL_URL`): состав, размер, поиск | без срока; снимается вместе с набором |
| `waf:diff:<набор>:<seq>` -- пакеты изменений, `waf:snap:<набор>:<epoch>:<seq>` -- снапшоты | `keeper` | края (`waf_sets_store`, печатает контроллер), `inspector-captcha`, `captcha-http`, `inspector-auth`, `auth-http`, `inspector-action`, `inspector-ip` -- `internal` блока `redis` | пакеты 90 с, снапшоты 30 с |

Размер: состав активного набора стоит ~200–260 байт на запись (ZSET и `why`), миллион
записей -- около 260 МБ при потолке `maxmemory 400mb`; переполнение при `noeviction` --
это отказ `store_unavailable` писателям (keeper память не трогает), а не вытеснение. Второй
горячий список такого размера в этот экземпляр не влезет -- потолок задан развёртыванием.

```sh
docker compose exec redis-internal redis-cli dbsize
docker compose exec redis-internal redis-cli --scan --pattern 'waf.blob.*' | wc -l
docker compose exec redis-internal redis-cli --scan --pattern 'cap:*'
```

Срок у блобов есть у всех -- 300 с (`BLOB_TTL_SEC`, controller/src/compile/pointer.ts), и
уборкой это и является: блобы старых поколений никто не продлевает, и они сгорают сами.
Опубликованное поколение держит keep-alive контроллера (controller/src/compile/keepalive.ts):
раз в минуту `EXPIRE` каждому блобу указателей nginx, правил и ip. Пропавший блоб (Redis
перезапущен, контроллер лежал дольше срока) он возвращает из плана того пространства, чей хеш
совпал с указателем; не совпал ни один -- база правлена после издания, в журнале `desired blobs
expired and cannot be restored`, лечится `publish`. Ноды со своей стороны промах не считают
финалом: агент, `inspector-ip` и `inspector-modsec` повторяют забор раз в 30 с (`retry_in` в их
журнале), пока тело не вернётся или не приедет новый указатель. `send` того же хеша тоже кладёт
блобы заново -- до сверки хеша, `SET NX EX`.

## Работа с шиной вручную

`nats-box` поднят вместе с остальными: `NATS_URL` в нём уже указывает на узел, поэтому сервер
указывать не нужно.

```sh
docker compose exec -T nats-box nats server info
docker compose exec -T nats-box nats stream ls
docker compose exec -T nats-box nats stream info WAF_AUDIT
docker compose exec -T nats-box nats sub 'waf.audit.>'    # итог запроса и вердикты инспекторов
docker compose exec -T nats-box nats sub 'waf.>'          # что уходит на шину
docker compose exec -T nats-box nats sub '_INBOX.waf.>'   # что приходит воркерам
```

`WAF_AUDIT` поднимает `core/bootstrap/streams.sh` при старте `nats-box`: subject `waf.audit.>`,
сутки, 256MB, `discard old`. Схема событий — [docs/audit.md](../audit.md#писатели).
Join одного запроса: `node` + `ray` + `phase`. Пересоздать поток вручную — тот же скрипт.

Логгер читает поток целиком, а не только `waf.audit.request.>`: якорь агента ложится в `waf.audit`,
находки инспекторов — в `waf.audit_finding`. Друг друга события не ждут, связывает их `ray` на чтении,
поэтому реплик у логгера может быть сколько угодно.
Filter subject у существующего durable consumer'а JetStream не меняет, поэтому consumer называется
`logger-audit-v2`. Старый после обновления остаётся висеть и копить сообщения — снять вручную:

```sh
docker compose exec -T nats-box nats consumer ls WAF_AUDIT
docker compose exec -T nats-box nats consumer rm WAF_AUDIT logger-audit --force
```

Схему ClickHouse логгер накатывает сам при старте, под замком `waf.schema_lock`: из двух реплик
накатывает одна, вторая ждёт и подхватывает, если первая умерла посреди (по возрасту пульса в
замке, две минуты). Миграции `024`–`031` пересоздают `waf.audit` и `waf.audit_finding` ради ключа
сортировки и переливают данные на месте: на стенде с двумя миллионами записей это минута-две, на
это время логгер не читает поток (JetStream копит), а журнал в панели показывает только то, что
записано после подмены, пока перелив не кончится. Старые таблицы на время перелива видны как
`waf.audit_v3` и `waf.audit_finding_v1`; если их нет, а `schema_migrations` кончается на `031`,
переезд завершён. Сорванный перелив безопасно идёт заново на следующем старте.

`WAF_LOG` поднимает тот же скрипт: subject `waf.log.>`, сутки, 128MB, `discard old`. Туда агент
кладёт строки `access_log` и `error_log`, снятые со своего сокета `/var/run/waf/log.sock`, а
инспекторы и их калитки — свой собственный журнал, той же пачкой и через собственный клиент шины.
Логгер читает поток вторым durable consumer'ом (`logger-log-v1`) в `waf.log`, а UX показывает
разделом «Логи». Дорога целиком — [docs/logger/logs.md](../logger/logs.md).

Поток заводит тот писатель, который пришёл первым: скрипт стендовый, а на живом контуре это может
оказаться и инспектор. `WAF_LOG_SHIP=off` в окружении процесса оставляет его журнал только в
stdout.

```sh
docker compose exec -T nats-box nats stream info WAF_LOG
docker compose exec -T nats-box nats sub 'waf.log.>'      # пачки строк с нод и процессов
```

Инбокс воркера ветвится: `<inbox>.v.<n>` -- вердикты, `<inbox>.js.<n>` -- ответы JetStream API,
`<inbox>.ds.<n>` -- доставка набора. Последняя ветка подписывается точным адресом, а не шаблоном:
push-консьюмер JetStream не доставляет в подтему, интерес к которой выражен только шаблоном. Это не
догадка, а измерение -- команда `probe` того же скрипта ставит два консьюмера рядом и показывает
разницу.
