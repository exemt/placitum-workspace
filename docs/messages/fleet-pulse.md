# Пульс флота

Кадр присутствия на шине: `PUB WAF_STATUS.<…>`, core NATS, fire-and-forget,
раз в 4 секунды. Это не аудит и не healthcheck контейнера. Контроллер слушает
`WAF_STATUS.>`, держит последний кадр каждого участника в памяти и сам считает
`degraded` по возрасту (15 с) и удаление (60 с). В Postgres не пишется.

Схема живёт в `controller/src/model/fleet.ts`; там же разбор, и он —
единственный вход кадра в контур.

| Кто | `kind` | Subject |
| --- | --- | --- |
| Агент ноды | `agent` | `WAF_STATUS.node.<node_id>.agent` |
| Воркер nginx | `worker` | `WAF_STATUS.node.<node_id>.worker.<pid>.<nonce>` |
| Инспектор | `inspector` | `WAF_STATUS.inspector.<имя>.<id>` |
| Сайдкар Redis | `redis` | `WAF_STATUS.store.redis.<id>` |
| Сайдкар S3 | `s3` | `WAF_STATUS.store.s3.<id>` |
| Сервис (logger, geo) | `service` | `WAF_STATUS.service.<имя>.<id>` |

Общее у всех — `v`, `kind` и `at` (RFC 3339 UTC). Дальше идентичность: у ноды
это `node_id`, у остальных `name` и `id` процесса — реплик несколько, и ключ
записи именно `id`. Поля `status` в кадре нет: живость считает получатель,
производитель отвечает только за `ready`.

## Секция `io`

Размеры и накопительные счётчики (`used_memory`, `objects`, `inserted`,
`accepted`) отвечают на вопрос «сколько всего», а не «сколько сейчас».
Разностью их не превратить в темп: запись живёт до первой минуты тишины, а
рестарт сервиса обнуляет счётчик, ничем не объявив об этом в кадре. Поэтому
темп считает производитель и кладёт в `io`.

Форма канала одна на весь контур — как локатор обменника и находка в
[README.md](README.md). Смысл тот же: один разбор на все `kind` и одна вёрстка
в UX вместо своей на каждый сервис.

| Поле | Единица | Что |
| --- | --- | --- |
| `ops` | 1/с | операций в секунду; обязательное, канал без него отбрасывается |
| `in` | байт/с | прочитано |
| `out` | байт/с | записано |
| `err` | 1/с | неудачных операций в секунду; входит в `ops` |
| `p50_ms` | мс | медиана времени операции |
| `p95_ms` | мс | 95-й перцентиль |
| `max_ms` | мс | худшая операция окна |
| `avg_ms` | мс | среднее за окно; инспекторы пишут для health-бара (≤100 зелёный, ≤500 жёлтый, дальше красный) |

Рядом с `io` едет `window_s` — окно усреднения. На чтение темпа оно не влияет
(в секунду есть в секунду), но без него нельзя сказать, насколько число
сглажено, и сравнивать каналы разных сервисов вслепую не стоит.

Что считать операцией, знает только имя канала:

| `kind` | Канал | Операция | Источник |
| --- | --- | --- | --- |
| `agent` | `audit` | датаграмма аудита с unix-сокета | `internal/handoff` |
| `agent` | `archive` | PUT объекта в S3 | `internal/retain`, вокруг `s3.put` |
| `inspector` | `inspect` | сообщение, доведённое до вердикта | `internal/queue` |
| `service` (logger) | `consume` | запись, снятая с JetStream | `internal/consume` |
| `service` (logger) | `insert` | строка, вставленная в ClickHouse | `internal/sink` |
| `redis` | `cmd` | команда Redis | дельта `INFO` между кадрами |
| `s3` | `api` | запрос S3 API | дельта prometheus-счётчиков MinIO между кадрами |

Записи в S3 с латентностью PUT по-прежнему показывает агент ноды (`archive`):
PUT делает он. Сайдкар не видит чужие вызовы, но у MinIO те же накопительные
счётчики, что `INFO` у Redis: `minio_api_requests_total` / traffic / errors
(и v2-имена `minio_s3_*`). Темп — дельта между кадрами, не проба `BucketExists`.
Обычный S3 без admin/metrics секцию `io` не отдаёт: жив бакет, объектов сколько
— есть, запросов в секунду — нет.

Redis, наоборот, отдаёт всё даром: `INFO stats`, которую сайдкар и так
запрашивает, содержит `total_commands_processed`, `total_net_input_bytes` и
`total_net_output_bytes`. Брать оттуда же `instantaneous_ops_per_sec` не
следует — у него своё окно около полутора секунд, которое сайдкар не
объявляет и не контролирует; дельта между двумя кадрами честнее.

## Два хеша ноды

В кадре агента их два, и это разные документы.

| Поле | Что | С чем сходится |
| --- | --- | --- |
| `config_hash` | `sha256:…` пака: шаблон до подстановки путей, как он приехал с шины | с изданным поколением -- отсюда «сошлось» на странице сходимости |
| `conf_fingerprint` | `md5:…` боевого `nginx.conf`, который агент положил на ноду | с `config_hash` воркеров -- отсюда «актуален» в таблице воркеров |

Воркер считает свой отпечаток сам, по файлу, с которым запущен
(`ngx_http_waf_presence_hash`), и поля `rev` у него нет: поколения он не знает.
Сравнивать воркера с `config_hash` агента нельзя ни при каких обстоятельствах
-- это md5 файла против sha256 пака, они не совпадут и на исправной ноде.

Отпечаток появляется в кадре и до первого apply: агент берёт его с диска на
старте, потому что воркеры работают по файлу прошлого запуска. Неудачный apply
его не меняет -- боевой файл остался прежним, о провале говорит `apply`.

## Как считать

Темп — кольцо секундных корзин, сумма за окно делённая на длину окна. Готовый
такой счётчик уже есть у агента: `nginx/agent/internal/rps` считает так `rps`
и `codes`. Он же — образец для остальных.

Время операции — гистограмма с логарифмическими корзинами, сбрасываемая
вместе с окном; из неё берутся `p50_ms`, `p95_ms` и `max_ms`. Одно среднее
прячет хвост: один PUT на две секунды растворяется в тысяче быстрых.
Поэтому распределение остаётся перцентилями. `avg_ms` — отдельное точное
среднее (сумма длительностей / число операций) и едет как health: у
инспектора на карточке это полоса 100 / 500 мс, а не замена p95.

## Пример

Кадр агента ноды: трафик через nginx в `rps` и `codes`, собственная работа
агента — в `io`.

  "id": "9f3c…",

  "conf_fingerprint": "md5:a036c6f4…",
  "rev": 43,
  "apply": "ok",
  "at": "2026-08-16T12:00:00.123456789Z",
  "rps": 1240.5,
  "codes": { "2xx": 1180.2, "3xx": 12.0, "4xx": 44.3, "5xx": 4.0 },
  "routes": [
    { "server": "shop.example.com", "location": "/api/",
      "id": "6a0b6d6e-1c2d-4e3f-8a9b-0c1d2e3f4a5b",
      "rps": 980.1, "codes": { "2xx": 940.0, "3xx": 0.0, "4xx": 38.1, "5xx": 2.0 } },
    { "server": "shop.example.com", "location": "/",

    "cpu": { "cores": 8, "usage": 0.23, "load1": 0.41, "load5": 0.38, "load15": 0.35 },
    "memory": { "total": 16777216000, "used": 4294967296, "available": 12482248704 },
    "disk": { "total": 214748364800, "used": 96636764160 },
    "uptime_s": 86400
  },
  "bus": { "reconnects": 1, "rtt_ms": 0.8 },
  "window_s": 10,
  "io": {
    "audit": { "ops": 1240.5, "in": 2621440 },
    "archive": {
      "ops": 3.2,

Секция необязательна целиком и по каждому полю: кадр без `io` разбирается как
прежде, канал без `ops` отбрасывается, отрицательные значения игнорируются.
Старый производитель и новый контроллер совместимы в обе стороны.

Статус: секцию пишут все производители из таблицы каналов. Фикстура в
[tests/pulse](../tests/pulse/README.md) остаётся для ручной проверки UX без
живого трафика — панель рисует одну и ту же форму что от неё, что от
production-кадра.

## Секция `routes` агента

Тот же темп, что `rps` и `codes`, разложенный по маршрутам конфигурации.
Считает его тот же счётчик по тем же датаграммам, поэтому сумма строк равна
`rps` кадра, а сумма классов — `codes`.

| Поле | Что |
| --- | --- |
| `server` | имя блока `server {}`: первое имя `server_name`, либо `_` у перехватчика по умолчанию |
| `location` | имя блока `location {}`: путь, регулярное выражение или `@имя`; `/` там, где блока нет |
| `id` | uuid пути из `waf_route_id`; входит в ключ маршрута, панель узнаёт по нему строку без сверки имён. Нет у модуля без директивы |
| `rps` | запросов в секунду за окно; обязательное |
| `codes` | тот же разбор по классам ответа, что у кадра |

Ключ — конфигурация, а не запрос: `server` это не заголовок `Host`, а
`location` не URI. Модуль печатает их в секцию `route` записи аудита
([agent.schema.ts](agent.schema.ts)), агент читает их оттуда и больше ни во
что не вмешивается. Поэтому мощность ключа ограничена размером конфига, и
клиент раздуть её не может. Потолок в `nginx/agent/internal/rps` (512
маршрутов на ноду) — страховка от патологического конфига; итог ноды он не
трогает, а превышение видно в кадре агента как `routes_dropped`.

Молчащего маршрута в списке нет вовсе. Ноль здесь означал бы «маршрут есть, и
на нём тихо», а кадр этого не знает: список считается по окну, и молчание
опустошает его так же, как удаление маршрута из конфига. Секции нет целиком,
пока нода не видела ни одного запроса.

Считаются запросы, а не записи аудита: в счётчик идёт только фаза запроса.
У запроса с инспекторами ответа записей две — отложенная запись запроса и
запись фазы ответа, — а у кадрового трафика (WebSocket, gRPC, SSE) по записи
на кадр. Фаза запроса есть у каждого запроса ровно одна: `waf on` входит в неё
всегда. Это же правило действует и для `rps`/`codes` ноды — иначе разбор по
маршрутам не сходился бы с итогом, рядом с которым он показан.

Что `waf off`, того здесь нет: маршрут без инспекции датаграмм не шлёт, и
метр меряет инспектируемый трафик, а не весь трафик nginx.

Контроллер складывает строки всех нод по паре «сервер + путь» и отдаёт их
секцией `routes` снапшота `/agent_health_socket`, дописывая `nodes` — сколько
нод видели маршрут в своём окне. Кадры degraded-нод в сумму не идут: degraded
— это молчание дольше 15 секунд, а окно счётчика 10, то есть числа в таком
кадре описывают то, чего уже нет. Страницы «Серверы» и «Пути» читают эту
секцию из того же снимка, что и страница состояния; своего сокета у них нет.

## Секция `waf` агента

Вердикты за окно `window_s`, всё в 1/с. `rps` и `codes` говорят, что ответил
апстрим; `waf` — что решил сам WAF. Нода может быть зелёной и слать 200-е,
пропуская всё без инспекции, — видно это только здесь.

| Поле | Что |
| --- | --- |
| `allow` | пропущено с вердиктом allow; обязательное |
| `deny` | заблокировано; обязательное |
| `challenge` | отправлено на проверку (captcha/JS) |
| `deadline_hits` | вердикта к `waf_deadline` не дождались |
| `fail_open` | из них пропущено без инспекции (policy pass) — метрика №1 |
| `fail_closed` | из них заблокировано (policy block) |

## Секция `bus`

Здоровье клиента шины у производителя, стандартно для всех `kind`, кроме
`worker`. Участник с флапающим NATS в остальном выглядит здоровым — он просто
«моргает» на странице; счётчик переподключений делает это видимым до того,
как участник пропадёт.

| Поле | Что |
| --- | --- |
| `reconnects` | переподключений с рождения процесса; обязательное |
| `rtt_ms` | последний RTT до сервера шины |

Рост `reconnects` между кадрами контроллер помечает как флап и отдаёт в
снапшот счётчиком за час (`bus_flaps_1h`).

## Секция `host.disk`

Диск с данными сервиса: `{"total": байт, "used": байт}`, необязательная часть
`host`. Место кончается чаще, чем CPU, — ClickHouse, MinIO и AOF Redis
съедают его молча.

## `work.lag` логгера

Отставание consumer-а от JetStream (pending). `clickhouse_ok: true` не значит
«успевает»: вставка может идти и при этом копить миллионы за спиной.

## Пометки контроллера

Не часть кадра — контроллер считает сам и кладёт в снапшот
`/agent_health_socket`:

| Поле снапшота | Как считается |
| --- | --- |
| `skew_ms` | время приёма минус `at`: перекос часов производителя |
| `restarts_1h` | сбросы `host.uptime_s` за час — рестарты, которые «up 2m» прячет |
| `bus_flaps_1h` | рост `bus.reconnects` за час |
| `evicted_1h` (redis) | прирост `evicted` между кадрами за час — потеря данных |

## Секция `errors`

Последние ошибки процесса — то, что оператор сейчас читает в логах контейнера,
когда карточка пожелтела. Секция стандартна для всех `kind`, кроме `worker`
(у него нет своей телеметрии), и необязательна: кадр без неё разбирается как
прежде.

```json
"errors": [
  { "at": "2026-08-16T11:59:58Z", "msg": "clickhouse: connection refused", "count": 12, "source": "insert" }
]
```

| Поле | Что |
| --- | --- |
| `at` | RFC 3339, время последнего повторения |
| `msg` | текст ошибки; производитель режет до 200 символов |
| `count` | сколько раз повторилась с первого появления; нет — значит один |
| `source` | имя канала `io` или подсистемы, где случилось; необязательно |

Производитель держит кольцо на 5 записей и дедуплицирует по `(source, msg)`:
повторившаяся ошибка сдвигает `at` и наращивает `count`, а не плодит записи.
Это не журнал и не замена логам — это «почему мне жёлтый», видимое с карточки
без похода в `docker logs`. Контроллер копирует список как есть (лишнее сверх
пяти отбрасывает, `msg` дорезает до 200) и отдаёт в снапшот
`/agent_health_socket`; темп ошибок по-прежнему едет числом в `io.*.err`,
здесь — их текст.

Статус: секцию не пишет пока ни один производитель — контроллер разбирает,
карточки показывают. Пока производители не подтянулись, кадры с `errors`
публикует фикстура [tests/pulse](../tests/pulse/README.md).

## Секция `work` инспектора

Не темп, а мгновенная загрузка реплики. Контроллер копирует числа как есть;
длину очереди UX рисует как health: `queued / queue_depth` по группе
(сумма реплик) и по каждому процессу.

| Поле | Что |
| --- | --- |
| `workers` | сколько обработчиков в процессе |
| `queue_depth` | ёмкость своей очереди (`queue_max` из `inspector.conf`) |
| `queued` | сколько запросов ждут в этом буфере, не считая тот, что сейчас в работе |
| `accepted` | сколько довели до вердикта с старта процесса |
| `shed` | отказали на входе, очередь полна (`queue_full drop`) |
| `expired` | сняли из очереди по бюджету |

`queued` — длина локального буфера у всех инспекторов. Клиент NATS держит
только prefetch (два сообщения): безлимитный `pending_msgs` больше не очередь.
