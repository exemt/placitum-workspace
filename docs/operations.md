# Эксплуатация

## Метрики

Отдаются в формате Prometheus через `waf_status`. Значения агрегированы по всем воркерам через
разделяемую память, поэтому не требуют суммирования по процессам.

### Решения

| Метрика | Тип | Метки | Смысл |
| --- | --- | --- | --- |
| `waf_requests_total` | counter | `phase`, `verdict` | Запросы по итоговым вердиктам |
| `waf_deny_total` | counter | `inspector`, `code` | Блокировки по инспектору и причине. Для блокировок по порогу метка `inspector` пуста, а `code` равен `SCORE_THRESHOLD` |
| `waf_redirect_total` | counter | `inspector` | Редиректы по инспектору, который их назначил |
| `waf_redirect_rejected_total` | counter | `inspector`, `reason` | Отбракованные цели: `not_allowed`, `bad_value`, `no_url`. Ненулевое значение означает либо расхождение `waf_redirect_allow` с конфигурацией сервиса, либо попытку увести трафик наружу |
| `waf_bypass_total` | counter | `reason` | Пропуски по `waf_response_bypass` |

### Счёт

| Метрика | Тип | Метки | Смысл |
| --- | --- | --- | --- |
| `waf_score` | histogram | `phase` | Распределение итоговой суммы. Бакеты стоит задать вокруг рабочих порогов, иначе распределение у порога не видно |
| `waf_score_deny_total` | counter | `phase` | Блокировок по достижении `waf_score_deny` |
| `waf_score_top_total` | counter | `inspector` | Кто чаще всех оказывается наибольшим вкладчиком при блокировке по порогу |
| `waf_inspector_score` | histogram | `inspector` | Распределение вклада отдельного инспектора. Основа для подбора `waf_score_deny` и режима вызова (`active` / `vote`) |

Архивация живёт в агенте, а не в модуле, поэтому её счётчики через `waf_status` не отдаются и в эту
таблицу не попадают: у агента своего эндпоинта метрик пока нет, наблюдать за ней приходится по
журналу (`archive: skipped`, `archive: put failed`, `archive: store cleanup failed`) и по доле
локаторов с `unavailable` в самой записи аудита. Первое, что стоит вывести, когда эндпоинт появится,
— глубина очереди и число записей с `overload`: именно они показывают, что
воркеров мало. `archive_error` — отказ `PUT`, а не нехватка очереди.

## Сходимость конфигурации

Не метрики модуля и не `waf_status`. Desired — `config_hash` шаблона в KV после `send`; actual —
heartbeat агента по тому же шаблону **до** подстановки `store:<uuid>`. Секреты в хеш не входят,
иначе контроллер не повторил бы значение. Состояния `drift` / `apply_failed` / `migrated` /
`undecryptable` и разбор UUID — [config-distribution.md](config-distribution.md#сходимость-флота).

Раскатка не закончена, пока в инвентаре есть узел не в `migrated`. Молчание heartbeat за TTL —
дыра, не успех.

## Алерты

Порядок отражает приоритет: первые два означают, что защиты может не быть прямо сейчас.

**Защита выключена молча.** Растёт доля `verdict="timeout_pass"` — запросы проходят без проверки.

```promql
sum(rate(waf_requests_total{verdict="timeout_pass"}[5m]))
  / sum(rate(waf_requests_total[5m])) > 0.01
```

**Инспектор не развёрнут.** Любой ненулевой `waf_inspector_absent_total` — ошибка конфигурации или
незапущенный сервис, а не перегрузка.

```promql
rate(waf_inspector_absent_total[5m]) > 0
```

**Circuit breaker открыт.** Инспектор фактически выключен.

```promql
max by (inspector) (waf_breaker_state) == 2
```

**Ложные срабатывания.** Резкий рост блокировок по одному инспектору обычно означает не атаку, а
неудачное обновление правил.

```promql
sum by (inspector) (rate(waf_deny_total[5m]))
  > 5 * sum by (inspector) (rate(waf_deny_total[1h] offset 1h))
```

**Порог перестал держать.** Доля блокировок по совокупности признаков выросла скачком. У этого две
разные причины, и различать их надо сразу: либо действительно началась распределённая атака, либо
один из инспекторов сместил свою шкалу после обновления правил и теперь тянет через порог обычный
трафик. Ответ даёт `waf_score_top_total`: во втором случае весь прирост приходится на одного
инспектора.

```promql
sum(rate(waf_score_deny_total[5m]))
  > 5 * sum(rate(waf_score_deny_total[1h] offset 1h))
```

**Латентность выходит из бюджета.**

```promql
histogram_quantile(0.99, sum by (le, phase) (rate(waf_phase_latency_seconds_bucket[5m]))) > 0.05
```

**Хранилище тела деградирует.**

```promql
rate(waf_body_unavailable_total[5m]) > 0
histogram_quantile(0.99, sum by (le, store) (rate(waf_body_put_latency_seconds_bucket[5m]))) > 0.01
```

**Утечка тел.** `waf_body_holds` растёт монотонно — значит удаление не работает, и хранилище наполнится.

```promql
deriv(waf_body_holds[15m]) > 0 and waf_body_holds > 1000
```

**Маскирование фактически выключено.** Любое срабатывание `waf_on_transform_error` с действием `pass`
означает, что приватные данные ушли в контур WAF.

```promql
rate(waf_transform_error_action_total{action="pass"}[5m]) > 0
rate(waf_transform_total{result=~"error|unparsable"}[5m]) > 0
```

**Сборка кадров растёт.** Клиент удерживает память бесконечной последовательностью фрагментов.

```promql
deriv(waf_reassembly_bytes[10m]) > 0 and waf_reassembly_bytes > 1e8
```

**Отбракованные ответы инспекторов.** Означает несовместимость версий или попытку прислать запрещённое.

```promql
rate(waf_inspector_invalid_total[5m]) > 0
```

**Наборы данных не обновляются.** Локальный слой работает по устаревшим спискам.

```promql
time() - waf_dataset_last_update_seconds > 600
```

**Лаг аудита.** Метрика на стороне JetStream; сам модуль его не видит.

```promql
nats_consumer_num_pending{stream="WAF_AUDIT"} > 1000000
```

## Подбор порогов и весов

Порог, назначенный из головы, — это либо выключенная защита, либо генератор ложных блокировок.
Единственный работающий способ — поставить его по распределению счёта на своём трафике.

**Шаг 1. Собрать данные, ничего не блокируя.** `waf_score_deny 0` оставляет вердикты `score`
работающими: инспекторы отвечают, счёт считается и пишется в аудит, но на трафик не влияет. Неделя
такого режима — нормальный срок, чтобы застать недельную сезонность.

**Шаг 2. Посмотреть на распределение, а не на среднее.** Интересна плотность у кандидата в пороги:
если рядом с ним много запросов, решение будет определяться шумом, и небольшое изменение правил
любого инспектора начнёт двигать долю блокировок. Порог ставится в разрежённую зону распределения.
Запрос — в [audit.md](audit.md#типовые-запросы).

**Шаг 3. Проверить, кто набирает счёт.** Если в блокируемой части один и тот же инспектор
единолично даёт почти весь счёт, порог не делает ничего полезного: он воспроизводит вердикт этого
инспектора с лишним шагом. Либо снижайте ему вес, либо признайте, что он должен отвечать `deny`.

```sql
SELECT score_top, count() AS c,
       round(avg(scores[score_top]) / avg(score_total), 2) AS share
FROM waf.audit
WHERE ts > now() - INTERVAL 1 DAY AND deny_code = 'SCORE_THRESHOLD'
GROUP BY score_top ORDER BY c DESC;
```

Доля выше примерно 0.8 означает именно этот случай.

**Шаг 4. Оценить эффект нового инспектора до включения.** Совещательный вклад пишется отдельно,
поэтому «что было бы» считается на исторических данных без единого затронутого запроса. Здесь же
подбирается вес: тот же запрос с другим множителем показывает, сколько запросов перешло бы порог.

```sql
SELECT countIf(score_total >= score_deny_at)                          AS now_denied,
       countIf(score_total + 0.3 * scores_advisory['ml'] >= score_deny_at) AS would_deny,
       count()                                                        AS total
FROM waf.audit
WHERE ts > now() - INTERVAL 1 DAY AND has(inspectors, 'ml') AND score_deny_at > 0;
```

**Шаг 5. Проверить полосу под порогом челленджем.** Сервис челленджа получает накопленный счёт и решает
по нему сам, поэтому его собственный порог — вторая, независимая точка настройки. Полоса ниже
`waf_score_deny`, в которой сервис требует доказательство, отвечает на вопрос, который распределение
само не даёт: если челлендж в этой полосе проходит подавляющее большинство запросов, порог блокировки
стоит слишком низко и ловит людей, а не ботов. Обратное тоже информативно.

Различие в том, где живут эти два порога. Порог отказа — в `waf_score_deny` на маршруте, порог
челленджа — в конфигурации сервиса, и подбираются они по разным данным: первый по распределению счёта,
второй по доле успешно пройденных проверок. Смешивать их в одном месте значило бы менять политику
блокировки, настраивая капчу.

Порог отказа — часть политики, а не константа продукта. Пересматривать его имеет смысл после каждого
заметного обновления правил у любого из инспекторов, потому что смещается шкала, а не только детект.

## Диагностика типовых аварий

### Латентность выросла на всех маршрутах

Смотреть `waf_wave_latency_seconds` по волнам, а не суммарную латентность фазы. Волна ждёт самого
медленного участника, поэтому один деградировавший инспектор в волне 0 добавляет свою задержку каждому
запросу.

Проверить `waf_breaker_state`: если breaker не открылся, значит инспектор отвечает, но медленно, а
порог breaker настроен только на таймауты. Быстрая мера — снизить `timeout=` этого инспектора, чтобы
он начал попадать в таймауты и breaker сработал.

Отдельно проверить `waf_body_put_latency_seconds`: деградация Redis выглядит как рост латентности всех
маршрутов с телом при нормальных латентностях инспекторов. Отличительный признак — растёт
`body_wait_us` в аудите, а `inspectors_latency` в норме.

### Часть запросов проходит без проверки

Проверить по порядку: долю `timeout_pass` (сработала политика fail-open), `waf_breaker_state`
(инспектор отключён breaker'ом), `waf_inspector_absent_total` (сервис не запущен), `mode=passive` у
вызова (случайно оставлен после проверки), `waf_bypass_total` (маршрут попал под
`waf_response_bypass`), наличие `waf off` в отработавшем location.

Последнее проверяется в аудите: поле `route_location` покажет, какой location применился, что часто
оказывается не тем, который ожидался.

### Пользователи в цикле редиректов на капчу

Немедленная мера — убрать сервис челленджа из `waf_inspect` затронутого location. Это
работает без участия сервиса и без правки его конфигурации: невыбранный инспектор не опрашивается, а
редирект в модуле больше ниоткуда не возникает. Альтернатива той же силы — снять `waf_redirect_allow` на
маршруте, тогда цели начнут отбраковываться, но каждый запрос продолжит платить за волну.

Затем проверить, в чём причина. Со стороны конфигурации: есть ли `waf off` в location цели; входит ли
цель в `waf_redirect_allow` (иначе в логе будет `waf_redirect_rejected_total` с `not_allowed`, и цикла
как раз не будет — будет политика `waf_deadline`); не форсирует ли `waf_cookie_defaults` атрибут, из-за которого
браузер не возвращает cookie — `secure=on` на контуре без TLS или `same_site=Strict` при переходе с
внешнего домена. Со стороны сервиса: выдаёт ли он cookie, принимает ли свой же clearance, работает ли
его предел попыток.

Запрос для оценки масштаба, по повторным редиректам одному клиенту:

```sql
SELECT client_ip, count() AS redirects, uniq(uri) AS uris
FROM waf.audit
WHERE ts > now() - INTERVAL 30 MINUTE AND verdict = 'redirect'
GROUP BY client_ip HAVING redirects > 3
ORDER BY redirects DESC LIMIT 50;
```

Много клиентов с десятками редиректов за полчаса означает, что clearance не принимается. Номера попытки
в аудите модуля нет — его знает только сервис, у него же и смотреть раскладку по попыткам.

### Заблокирован легитимный трафик

Найти правило и инспектора:

```sql
SELECT deny_code, count() AS c,
       uniq(client_ip) AS ips, groupUniqArray(5)(uri) AS sample_uris
FROM waf.audit
WHERE ts > now() - INTERVAL 1 HOUR AND verdict = 'deny'
GROUP BY deny_code
ORDER BY c DESC LIMIT 20;
```

Правильная последовательность действий: перевести инспектора в `mode=passive` на затронутом маршруте,
подтвердить по аудиту, что блокировки прекратились, а вердикты продолжают собираться, затем исправить
правило и вернуть `mode=active`. Это лучше, чем выключать инспектора целиком: вы сохраняете
видимость и не теряете данные для исправления.

Если отказ по порогу, в `inspectors_verdict.agent` стоит
`code=SCORE_THRESHOLD`. Отдельного `deny_inspector` нет — вкладчиков
смотреть в раскладке счёта:

```sql
SELECT score_top, score_deny_at, round(avg(score_total)) AS avg_score,
       count() AS c, uniq(client_ip) AS ips, groupUniqArray(5)(uri) AS sample_uris
FROM waf.audit
WHERE ts > now() - INTERVAL 1 HOUR AND deny_code = 'SCORE_THRESHOLD'
GROUP BY score_top, score_deny_at
ORDER BY c DESC LIMIT 20;
```

У блокировки по порогу есть немедленная мера, которой нет у обычной: поднять `waf_score_deny` на
затронутом маршруте и перечитать конфигурацию. Это снимает блокировки, не выключая ни одного
инспектора и не трогая ни один сервис, — детект продолжает работать и писать в аудит, пока вы
разбираетесь. Средний счёт из запроса выше подсказывает, до какого значения поднимать; если он лишь
на единицы превышает порог, дело почти наверняка в сместившейся шкале одного инспектора, а не в
атаке.

### Пропускная способность WebSocket-соединений упала

Признак — сообщения от клиента доставляются с задержкой, кратной времени round-trip, а
`waf_frame_latency_seconds` в норме. Это не деградация, а свойство режима `gate`: в пределах одного
направления одновременно выносится не более одного вердикта, поэтому пропускная способность соединения
ограничена величиной, обратной RTT. При полумиллисекундном RTT это около двух тысяч сообщений в секунду.

Проверить фактическую частоту сообщений по `waf_frames_total`. Если она приблизилась к границе, вариантов
три: перевести направление в `waf_frame_mode monitor`, включить `waf_frame_sample` меньше единицы, либо
разместить инспектор кадров локально, чтобы сократить RTT. Увеличение `waf_frame_deadline` не помогает —
ограничение задаёт RTT, а не таймаут.

### Хранилище тела наполняется

`waf_body_holds` растёт, `waf_body_delete_total{result="ok"}` не растёт пропорционально
`waf_body_put_total`. Причины по частоте: воркеры падают между `put` и `del` (смотреть лог ошибок
nginx на предмет segfault); дедлайн маршрута велик, а инспектор залип, поэтому тела висят весь дедлайн;
драйвер не поддерживает удаление и работает только на TTL.

Немедленная мера — снизить `waf_body_max_holds`, чтобы отказ в размещении наступал раньше исчерпания
хранилища, и убедиться, что `waf_exception <фаза> body` даёт приемлемое поведение.

### Аудит отстаёт или теряется

Растёт `nats_consumer_num_pending` — ClickHouse не успевает или недоступен. Проверить
`system.errors` и таблицу с ошибками разбора: `nats_handle_error_mode = 'stream'` направляет их в
виртуальные колонки вместо остановки конвейера, и там обычно видна причина.

Растёт `waf_audit_dropped_total` — переполнен буфер исходящих на стороне модуля. Проверить
`waf_bus_pending_bytes` и увеличить `pending_max`, но сначала убедиться, что причина не в недоступности
шины.

Ошибка «too many parts» в ClickHouse означает недостаточный батчинг. Увеличивать `batch=` в
`waf_audit` и `nats_max_block_size` в таблице-очереди, а не количество ресурсов ClickHouse.

## Регулярные проверки

**Ежедневно:** доля `timeout_pass` за сутки, топ причин блокировок на резкие изменения, лаг аудита,
сходимость `config_hash` по флоту.

**Еженедельно:** пересмотр таймаутов по квантилям из аудита (запрос в
[audit.md](audit.md#типовые-запросы)); кандидаты в ложные срабатывания; распределение счёта против
действующих порогов; объём и рост таблицы аудита против TTL.

**Ежемесячно:** проверка восстановления при недоступности каждого инспектора на тестовом контуре;
проверка поведения при недоступном хранилище тела и при недоступном сервисе маскирования; ревизия всех
`waf off` в конфигурации; проверка ротации ключей подписи clearance и шифрования тел; сверка фактически
применяющихся правил маскирования по полю `body_transform_rules` с ожидаемыми, чтобы слепые зоны в детекте
оставались известными.

**Перед каждым изменением правил инспектора:** прогон в `mode=passive` с оценкой доли срабатываний по
реальному трафику. Это единственный способ отличить исправление детекта от новой волны ложных
блокировок до того, как её увидят пользователи. Для инспектора, отвечающего `score`, проверяется не
только доля срабатываний, но и смещение шкалы: обновление правил, поднявшее типичную оценку с
сорока до шестидесяти, ничего не меняет в поведении самого инспектора и при этом сдвигает через
порог часть трафика.
