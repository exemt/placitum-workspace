# Раскладка по репозиториям: core, shared, компоненты

Документ для принятия решений, а не их запись. Контур разъезжается по отдельным репозиториям
([delivery.md](delivery.md)), и до того как уедет второй компонент, надо договориться о трёх
вещах: что считать фундаментом (`core`), что вынести в общий код (`shared`) и что остаётся у
компонента. Цифры ниже — замеры по дереву на 12.09.2026, не оценки.

Решено на сегодня: имена `placitum/<компонент>` (репозиторий, образ и путь модуля — одно имя);
документ живёт у хозяина — устройство компонента в репозитории компонента, контракт контура в
платформе. Всё остальное в этом документе — предложения.

## Три слоя

```
core        фундамент: инфраструктура, схемы баз, потоки, секреты, бутстрап контура
shared      общий код процессов: пульс, журнал, очередь, протокол, конфиг, гео-клиент
компоненты  инспекторы, сервисы, контроллер, модуль nginx -- по репозиторию на каждый
```

Слои связаны в одну сторону: компонент зависит от `shared`, установка зависит от `core`,
`core` не знает про компоненты ничего, кроме имён образов и порядка запуска.

## core

**Что это.** Не код, а поставка окружения: то, чем поднимают контур до первого компонента, и то,
без чего компонент не стартует. Своих образов у `core` нет — ClickHouse, NATS, Redis, Postgres и
MinIO берутся официальные; `core` даёт им конфигурацию, схему и порядок.

Состав и состояние на 12.09.2026 — каталог [`core/`](../core/README.md) уже заведён:

| Что | Откуда | Состояние |
| --- | --- | --- |
| Сервисы инфраструктуры одним файлом | из `deploy/docker-compose.yml`, где лежал весь контур | `core/compose/infra.yml`: шесть сервисов и два клиента бутстрапа; стенд включает его через `include` |
| Конфиги: `nats-server.conf`, XML ClickHouse, lifecycle бакетов MinIO | `deploy/nats`, `deploy/clickhouse`, `deploy/minio` | переехали в `core/config/` |
| Потоки JetStream `WAF_AUDIT` и `WAF_LOG` | `tests/streams/streams.sh` — то есть в тестах | переехал в `core/bootstrap/streams.sh` |
| Ключ контура и реквизиты | `deploy/secrets/gen.mjs` | остались у установки: ключ и hmac — свойство инсталляции, а не инфраструктуры |
| Схема ClickHouse | `logger/schema` (35 миграций, накатывает логгер) | у владельца данных, см. спор ниже |
| Схема Postgres | `controller/schema` (103 файла) | у владельца данных; накатчика нет вовсе — `core/migrate/README.md` |
| Проверка готовности контура | `tests/*`, руками | не сделана |
| Файл установки: компоненты со сборкой из их репозиториев (`build.context` на git-URL) | стенд собирает из локальных путей | не сделан — ждёт разъезда компонентов |
| Манифесты Kubernetes | — | не сделаны |

**Спорное: миграции.** Три расклада.

1. **Схема остаётся у владельца данных.** Логгер накатывает ClickHouse (уже так и делает:
   `schema_migrations` плюс `schema_lock` — две реплики не подерутся), контроллер накатывает
   Postgres. `core` только поднимает базы. Плюс: DDL и код, который в эти таблицы пишет,
   выпускаются вместе и разъехаться не могут. Минус: порядок обновления контура неявный.
2. **Схемы переезжают в core.** `core` накатывает обе базы, компоненты считают таблицы
   существующими. Плюс: одна точка для апгрейда установки. Минус: версия схемы и версия кода
   выпускаются порознь — это тот самый перекос, от которого спасает первый вариант.
3. **Пополам:** бутстрап (создать базу, пользователя, словари, бакеты) — в `core`, DDL своих
   таблиц — у владельца.

Рекомендую **третий**: бутстрап и порядок — в `core`, DDL — у компонента, а `core` запускает
миграции, дёргая образ компонента (`docker compose run --rm logger migrate`). Тогда «кто пишет в
таблицу — тот и объявляет таблицу» остаётся правилом, а установка всё равно обновляется одной
командой.

**Отдельная дыра, которую core обязан закрыть.** У Postgres контроллера **нет накатчика миграций
вовсе**: 103 файла `controller/schema` применяются только `docker-entrypoint-initdb.d` на пустом
томе. Живая установка не обновляется никак — руками. У ClickHouse накатчик есть и работает
(`logger/internal/migrate`), его модель и стоит повторить.

## shared

**Заведён 12.09.2026** и выложен в `github.com/exemt/placitum-shared`, версия `v0.1.0`:
`pulse`, `host`, `flow`, `loglevel`, `netinfo`, `geopb` — те шесть, что совпадали у всех
байт в байт. Первым на него переведён инспектор действий: модуль тянется из публичного
прокси, а в платформе правка видна сразу через `go.work`. `v0.2.0` (тем же вечером): `logkit`
— журнал сервиса, восемь копий совпадали байт в байт; словарь уровней у него теперь общий
с инспекторами (`loglevel.Env`). `v0.3.0` (тот же вечер): шапка кадра присутствия `pulse.Frame`,
`dataset` в двух режимах, `logkit.Sink` у инспекторов вместо `logsink`; копий `host` и `flow`
не осталось. `v0.4.0` (ночь на 13.09): сборка процесса (`version`, `revision`) в шапке кадра,
`geopb` перегенерирован с `go_package` этого модуля.

Установка из публичных репозиториев впервые прошла целиком 13.09 (этап 6 плана перехода):
свежий клон `placitum-core`, все образы из git-контекстов, дым через API и узел.

**Сколько стоит его отсутствие.** Двенадцать пакетов лежат копиями в девяти модулях инспекторов:

| Пакет | Строк | Копий | Что это |
| --- | --- | --- | --- |
| `netinfo` | 1108 | 8 | клиент кодера гео, кэш, отрицательный кэш |
| `config` | 785 | 9 | разбор `inspector.conf`, цепочка окружения |
| `desired` | 773 | 9 | поколение из KV: staging, применение, откат |
| `protocol` | 683 | 9 | схема сообщений шины |
| `logsink` | 656 | 9 | журнал процесса в `waf.log` |
| `audit` | 651 | 9 | событие `kind=inspector` пачками |
| `geopb` | 536 | 8 | сгенерированный gRPC-клиент гео |
| `queue` | 503 | 9 | очередь, воркеры, дедлайны |
| `flow` | 327 | 9 | счётчики ввода-вывода для пульса |
| `loglevel` | 195 | 9 | словарь уровней nginx |
| `host` | 156 | 9 | снимок хоста для пульса |
| `pulse` | 94 | 9 | кадр присутствия |

6467 строк на модуль, девять модулей — около 58 тысяч строк почти одинакового кода. Плюс вторая
семья: у сервисов и агентов тот же журнал был написан заново под именем `logkit` — восемь
копий; с `v0.2.0` он в `shared`.

И это уже расходится: `flow`, `host`, `pulse` у `action` и `counter` совпадают байт в байт, а
`queue`, `protocol` и `logsink` — уже нет. Цена расхождения известна по конверту секретов: три
реализации одного формата, и раскатка не работала вовсе при полностью исправном ключе.

**Три способа.**

1. **Общий Go-модуль** `placitum/shared`, компонент пинует версию в `go.mod`. Плюс: одна
   реализация, семвер, обновление осознанное. Минус: сборка компонента требует доступа к модулю
   (для публичных репозиториев — обычный прокси модулей, без реквизитов), и выпуск идёт в два
   шага: сначала `shared`, потом компоненты.
2. **Копия в каждом репозитории**, как сейчас. Плюс: компонент самодостаточен, сборка ничего не
   тянет. Минус: расхождение — не риск, а наблюдаемый факт.
3. **Генерация:** один исходник в монорепозитории, скрипт раскладывает копии по компонентам при
   split. Плюс: одна правка, никакой сетевой зависимости. Минус: в репозиториях лежит код,
   который нельзя править, и это придётся объяснять каждому, кто туда придёт.

Выбран **первый** и уже сделан: в монорепозитории лежит
`go.work`, перечисляющий все модули, — тогда правка в `shared` видна компонентам сразу, без
выпуска версии. В поставочную ветку `go.work` не попадает (его там нет), и сборка идёт по пину из
`go.mod`. Правило «каталог компонента самодостаточен» при этом сохраняется: единственная внешняя
зависимость — публичный модуль с фиксированной версией, такой же, как `nats.go`.

**Грабля перевода на shared.** `go.work` прячет отсутствующий `require`: в платформе компонент
собирается, потому что workspace находит модуль на диске, а сборка образа (где `go.work` нет)
падает на `no required module provides package`. После перевода компонента обязателен
`GOWORK=off go mod tidy` — он и запишет зависимость в `go.mod`.

**Что едет в shared:** пульс, журнал процесса и уровни, счётчики потока, снимок хоста, очередь и
дедлайны, схема сообщений шины, разбор `inspector.conf` и цепочка окружения, поколение из KV,
клиент гео и его protobuf, зеркало активных наборов, отправка событий аудита.

**Что не едет:** всё, в чём есть решение инспектора. Профили, условия, вердикты, пороги, политика
— это и есть компонент. Правило простое: в `shared` попадает то, у чего один смысл на весь контур
и один хозяин; как только у кода появляется «а у нас иначе», он остаётся дома.

**Версии.** `shared` выпускается семвером и не ломает мажор ради удобства: пятнадцать компонентов
не переписываются разом. Компонент обновляет пин, когда ему нужно, — кроме обновлений контракта
шины, где порядок обратный (сначала все читатели, потом писатели).

## Компоненты

По репозиторию на каждый: восемь инспекторов на Go, `vlai` на Python, `keeper`, `geo`, `logger`,
`crypto`, четыре агента, контроллер с панелью, модуль nginx. У компонента остаётся его суть:
профили, политика, схема его таблиц, его Dockerfile, его доки и его образ.

Порядок разъезда и чек-лист готовности — [delivery.md](delivery.md). `core` и `shared` получают
поставочные ветки на тех же правилах, что остальные.

## Имена

Одно имя на три вещи: репозиторий `github.com/placitum/<компонент>`, образ
`placitum/<компонент>`, путь модуля `github.com/placitum/<компонент>`. Модуль переименовывается
**в монорепозитории**, разом у всех, а не в момент split: иначе каждая ветка требует правки
импортов, и копии расходятся — как уже вышло с `waf-ip`.

Перекрёстных импортов между модулями в дереве нет (единственное упоминание чужого пути —
`go_package` внутри `geo.proto`), поэтому переименование ничего не ломает: сегодня путь модуля —
просто имя, по сети он не резолвится. С появлением `shared` это перестанет быть верным, и тогда
имя должно быть уже настоящим.

Про домен: путь вида `go.plcwaf.com/logger` даёт независимость от того, где лежит репозиторий, но
требует, чтобы домен отдавал метку вечно. Раз домен временный — не стоит: имя площадки стабильнее
временного домена. Занятость проверена 12.09.2026: `github.com/placitum` существует как
пользователь с нулём публичных репозиториев (возможно, свой — проверить), публичных образов
`placitum/*` на Docker Hub нет.

## Открытые вопросы

| Вопрос | Варианты | Состояние |
| --- | --- | --- |
| Миграции: у владельца, в core или пополам | см. раздел core | предложено «пополам» |
| Накатчик миграций Postgres | писать в core / писать в контроллере | не решено; дыра есть уже сейчас |
| `shared`: модуль, копия или генерация | см. раздел shared | предложен модуль плюс `go.work` |
| Когда заводить `shared` | до разъезда / после первых трёх репозиториев | не решено |
| Имя площадки `placitum` на GitHub | занято пользователем — свой или чужой | проверить |
| Приватная монорепа и ссылки из публичных реп | пересказ сейчас, ссылки после публикации | предложено |
| Сборка в изолированном контуре: `vendor/` в репозиториях или своё зеркало модулей | важно, потому что образы собирает установка, а не мы | не решено |
| Имена образов на стенде (`waf-*`) против выбранных `placitum/*` | переименовать разом или по мере разъезда компонентов | не решено; `deploy/deliver.mjs` уже зовёт их `placitum/*` |
