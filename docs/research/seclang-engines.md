# Выбор движка SecLang

## Вопрос

«Движок ModSecurity» — это три разных продукта с общим языком правил. Какой из них брать для
инспектора правил, описанного в [modsecurity-inspector.md](modsecurity-inspector.md).

## Короткий ответ

Coraza — для референсной реализации. libmodsecurity v3 — если требуется побитовое совпадение
поведения с уже работающим у вас развёртыванием ModSecurity v3 или если в наборе есть правила,
опирающиеся на возможности PCRE, которых нет в RE2.

Существенно, что выбор обратим. Инспектор общается с модулем по протоколу вердикта, движок за этим
протоколом не виден вообще. Заменить реализацию — значит поменять образ сервиса, а не тронуть
конфигурацию nginx. Более того, оба движка можно какое-то время держать на одном трафике
одновременно: один `active`, второй `passive` под другим именем, и сравнить их вердикты по
аудиту. Это самый дешёвый из существующих способов принять такое решение по фактам.

## Кандидаты

**ModSecurity v2** (актуальная 2.9.14) — модуль Apache, плотно сросшийся с его внутренностями и APR.
Как отдельный сервис запускается — именно его оборачивает `haproxy/spoa-modsecurity`, — но ценой
эмуляции окружения Apache вокруг движка. Для новой разработки смысла нет: это работа ради
совместимости с наборами правил, которые давно портированы.

**libmodsecurity v3** (актуальная 3.0.16, июнь 2026) — самостоятельная библиотека на C++ с C API,
написанная как раз для встраивания вне Apache. С января 2024 сопровождается OWASP; выпуски выходят
регулярно, преимущественно с исправлениями безопасности.

**Coraza v3** (актуальная 3.3) — реализация SecLang на Go, тоже под крылом OWASP, полностью
совместимая с CRS v4. Для неё уже существует внепроцессный демон `coraza-spoa`, то есть роль,
идентичная нашему инспектору, для этого движка отработана.

## Сравнение по значимым для нас критериям

| Критерий | libmodsecurity v3 | Coraza v3 |
| --- | --- | --- |
| Язык | C++, C API | Go |
| Безопасность памяти | Ручная. За 2026 год — переполнения буфера в парсере multipart, `hex_decode`, `@pm` | Гарантирована рантаймом |
| Регулярные выражения | PCRE2, экспоненциальный бэктрекинг возможен, ограничивается `SecPcreMatchLimit` | RE2, линейное время по построению |
| Возможности регулярных выражений | Обратные ссылки, lookaround, вся PCRE | Без обратных ссылок и lookaround: ограничение RE2 |
| Многопоточность | Транзакции параллелятся, набор правил только на чтение; история гонок в этой области длинная | Транзакции конкурентно-безопасны по контракту |
| Отмена оценки | Нет | Нет |
| Совместимость с CRS v4 | Эталонная | Заявлена полная, набор тестов CRS проходит |
| Полнота SecLang | Эталонная | Часть возможностей отсутствует или включается флагами сборки |
| Стоимость интеграции с нашим скелетом инспектора | cgo либо сервис целиком на C | Прямая: скелет из `inspectors.md` уже на Go |
| Прецедент внепроцессного запуска | `spoa-modsecurity` (для v2) | `coraza-spoa` |

## Что из этого действительно решает

**Регулярные выражения.** Это главный аргумент, и он двусторонний. RE2 исключает целый класс атак:
специально подобранный ввод не может раздуть время оценки на порядки. В системе, где каждый запрос
имеет дедлайн в десятки миллисекунд, а один залипший воркер пула уменьшает пропускную способность
сервиса, это не теоретическое преимущество. Обратная сторона — RE2 не поддерживает обратные ссылки и
lookaround, поэтому набор правил, где они используются, в Coraza просто не соберётся. CRS написана с
оглядкой на это, а вот собственные правила надо проверять.

**Безопасность памяти.** Разбор недоверенного ввода на C++ даёт CVE регулярно — это видно по истории
выпусков. Вынос движка в отдельный процесс уже снижает последствия радикально (см.
[modsecurity-inspector.md](modsecurity-inspector.md#почему-не-штатный-коннектор-в-nginx)), но разница
между «сервис упал и перезапустился» и «класса ошибок нет» сохраняется. Падение процесса на C++
теряет все транзакции в полёте разом, включая те, что уже стояли в очереди; для инспектора с пулом
воркеров это десятки запросов, обрабатываемых потом по политике `waf_deadline`.

**Стоимость интеграции.** Референсный скелет инспектора в
[inspectors.md](../inspectors.md#скелет-инспектора) написан на Go, клиент NATS для Go — основной и
самый обкатанный. С Coraza инспектор — это тот же скелет плюс вызовы движка. С libmodsecurity
вариантов два, и оба дороже: cgo (накладные расходы вызова на фоне миллисекунд оценки ничтожны, но
появляется смешанная сборка, смешанная отладка и необходимость держать блокирующие вызовы вне
планировщика goroutine) либо сервис целиком на C с `nats.c`.

**Полнота SecLang.** Единственный весомый аргумент в пользу libmodsecurity. Если у вас уже работает
ModSecurity v3 с настроенным набором правил и накопленными исключениями, переход на другой движок —
это повторная настройка исключений на реальном трафике, а не смена библиотеки. Точный перечень
расхождений надо сверять с текущей версией Coraza, а не с обзорами: OWASP как раз ведёт согласование
поведения между тремя реализациями SecLang, и перечень меняется.

## Рекомендация

Взять Coraza для референсного инспектора. Причины по убыванию веса: отсутствие катастрофического
бэктрекинга в системе с жёсткими дедлайнами, безопасность памяти при разборе недоверенного ввода,
совпадение с языком остальных референсных сервисов.

Заложить в инспектор возможность второй реализации сразу: отображение сообщения на API движка
одинаково для обоих (см. таблицу в
[modsecurity-inspector.md](modsecurity-inspector.md#отображение-сообщения-на-api-движка)), поэтому
разумно спрятать движок за внутренним интерфейсом из пяти методов по числу фаз. Стоимость этого
решения на старте — один интерфейс, выгода — обратимость выбора и возможность гонять оба движка
рядом.

Если в контуре уже есть работающий ModSecurity v3 с настроенными исключениями, порядок обратный:
первым инспектором делается libmodsecurity, чтобы поведение не поменялось при переезде, а Coraza
выводится рядом в `mode=passive` и сравнивается по аудиту. Перевод делается тогда, когда расхождение
вердиктов объяснено, а не когда оно оказалось малым.

## Что осталось выяснить

- Перечень возможностей SecLang, отсутствующих в текущей версии Coraza, — по её собственному
  документу совместимости, а не по обзорам.
- Собирается ли ваш набор собственных правил под RE2: наличие обратных ссылок и lookaround
  проверяется механически, до всякого выбора.
- Профиль латентности обоих движков на одном и том же наборе правил и одном и том же трафике. Это
  единственный способ узнать цену, и он же попутно проверяет совпадение вердиктов.
- Поведение обоих при теле, помеченном `truncated`, и при неразобранном `Content-Type`: расхождение
  тут напрямую превращается в разную долю ложных срабатываний.
