# auth

Калитка второго фактора на живом контуре. Три сценария, все с хоста.

| Сценарий | О чём |
| --- | --- |
| [`auth.sh`](../../../tests/auth/auth.sh) | Калитка целиком: лестница вердикта, вход, отзыв, подбор |
| [`ldap.sh`](../../../tests/auth/ldap.sh) | Провайдер каталога на живом OpenLDAP: bind, группы, отказы |
| [`list.sh`](../../../tests/auth/list.sh) | Активный список — истина: удаление записи завершает сессию |

```sh
cd deploy
docker compose up -d --wait
sh ../tests/auth/auth.sh
sh ../tests/auth/ldap.sh
sh ../tests/auth/list.sh
```

Модуль — [inspectors/auth](../../inspectors/auth/README.md), сервисы
`inspector-auth`, `auth-http` и `ldap`. Маршруты стенда — `/auth/`,
`/auth-fast/`, `/auth-list/`, `/auth-code/`, `/auth-ldap/`, `/auth-observe/`;
формы — `/waf/login`, `/waf/login-list`, `/waf/code`, `/waf/login-ldap`.

## auth.sh

| Раздел | Утверждение |
| --- | --- |
| Лестница вердикта | Навигационный GET → 303 на форму; POST, XHR и путь `api_paths` → 401; маршрут без инспектора (`= /auth/healthz`) калитку не спрашивает вовсе; в цели редиректа лежит возврат вместе со строкой запроса |
| Вход | Логин, пароль и код TOTP дают сессию; с ней проходят и GET, и POST |
| Заголовки | `X-WAF-User`, `X-WAF-Groups`, `X-WAF-Auth` доходят до приложения, а присланные клиентом `admin` / `root` перезаписаны |
| Одноразовость | Тот же код TOTP вторым билетом не проходит; сожжённый билет формы не проходит |
| Выход | Отзыв гасит уже выданный токен: угнанная cookie получает `AUTH_SESSION_REVOKED` |
| Способ входа | Профиль `list` (`factors: [local]`) не спрашивает код и пускает без него; приложению видно `X-WAF-Auth: pwd` |
| Профили | Форма общего кода не спрашивает логин; токен профиля `code` на чужом маршруте — `AUTH_SESSION_SCOPE`; `observe` пропускает без сессии |
| Подбор | Серия неверных паролей упирается в блокировку |

Решения калитки проверяются по `X-WAF-Debug` там, где код ответа принадлежит
приложению, а не контуру: публичный маршрут отдаёт то, что отдаст апстрим, и
судить по нему о вердикте нельзя — на нём проверяется как раз отсутствие
`auth=` в диагностическом заголовке.

## Почему сценарий устроен именно так

**Вся ходовая часть — один `sh` внутри `nats-box`.** Банка cookie обязана
пережить весь прогон, а каждый `docker compose exec` — новый процесс.

**Код TOTP считает `auth-probe --totp`.** Внутри контура нет ни python, ни
аутентификатора, а вторая реализация HMAC-SHA1 в `busybox sh` рядом с боевой —
это второй источник истины. Сценарий ждёт начала шага, чтобы у входа была
полная минута и чтобы два прогона подряд не спорили за один код: принятый код
гасится, и повторно тот же шаг не пройдёт.

**Подбор — в самом конце.** Блокировка считается по адресу клиента и общая на
весь процесс: после неё с этой машины не пройдёт ни один вход, ни в один
профиль. Точный номер попытки не проверяется — неудачи предыдущих разделов уже
в счётчике.

**Счётчики и билеты чистятся в начале и в конце.** Сценарий намеренно доводит
учётную запись до блокировки, и оставлять её запертой следующему прогону
нельзя.

## ldap.sh

Каталог — контейнер `ldap`, дерево из
[`deploy/ldap/bootstrap`](../../../deploy/ldap/bootstrap). Проверяется вход
`ivanov`, группы в заголовке приложению и четыре отказа: чужая группа, неверный
пароль, пустой пароль (анонимный bind каталог принимает — сервис обязан
отсечь его до похода) и несуществующая запись.

Каждая попытка берёт свежую банку cookie: билет формы одноразовый.

## list.sh

Проверяется то, чего нет в `auth.sh`: маршрут `/auth-fast/` объявляет
`if $cookie_waf_sess not in auth_sessions`, и на запросах вошедшего инспектор
не публикуется вовсе. Видно это по диагностическому заголовку — у пропущенной
калитки нет ни `auth=`, ни `rid`.

Дальше — отмена снаружи: `sid` кладётся в `auth_banned` через API контроллера,
и обе ветки маршрута отвечают 401 с `by=local`, то есть решением локального
слоя без единого сообщения на шину.

Бан снимается двумя способами, и сценарий проверяет оба: удалением записи
оператором (срок первого бана заведомо больше прогона, поэтому проверка
провалится, если снятие не сработало) и истечением собственного срока у
второго.

Наборы создаются в контроллере, если их ещё нет: слот в `nginx.conf` объявляет
только имя, а состав живёт в Postgres.

## Профили стенда и раздел UX

Сценарии работают по профилям из образа (`deploy/auth/profiles`), а не по
поколению из контроллера: край стенда — рукописный `nginx.conf` на `nginx-1..3`,
и его локейшены `/waf/login`, `/waf/code`, `/waf/login-ldap`, `/waf/login-list`
в модели контроллера не описаны.

Поэтому у одноимённых профилей в базе контроллера сервер не проставлен: адрес
формы им выбирать не из чего. Раздел `/auth` их показывает и открывает, но
сохранение потребует выбрать сервер и его локейшен —
[так и задумано](../../inspectors/auth/README.md#сервер-адрес-формы-и-набор--выбором-а-не-набором-текста).
Чтобы править их из UX, локейшены форм надо завести в модели того сервера, чей
конфиг раскатывает контроллер (`edge-managed`).

## Чего здесь нет

- NTLM: для него нужен контроллер домена, а не LDAP-каталог. Разбор ответов
  покрыт модульными тестами, живой bind — задача контура с AD.
- Тихое продление: `renew_after` профиля стенда — час, и ждать его в сценарии
  незачем. Ветка инспектора проверена модульным тестом
  (`internal/decide`), ветка формы — вручную на профиле с коротким сроком.
- Страницы отказа: `/usr/share/waf/pages` в образ стенда не кладут, и 401
  доходит до последнего `try_files`. Проверяется код ответа, не тело.
