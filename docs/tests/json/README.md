# json

Инспектор контракта API на живом контуре: обе фазы, все политики исходов и
усечение тела. Один сценарий, с хоста.

| Сценарий | О чём |
| --- | --- |
| [`json.sh`](../../../tests/json/json.sh) | Контракт целиком: тело, параметры, путь вне спеки, наблюдение, усечение, фаза ответа |

```sh
cd deploy
docker compose up -d --wait
sh ../tests/json/json.sh
```

Модуль — [inspectors/json](https://github.com/exemt/placitum-json/blob/develop/docs/README.md), служба
`inspector-json` (две реплики). Маршруты стенда — `/json/`, `/json/trim`,
`/json-strict/`, `/json-strict/fail`, `/json-observe/`, `/json-soft/`,
`/json-soft/trim`. Контракт — объект содержимого `stand_openapi`
(bootstrap-копия: `inspectors/json/profiles/*/schema-stand`), приложение за
маршрутами — эхо `backend`.

## Что утверждает сценарий

| Раздел | Утверждение |
| --- | --- |
| Тело против схемы | Валидное тело проходит; строка вместо числа, пропущенное `required` и лишнее поле при `additionalProperties: false` — отказ 400 с `JSON_SCHEMA_MISMATCH`; оборванный JSON — `JSON_UNPARSABLE` |
| Параметры | `/orders/{id}` с нечисловым `id` — отказ; `?verbose=maybe` — отказ; `?verbose=true` проходит |
| Путь вне контракта | Профиль `api` пропускает с `JSON_UNKNOWN_OPERATION`, `strict` отказывает тем же кодом: белый список путей — это политика, а не другая проверка |
| Наблюдение | `observe` на заведомо невалидном теле отвечает `allow`, причина остаётся в заголовке и в аудите |
| Усечение | Тело крупнее `waf_body_limit ... trim` приезжает префиксом: `api` отказывает (`JSON_BODY_TRUNCATED`), `soft` пропускает с той же причиной |
| Фаза ответа | Эхо совпадает с объявленным ответом `/orders` — `allow`; `/report` объявлен не тем, что отдаёт приложение — счёт на `api` и отказ 502 на `strict`; код 503 у операции, где объявлен только 200, — `JSON_STATUS_UNDECLARED` |
| Проба | `json-probe` без обменника получает `deny` на профиле `_probe` и `allow` на описанном пути профиля `api` |

## Почему сценарий устроен именно так

**Вердикты читаются из `X-WAF-Debug`, а не только из кода ответа.** Код ответа
на пропускающем маршруте принадлежит приложению: `200` на `/json/nothing-here`
не отличает «инспектор пропустил» от «инспектора на маршруте нет». Диагностика
модуля называет и вердикт, и код причины.

**Записей в заголовке две, и порядок значим.** Фаза ответа печатает свою запись
вторым заголовком, поэтому у сценария два извлекателя: `gate` берёт первую
запись (запрос), `rgate` — последнюю (ответ).

**Полей у записи разное число.** `allow` печатается как `<вердикт>/<мс>`,
`deny` — как `<вердикт>/<код>/<мс>`, `score` — как
`<вердикт>/<счёт>/<взвешенный>/<код>/<мс>`. Общее у всех одно: код стоит перед
полем длительности, и `awk` в сценарии разбирает запись именно так, а не по
номеру поля.

**Усечение проверяется двумя маршрутами, а не одним.** Политика `on_truncated`
— единственное место, где два профиля на одном и том же теле обязаны ответить
по-разному; проверять её одним маршрутом значит проверять половину.

**Профиль `strict` стоит на своём префиксе.** `base_path` профиля обязан
совпасть с префиксом маршрута: срезается он посегментно, поэтому `/json` не
срезается у `/json-strict/...`, и путать эти два маршрута нельзя.

## Что сценарий не проверяет

- Доставку профилей из контроллера: она проверяется отдельно — `send` в разделе
  `/json` панели и `desired applied` в логе инспектора.
- Внешние `$ref` в спецификации: они не разрешаются намеренно, и проверять
  здесь нечего.
- Спеки в JSON (не YAML): разбор один и тот же, разница — в разборщике
  документа, и она закрыта тестами модуля (`go test ./internal/...`).
