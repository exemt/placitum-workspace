# Переход на сборку из репозиториев

План того, что осталось между сегодняшним днём и установкой, которая собирается целиком из
`placitum-*` и проходит тесты. Составлен 12.09.2026 по замерам дерева, а не по памяти: цифры ниже
сняты скриптами в тот же вечер.

Как раскладывали компоненты — [delivery.md](delivery.md); слои и их смысл — [repos.md](repos.md);
адреса и умолчания — [env.md](env.md).

## Где мы

Девятнадцать репозиториев выложены, у каждого `develop`, каждый собирается из чистого клона;
платформа закоммичена (`1254784`). Старых путей модулей `github.com/nginx-waf/…` в дереве не
осталось, все образы стенда названы `placitum/*`.

Этапы 1–3 и 5 сделаны; от этапа 4 остались `queue`, `audit`, `desired`, `config` и `protocol`.
Установка из публичных репозиториев проходит на пре-проде целиком, с дымом (этап 6, шаги 1–5).
Стенд разработки по-прежнему собирает образы из локальных каталогов платформы — это решение,
а не долг.

## Решения до начала работ

Их нужно принять раньше, чем трогать код: от каждого зависит, какая работа вообще нужна.

| Решение | Варианты | Предложение |
| --- | --- | --- |
| **Где правят код** | в платформе (репозитории — зеркала) / в репозиториях компонентов | В платформе до релиза 1.0. Репозитории компонентов остаются производными: README каждого это уже говорит. Иначе правка в репозитории затрётся следующей выкладкой |
| **На чём живёт стенд** | на копиях платформы / на тех же источниках, что установка | Стенд — на копиях (он для разработки и e2e); установка из репозиториев проверяется отдельным стендом на пре-проде (`deploy/preprod/stand.sh` уже есть) |
| **Закрытый контур** | зеркала реестров / `vendor/` и заранее скачанные зависимости | Решить до первой сборки у клиента без сети: сейчас сборке нужны proxy.golang.org, npm, PyPI, download.pytorch.org, HuggingFace, Docker Hub и quay.io |
| **`tools/waf-mcp`** | своя репа / остаётся в платформе | В платформе: инструмент оператора поверх API, в установку не входит |
| **Мусор** | снести / оставить | Снести `backend/` (никто не собирает), `inspectors/challenge` (в каталоге поставки его нет), пустые `inspectors;C`, `logger;C`, `inspectors/auth;C`, `inspectors/captcha;C`, `inspectors/inspectors` |

## Этап 1. Выкладка одной командой

Без этого каждый следующий шаг — ручная процедура из тринадцати пунктов на девятнадцать
репозиториев.

- **`deploy/deliver.mjs` перевести на проверенный способ.** Сейчас он делает `git subtree split`,
  а опубликованные `develop` собраны мимо истории платформы: split даст не-перемотку. Способ,
  который работает, — временный индекс и коммит с родителем «текущая вершина `develop`» (так
  выложены все девятнадцать).
- **`publish <имя>`** должен сам: собрать дерево, проверить `gofmt -l`, секреты, собрать образ,
  вытолкнуть и собрать образ **из свежего клона**. Отдельно — `publish --all` с отчётом.
- **Репозитории на несколько образов** (`agents`, `node`, `auth`, `captcha`) — реестр должен
  знать подкаталоги и Dockerfile каждого образа.
- **Шаг 11 в `delivery.md`** («пока main не закоммичен») переписать под этот способ.

Готово, когда: `node deploy/deliver.mjs publish --all` проходит на чистом дереве и ни один push
не требует force.

## Этап 2. core описывает весь контур

- **`waf.yml`**: subject rewrite `waf.rsp.rewrite` → `waf.req.rewrite` (стенд и модуль используют
  второй — установка подняла бы инспектор на пустом subject).
- **Убрать встроенные умолчания источников** (`${PLC_SRC_X:?задайте в sources.env}`): битое
  `placitum-redis-agent.git` у `redis-internal-agent` появилось ровно потому, что адрес жил в двух
  местах.
- **Дописать сервисы**: `auth` и `auth-http`, `captcha` и `captcha-http`, `cookie`, `vlai` (за
  профилем), `haproxy`. В `sources.env` — строки для них; `cookie` там уже есть, сервиса нет.
- **`bootstrap/secrets.sh`**: ключи подписи `auth.hmac`, `auth-app.hmac`, `captcha.hmac`,
  `cookie.hmac` — без них калитка, капча и `cookie` не стартуют.
- **`LICENSE.md`, `LICENSE.ru.md`, `INSTALL.md`** — core единственный без них.
- **Выкладка**: локальная `deliver/core` (`e255064`) несёт три проверенных на пре-проде исправления
  (MinIO на quay.io, имя проекта, `.gitattributes`), но в сообщении — `Co-Authored-By`. Её
  содержимое уже в рабочем дереве; выкладывать новым коммитом поверх `16cf8bf`, без приписки.
- В `placitum-core` переключить default branch на `develop` и удалить `main`.

Готово, когда: `docker compose -f compose/waf.yml config --services` из свежего клона перечисляет
весь контур, а `install.sh check` проходит.

## Этап 3. Миграции Postgres — сделано 12.09.2026

Накатчик живёт в контроллере (`controller/src/migrate.ts`) и работает при старте; отдельный
запуск `node src/migrate.ts --check` показывает план. Проверен на трёх состояниях базы: пустая,
живая с недостающей миграцией, старше поставки без журнала. `install.sh migrate` запускает его
из образа до старта процессов. Осталось из списка ниже: перевести предполёт e2e на тот же
накатчик и убрать `WAF_PG_INITDB` со стенда — там в initdb едут ещё гео-сид и стендовое дерево.

Исходный разбор, ради истории:

Накатчика не было, но его логика уже была написана: e2e-предполёт `tests/lib/bootstrap.mjs`,
функция `applySchema()`, — журнал `waf_schema_log`, затравка базы, поднятой до поставки 1.0,
через `WAF_SCHEMA_BASE`.

- **Перенести в контроллер** шагом старта: пустая база — `01-baseline.sql` и `02-shipped.sql`;
  непустая — `migrations/1NN_*.sql`, которых нет в журнале.
- **`pg_advisory_lock`** на время прохода — две реплики стартуют одновременно.
- **Читать `CONTROLLER_SCHEMA_DIR`**: переменная уже стоит в образе, но код её не читает.
- **`migrate --check`** — печать того, что бы накатилось, без применения.
- **Не исполнять `.sh`**: предполёт принимает миграции `*.sh` (гео-сид), накатчик контроллера —
  только SQL; каталог гео остаётся операторским шагом.
- **Правило совместимости** — миграция совместима с предыдущим релизом, на время раскатки на
  одной схеме живут две версии кода.
- После — убрать `WAF_PG_INITDB` из `core` и перевести предполёт e2e на тот же накатчик, чтобы
  логика не жила в двух местах.

Требования целиком — `core/migrate/README.md`. Готово, когда: контроллер из репозитория поднимает
пустую базу сам, а на базе с журналом докатывает только новые файлы.

## Этап 5. Образы — сделано 13.09.2026, кроме `vlai` без сети

- `HEALTHCHECK` появился у `node` (жив мастер nginx: `kill -0` по pid-файлу; агент — PID 1),
  `controller` (`/healthz`), трёх агентов (отметка жизни после каждого кадра присутствия —
  порта у агента нет), `action` и `cookie` (проба тем же путём, что запрос модуля: профиль
  `default`, любой вердикт). `logger` по-прежнему без него намеренно.
- Версия видна изнутри: `-ldflags -X main.version/main.revision` во всех Go-образах, строка
  `build` при старте, поля `version`/`revision` в шапке кадра присутствия (`shared v0.4.0`) и в
  модели флота контроллера; контроллер печатает свою в строке `listening`. Панель пока не
  показывает — отдельная мелочь.
- Установщик берёт `PLC_VERSION` из тега core (иначе `dev`) и `PLC_REVISION` из коммита core и
  передаёт в каждую сборку (`x-build` в `waf.yml`).
- `geopb` перегенерирован (4.6): в дескрипторе `placitum-shared/geopb`.

Исходный список, ради истории:

- **`HEALTHCHECK` нет** у `node`, `controller` (проверка есть только в compose стенда),
  `agents-haproxy`, `agents-redis`, `agents-s3`, `action` (нет и пробы), `cookie`. У `logger` его
  нет намеренно: у двух бинарей разные признаки здоровья.
- **Версия не видна изнутри.** Метки OCI есть, но процесс о себе молчит: поле версии в кадре
  присутствия (заодно с 4.2) и строка при старте.
- **Установщик не передаёт `VERSION` и `REVISION`** в сборку — все образы установки получаются
  `dev`/`unknown`. Брать из ветки или тега источника.
- **`vlai`**: сборка тянет PyPI и download.pytorch.org, веса модели качаются при старте в том
  (`HF_HOME`). Для установки без сети — заранее скачанный том или зеркало; вариант под GPU
  (`Dockerfile.cuda`) установщик пока не умеет выбирать.

## Этап 6. Тесты сборки из репозиториев — шаги 1–5 пройдены 13.09.2026 на пре-проде

Прогон на пре-проде (mvm, Ubuntu 24.04, Docker 29, Compose 5): `./stand.sh fresh` — свежий клон
`placitum-core`, сброс, установка из публичных репозиториев, дым. Второй прогон прошёл целиком:
`check`, инфраструктура, схема накатчиком, все образы из git-контекстов, контур поднят, дым
зелёный (`deploy/preprod/smoke.sh`, он же `stand.sh smoke`): панель и база → объявление `ip` на
пространстве → апстрим, сервер, порт узла → путь `/smoke` с `waf on`, прокси на `/healthz`
контроллера под `ip` → «Разослать», и узел отчитался поколением → 200 через узел → `accepted` у
`ip` вырос на все 50 запросов → во флоте ноды, инспекторы, сервисы и хранилища со сборкой. До
этого установку прогоняли на Windows-машине стенда (проект `plctest`).

Что всплыло и починено:

- **Секреты `0600` не читались процессами образов** — видно только на Linux: compose монтирует
  файл секрета с режимом хоста, а образы работают от своих пользователей, и семь сервисов ушли
  в цикл рестартов. Файлы теперь `0644` в каталоге `0700` (core `6ed8ac4`). Docker Desktop права
  монтирования не проверяет.
- **Порты инфраструктуры торчали наружу** с реквизитами из `.env` — теперь не публикуются,
  `PLC_INFRA_PORTS=loopback` по желанию (core `9a031b9`).
- **Поставка не везла порт узла**: сервер без привязки уходил на `:80`, а контейнер пробрасывает
  `8080` — миграция `100_node_port.sql` (controller `bb3a2c1`).
- **Инспектор надо объявить на пространстве**, иначе `undeclared_inspector`, и **включить `waf`**
  на сервере или пути: умолчание `off`, маршрут с инспекторами без него модуль пропускает молча.
  Оба шага описаны в INSTALL.md.
- **Первый дым проверял узел, но не инспектора**: путь с `return 200` отвечает до фазы доступа,
  где работает модуль. Дым переписан на прокси и счётчик инспектора и ждёт, пока узел
  отчитается поколением: до reload запросы обслуживают старые воркеры.
- **Обвязка стенда**: `down` без `sources.env` не разбирал `waf.yml`, `reset` удалял секреты по
  старому списку, `doctor` считал `#develop:redis` веткой. Windows-хост: bake не понимает
  git-адреса контекстов — `COMPOSE_BAKE=false`.

Стендовое в образах `ip` и `action` (набор `e2e_ip_banned`, профили, списки, тестовое гео, профиль
`stand-rewrite`; из-за него `ip` на чистой установке подключал несуществующий набор) 13.09 переехало
в `deploy/ip` и `deploy/action`: в образе осталось только то, что поставка не даёт удалить.

Там же найдено, не чинено: при сборке из git-адреса BuildKit `.dockerignore` не применяет. На
пре-проде `counter` везёт исключённые им `stand`, `ws`, `ws_ladder`, `ws_quota`, `wsload`; у
`rewrite` (`stand`, `stand-observe`, `ws`, `ws_quota`), `json` (`api`, `observe`, `soft`, `strict`,
`ws`) и `captcha` (`form`, `login`, `observe`) профили сверх `default` и `_probe` не исключены вовсе.

Шаг 6 (e2e платформы на поставленном контуре) не начат: прогоны монтируют внутренности
компонентов.

Исходный порядок, ради истории:

Цель всего перехода. Порядок — от дешёвого к полному, каждый шаг ловит свой класс поломок.

1. **`install.sh check` на чистой машине** — Docker, compose, место, источники.
2. **Инфраструктура**: `install.sh infra` — образы реестров (MinIO уже переезжал с Docker Hub),
   имя проекта, потоки.
3. **Каждый компонент из git** по одному: `docker buildx build "<репа>.git#develop[:подкаталог]"` —
   ловит пропавшие файлы, `go.sum`, `go.work`, CRLF.
4. **Полная установка** `install.sh install` из `sources.env` без единого локального пути.
5. **Дым на поставленном контуре**: панель, заведённый маршрут, запрос через узел, запись в
   аудите, вердикт инспектора.
6. **e2e платформы на поставленном контуре** — отдельный вопрос: сейчас e2e завязаны на
   внутренности компонентов (монтирования профилей и конфигов: `captcha` ×6, `ip` ×5,
   `nginx/agent` ×4, `modsec` ×4, `auth` ×4 и так далее). На установке из репозиториев этих
   файлов на диске нет — прогоны надо перевести на профили через API контроллера.

Площадка — пре-прод (`deploy/preprod/stand.sh` уже гоняет установку с нуля).

## Этап 7. Релиз

- Тег `vX.Y.Z` в каждом репозитории, `sources.env` с тегами вместо веток.
- `main` в репозиториях наполняется в момент релиза: `deliver.mjs publish --branch main`.
- CI каждого из девятнадцати проверить зелёным: он запускается на push, но результат никто не
  смотрел.

## Долги, которые можно закрывать параллельно

- **Два справочника директив разошлись**: `docs/directives/list` и `docs/directives/module-copy`,
  у каждого свои страницы и свои правки в общих. Свести чтением, не скриптом.
- **Имена окружения** по плану [env.md](env.md#план-приведения-имён) — компонент приводит имена в
  тот же заход, когда его трогают на этапах 4–5.
- **Ссылки из публичных репозиториев в платформу** — когда платформа станет публичной, одним
  проходом вместо упоминаний.
- **Реквизиты в умолчаниях**: `keeper` (`postgres://waf:waf@…`) и миграции логгера (`waf`/`waf`).

## Порядок

Этапы 1 и 2 — сначала и последовательно: без выкладки одной командой всё остальное дорого, без
полного `core` нечего тестировать. Этапы 3, 4 и 5 не зависят друг от друга — их можно вести
разными сессиями. Этап 6 начинается, как только готовы 1 и 2, и повторяется после каждого из 3–5.
Этап 7 — когда шестой проходит целиком.
