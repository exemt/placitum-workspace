# Протокол вердикта

## Транспорт

Горячий путь работает на core NATS в режиме scatter-gather. Модуль публикует запрос на subject
инспектора, указывая свой инбокс в поле reply-to; инспектор отвечает в этот инбокс. Один subject на
одного инспектора: так состав опрашиваемых в каждом location задаётся точно, а таймауты и метрики
получаются по инспектору естественным образом.

```
publish  waf.req.sqli   reply-to _INBOX.waf.<node>.<pid>.<nonce>.v.<rid>.<inspector>
```

Инспектору достаточно ответить на то, что стоит в reply-to. Разбор адреса — забота модуля: `v`
отделяет ветку вердиктов от служебных веток инбокса, а номер инспектора нужен на случай ответа без
тела (см. [architecture.md](architecture.md#модель-воркеров)).

Формат сообщений — JSON. Он выбран для читаемости и простоты написания инспекторов на любом языке.
Если профилирование покажет, что сериализация заметна, формат заменяется на MessagePack без изменения
структуры полей; версия схемы это отражает.

Аудит идёт отдельным путём в JetStream и к этому протоколу не относится: модуль
отдаёт итог агенту на unix-сокет, агент пишет `kind=request`, инспектор —
`kind=inspector` с тем же `ray`, см. [audit.md](audit.md#писатели).

## Запрос на инспекцию

```json
{
  "v": 2,
  "rid": "3f2a9c1e00000017",
  "ray": "9b1c1f4e-6a2b-4c3d-8e5f-0a1b2c3d4e5f",
  "phase": "request",
  "wave": 1,
  "inspector": "sqli",
  "deadline_ms": 15,
  "audit_subject": "waf.audit.inspector.sqli",
  "node": "edge-07",
  "conn": {
    "client_ip": "203.0.113.42",
    "client_port": 51544,
    "server_ip": "10.0.4.7",
    "server_port": 443,
    "tls": { "version": "TLSv1.3", "sni": "shop.example.com" }
  },
  "http": {
    "method": "POST",
    "scheme": "https",
    "host": "shop.example.com",
    "uri": "/api/orders",
    "args_size": 8,
    "version": "HTTP/2.0"
  },
  "needs": ["headers", "args", "body"],
  "store": {
    "headers": { "store": "hot", "driver": "redis", "key": "w7:3f2a9c1e00000017:req:hdr", "size": 412 },
    "args":    { "store": "hot", "driver": "redis", "key": "w7:3f2a9c1e00000017:req:arg", "size": 8 },
    "body":    { "store": "hot", "driver": "redis", "key": "w7:3f2a9c1e00000017:req",
                 "size": 18342, "sha256": "9f86d081884c7d65...", "complete": true, "truncated": false }
  },
  "route": { "server_name": "shop.example.com", "location": "/api", "profile": "strict" },
  "score": { "total": 45, "deny_at": 100 },
  "prior": [
    { "phase": "request", "wave": 0, "inspector": "ip", "verdict": "allow",
      "actions": [ { "do": "challenge", "apply": "request", "code": "IP_GREYLIST" } ] },
    { "phase": "request", "wave": 0, "inspector": "repu", "verdict": "score",
      "score": 45, "reason": { "code": "REPU_DATACENTER" } }
  ]
}
```

Содержимого запроса в сообщении нет. Заголовки, строка запроса и тело едут локаторами в секции
`store` — той же формы, что в аудите модуля, — потому что длину всех трёх задаёт клиент, а сообщение
публикуется по одному на каждого инспектора волны. Инлайном остаётся только путь: он нужен каждому
для сопоставления правил, а вынос его в обменник сделал бы round-trip обязательным даже для тех, кому
обменник не нужен вовсе.

Поля:

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `v` | да | Версия схемы. Инспектор обязан отвергать незнакомые версии |
| `rid` | да | Идентификатор запроса, уникальный в пределах узла и поколения процесса |
| `ray` | да | UUID v4 запроса. Единственный ключ склейки с аудитом: `rid` адресует слот и переиспользуется |
| `phase` | да | `request`, `response` или `frame`. Направление кадра — в `stream.direction`, а не в фазе. Форма сообщения для кадров описана в [streaming.md](streaming.md#идентификация) |
| `wave` | да | Номер волны, полезен для диагностики |
| `inspector` | да | Имя инспектора, которому адресовано сообщение |
| `deadline_ms` | да | Сколько времени у инспектора осталось. Позволяет ему самому решить, стоит ли начинать дорогую работу |
| `audit_subject` | да | Куда публиковать подробности находок, `kind=inspector`. `null` — деталей не ждут |
| `conn` | да | Параметры соединения, включая данные TLS-рукопожатия |
| `http` | да | Метод, host, uri, версия и `args_size` — длина строки запроса; сама строка в `store.args` |
| `needs` | нет | Объекты `waf_capture` маршрута. Одинаковы у всех инспекторов вызова |
| `store` | да | Три локатора одной формы: `headers`, `args`, `body` — объекты **текущей** фазы. Каждый — размещённый объект, признак недоступности либо `null`. Формат в [body-storage.md](body-storage.md#локатор) |
| `request_store` | нет | Те же три локатора для объектов фазы запроса. Есть на фазах `response` и `frame`, чтобы инспектор восстанавливал контекст запроса, не храня состояния |
| `route` | да | Какой server и location применились, и какой профиль конфигурации назначен маршрутом, см. [«Профиль инспектора по маршруту»](#профиль-инспектора-по-маршруту) |
| `score` | да | Накопленный счёт фазы и порог отказа маршрута, см. [скоринг](#скоринг) |
| `prior` | нет | Что высказали предыдущие: кто, на какой фазе и волне, что решил и о чём просит соседей. Сквозная по фазам — на `response` и `frame` приезжают и записи фазы запроса. Записей пассивных нет ни у кого. Форма, словарь действий и пределы — [inspector-actions.md](inspector-actions.md) |

`null` в `store` означает: объекта нет в `waf_capture` маршрута, либо класть было нечего. Объект,
который лежит только ради archive/preview, инспекторам тоже `null`.

### Профиль инспектора по маршруту

Поле `route.profile` — имя набора правил, который должен применить инспектор на этом маршруте, например
`"default"` или `"strict"`. Оно всегда присутствует; если ни на одном уровне конфигурации (`http`,
`server`, `location`) профиль для этого инспектора не задан явно, модуль подставляет литерал
`"default"`.

Для модуля это непрозрачная строка: он не знает, какие профили существуют внутри инспектора, и не
может проверить это значение при `nginx -t`. Валидация — ответственность инспектора: он решает, что
делать с неизвестным именем профиля (падать в `default` или отдавать `deny`), см.
[directives/list/inspector.md](directives/list/inspector.md) про то, как профиль задаётся (`profile=` в реестре),
и [inspectors.md](inspectors.md) про контракт со стороны инспектора.

Профиль — это *что проверять*, а не *проверять ли*: нет строки `waf_inspect` — инспектор не бежит.

Поле аддитивное и необязательное для старых инспекторов, поэтому его появление не увеличивает `v`.

В секции `score` поле `total` — сумма вкладов инспекторов предыдущих волн после применения весов,
`deny_at` — действующий на этом маршруте порог отказа (`0` означает, что порог выключен).

Инспектору эта пара нужна для двух разных дел. Во-первых, соразмерить собственный ответ: при `total`
95 и `deny_at` 100 даже слабая находка становится решающей, и тратить остаток дедлайна на уточнение
уже незачем. Во-вторых, решить то, чего не решает модуль: сервис челленджа определяет, пора ли
требовать доказательство, что клиент человек, именно по накопленному счёту и по `prior`. Порога
челленджа в сообщении нет, потому что его нет и в модуле — см.
[разрешение конфликтов](#разрешение-конфликтов).

В элементах `prior` поле `score` — то, что легло в сумму: при `verdict: score` это заявка как
прислана, у совещательного (`mode=vote`) с `verdict: deny` — сто. Множителя на вызове нет, поэтому
число одно.

Для фазы ответа добавляется секция `response`, а `store` меняет сторону:

```json
{
  "v": 2,
  "rid": "3f2a9c1e00000017",
  "phase": "response",
  "inspector": "dlp",
  "response": { "status": 200, "upstream_ms": 34 },
  "store": {
    "headers": { "store": "hot", "key": "w7:3f2a9c1e00000017:rsp:hdr", "size": 318 },
    "args": null,
    "body": { "store": "hot", "key": "w7:3f2a9c1e00000017:rsp", "size": 48211, "complete": true }
  },
  "request_store": {
    "headers": { "store": "hot", "key": "w7:3f2a9c1e00000017:req:hdr", "size": 412 },
    "args":    { "store": "hot", "key": "w7:3f2a9c1e00000017:req:arg", "size": 8 },
    "body":    null
  }
}
```

`store` всегда означает объекты текущей фазы — одно правило на все три. Заголовки ответа поэтому
такой же объект обменника, как остальные, а не инлайновый список: инлайн проходит мимо `mask=` и
`deny=` из [waf_capture](directives/list/capture.md), то есть мимо `set-cookie`.

Инлайновый список в секции `response` остался запасным путём: он едет там, где маршрут заголовки
ответа **не снимает**, и `set-cookie` в нём не едет вовсе — применять к нему нечего, а отдавать
сессию в чужой процесс «как есть» дороже любой находки. Появился `waf_capture response headers` —
список переезжает в `store.headers` вместе со своими `mask=` и `deny=`, и инлайна в сообщении уже
нет: два источника одного и того же расходились бы ровно в том, что маршрут просил скрыть.

Секция `http` в фазе ответа сохраняется, а объекты фазы запроса приезжают в `request_store`, чтобы
инспектор восстанавливал контекст запроса, не храня состояние между фазами. Объекты запроса ради
этого не удаляются из обменника до конца фазы ответа. Тело запроса в `request_store` — только если
маршрут его снимал и оно ещё живо; для правил фазы 3–4 движка правил оно, как правило, не нужно.

### Продолжение и липкость

Спрашивает первым модуль. На маршруте с `keep=on` у
[waf_inspect](directives/list/inspect.md) **фазы запроса** сообщение этой фазы несёт признак и ключ:

```json
"resume": { "want": true, "token": "MHDxOEwOEFDoHDwXbXQ0lS" }
```

Это единственное, что инспектор о липкости знает заранее, и знать ему это необходимо: держать
состояние на каждом запросе -- значит платить памятью за маршруты, которым липкость не нужна. Без
`want` инспектор обязан выбросить транзакцию, ответив. Что `keep=on` не останется без потребителя --
что у того же имени на поздней фазе того же маршрута стоит `resume=`, -- гарантирует `nginx -t`:
пара проверяется по эффективным маршрутам в обе стороны.

Инспектор, которому дешевле доиграть уже начатую работу, чем восстанавливать контекст, отвечает
продолжением в вердикте фазы запроса:

```json
{ "verdict": "score", "score": 15,
  "continue": { "subject": "waf.req.modsec.i.7f3a91",
                "token": "MHDxOEwOEFDoHDwXbXQ0lS", "ttl_ms": 30000 } }
```

Модуль запоминает его на время запроса и на следующей фазе публикует в этот subject, вернув ключ и
требование маршрута:

```json
"resume": { "token": "MHDxOEwOEFDoHDwXbXQ0lS", "require": false }
```

Секция едет на **любой** маршрут с `resume=`, в какой бы subject сообщение ни шло -- в личный, пока
продолжение живо, или в групповой, когда его не было, оно истекло или экземпляр исчез. По ключу
инспектор ищет состояние; по `require` решает, что делать, когда его нет: `false` (`resume=prefer`)
-- переиграть фазы по контексту запроса и отметить `resumed=false` в аудите, `true`
(`resume=require`) -- отказать с кодом потери состояния (`MODSEC_RESUME_LOST` у modsec) и записать
ошибку в лог. Без секции вовсе (`resume=off`) инспектор инициализируется заново молча.

**Ключ обязателен, и называет его модуль.** Опереться на `rid` нельзя: он кодирует слот ожидания
модуля, а слот берётся заново на каждую волну -- у двух сообщений одного запроса `rid` разный.
Продолжение без ключа модуль игнорирует: это subject, по которому нечего спрашивать. Заодно ключ
неугадываем, и состояние чужого запроса по нему не забрать.

Subject проверяется при разборе: он обязан лежать внутри пространства имён самого инспектора
(`<его subject>.…`) и годиться в адрес публикации. Иначе скомпрометированный инспектор
перенаправлял бы запросы маршрута к чужому -- то же самое, что отвечать от чужого имени.

Срок `ttl_ms` — обещание экземпляра. После него модуль в личный subject не ходит: состояния там
может уже не быть, а лишний круг по шине стоит дороже переигровки.

### Освобождение

Продолжение чаще не понадобится, чем понадобится: отказал другой инспектор на волне раньше, фаза
ответа обошлась стороной (204, 304, апгрейд, подзапрос), клиент оборвался, апстрим не ответил. Во
всех этих случаях экземпляр держит транзакцию, которую никто не спросит.

Поэтому в конце запроса модуль публикует освобождение — на `<subject инспектора>.release`, в один
конец и без ответа:

```json
{ "v": 2, "rid": "3f2a9c1e00000017", "inspector": "modsec", "phase": "response",
  "release": { "token": "68b353ac-f72c-40a7-861e-390d1da8221e", "reason": "deny" } }
```

`reason` — `deny` (запрос отказан) либо `skip` (фаза не побежала). Он ни на что не влияет и нужен
ровно затем, чтобы в логе инспектора было видно, почему липкость на маршруте не срабатывает.

**Тема общая, а не личная.** Причина в том самом «отказал другой инспектор раньше»: волна замыкается
на его вердикте, ответ нашего инспектора приходит в закрытый слот и отбрасывается вместе с
`continue` — личного адреса модуль в этом случае не знает вовсе. Общая тема доходит до всех
экземпляров; ключ есть только у одного, остальные ничего не находят и ничего не делают.

Отсюда же и то, что **ключ называет модуль**: ключ, существующий только в ответе, нельзя ни
использовать, ни отозвать, если ответ не дошёл. Ключ — `ray`: он один на запрос и переживает фазы, в
отличие от `rid`, который кодирует слот ожидания и берётся заново на каждую волну.

Срок на стороне инспектора при этом остаётся — как `ttl` у объектов обменника при явном удалении:
страховка на случай, когда сообщение не доедет, а не основной механизм.

Инвариант: **липкость — оптимизация, а не канал данных.** Сообщение фазы ответа одинаково с
продолжением и без него, меняется только subject. При `prefer` инспектор, у которого состояния уже
нет, отвечает тем же вердиктом меньшей полноты, а не ошибкой. Отсюда право включать пару
`keep=`/`resume=` позже и выключать в любой момент, а также обязанность модуля отработать откат:
соединение с шиной поднято с `no_responders`, поэтому публикация в subject исчезнувшего экземпляра
возвращает 503 немедленно, и при `prefer` сообщение тут же уходит в групповой subject реестра.

`require` -- сознательный отказ от этого инварианта на одном маршруте: там правила фазы ответа
смотрят на то, чего в переигранной транзакции нет (тело запроса, настоящий входящий счёт), и отказ
честнее проверки, которая молча не сработает. Отказ выносит инспектор, получивший ключ без состояния;
исчезнувший экземпляр (503) по-прежнему решается `waf_exception <фаза> absent`, без отката в группу.

Для gRPC добавляется секция `grpc` с именем метода и разобранным кадрированием, чтобы инспектор не
реализовывал разбор length-prefixed message сам:

```json
"grpc": {
  "method": "/orders.OrderService/Create",
  "codec": "proto",
  "compressed": false,
  "messages": [ { "offset": 5, "size": 118 } ]
}
```

Для инспекции отдельных кадров вместо `rid` и `http` используются `conn_id`, `seq` и `stream`; полная
форма сообщения — в [streaming.md](streaming.md#модель-кадров).

## Ответ инспектора

В ответе только решение. Всё, что вердикт объясняет — текст находки, номер правила, совпавшие поля,
время движка, — уезжает событием `kind=inspector` в `audit_subject`, потому что модуль этого не
применяет, а на горячем пути оно раздувает ответ. Форма события —
[inspector-audit.schema.ts](messages/inspector-audit.schema.ts), склейка с `kind=request` — по `ray`.

Формы реплая по секциям, с примерами от каждого инспектора контура, собраны в
[messages/inspector-module.md](messages/inspector-module.md).

```json
{
  "v": 2,
  "rid": "3f2a9c1e00000017",
  "inspector": "sqli",
  "verdict": "deny",
  "reason": { "code": "SQLI_UNION_SELECT" },
  "response": { "name": "blocked" },
  "headers": { "set": { "X-WAF-Rule": "942100" }, "unset": ["X-Debug-Trace"] }
}
```

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `v` | да | Версия схемы, должна совпадать с запросом |
| `rid` | да | Эхо идентификатора. Несовпадение — ответ отбрасывается |
| `inspector` | да | Имя себя. Должно входить в ожидаемый набор волны, иначе ответ отбрасывается |
| `verdict` | да | `allow`, `score`, `redirect`, `deny` или `error` |
| `reason` | при `deny`, `redirect` и ненулевом `score` | Машинный `code` — в диагностический заголовок и в выбор записи каталога отказов; клиенту он не попадает. Плюс публичная тройка `scope` / `subject` / `retry`, которую печатает клиенту страница отказа, см. [публичная сторона причины](#публичная-сторона-причины) |
| `score` | при `verdict: "score"` | Целое от 0 до 100 — уверенность инспектора в злонамеренности запроса. При других вердиктах игнорируется |
| `response` | нет | При `verdict: "deny"` — символьное имя записи каталога `waf_deny_response`. При других вердиктах игнорируется |
| `redirect` | при `verdict: "redirect"` | Цель редиректа: `url` и необязательный `status`. URL сверяется с `waf_redirect_allow` маршрута |
| `headers` | нет | Переопределение заголовков: `set` и `unset`. На фазе запроса — заголовки запроса перед проксированием; на фазе ответа правит заголовки ответа до отдачи клиенту |
| `args` | нет | Правка строки запроса по именам, зеркало `headers`: `set` меняет значение имени или дописывает пару, `unset` снимает все пары имени. Только фаза запроса при `allow` и `waf_send request args=store`; байты в проводном виде, модуль не декодирует, см. [секция args](#секция-args) |
| `rewrite` | нет | Объект обменника получателю: на фазе ответа — подмена тела ответа, на фазе кадров — нагрузки кадра, на фазе запроса при `allow` — подмена тела запроса апстриму (`waf_send request body=store`), при `deny` — тело собственного отказа (форма входа, виджет капчи). Каждая принятая секция становится актуальной версией для следующей волны, см. [секция rewrite](#секция-rewrite) |
| `cookies` | нет | Список cookie для установки; пустое `value` с `max_age: 0` — снятие, см. ниже |
| `sessions` | нет | Чьи сессии инспектор увидел на запросе: источник, вид, логин, идентификатор. От вердикта не зависит, модуль ничего из этого не применяет — секция едет в запись аудита, см. [секция sessions](#секция-sessions) |
| `continue` | нет | Продолжение: личный `subject` экземпляра, `token` (ключ состояния) и `ttl_ms`. Модуль использует его на следующей фазе только при `resume=prefer\|require`, см. [продолжение и липкость](#продолжение-и-липкость) |
| `actions` | нет | О чём просить других инспекторов: `do`, адресат `to`, повод `code` и параметры. От вердикта не зависит — действия прикладываются и к `allow`, и это основной случай. Модуль их переносит и ограничивает, но не исполняет — кроме тех, чей адресат он сам: режим вызова соседа, журнал и архив маршрута и маркер записи (`do: "mark"`, строка `marker`), см. [inspector-actions.md](inspector-actions.md) |
| `cache` | нет | `false` — вердикт зависит не только от содержимого (корзины, сессия, время), и повторять его по хешу кадра нельзя: `waf_frame_cache` такой кадр не запоминает. `true` и отсутствие поля равнозначны. Читается только на фазе кадров; counter на кадрах шлёт `false` всегда, см. [frame.md](directives/list/frame.md#waf_frame_cache) |

### Публичная сторона причины

`reason.code` клиенту не показывается: он для оператора и для лога. Но объяснить отказ клиенту
чем-то надо, иначе страница остаётся с одной фразой «запрос отклонён» на все случаи, а звонок в
поддержку начинается с выяснения, что вообще произошло.

Поэтому у `reason` есть вторая половина — три поля, которые уезжают на страницу отказа как
переменные модуля (`$waf_deny_scope`, `$waf_deny_subject`, `$waf_deny_retry`, см.
[deny-pages.md](deny-pages.md)).

| Поле | Тип | Описание |
| --- | --- | --- |
| `scope` | строка из словаря | Что закрыто: `address`, `network`, `country`, `asn`, `session`, `request` |
| `subject` | строка | Чем это названо: `203.0.113.7`, `203.0.113.0/24`, `RU`, `AS64496` |
| `retry` | целое, секунды | Через сколько повторять. `0` и отсутствие — срока никто не назвал |

```json
{
  "v": 2,
  "rid": "3f2a9c1e00000017",
  "inspector": "ip",
  "verdict": "deny",
  "reason": { "code": "IP_LIST", "scope": "network", "subject": "203.0.113.0/24" },
  "response": { "name": "blocked" }
}
```

Читатель у этих трёх полей другой, чем у кода: код читает оператор в логе, эти — посторонний
человек в браузере. Отсюда проверки строже, чем у остального ответа, и все они молчаливые:
непрошедшее поле отбрасывается, а вердикт остаётся в силе — инспектор, ошибшийся в объяснении, не
должен отменять само решение.

- `scope` вне словаря — поле пусто. Ветки страницы написаны под словарь, и седьмое слово дало бы
  пустой абзац вместо объяснения.
- `subject` длиннее 64 байт или с символами вне `[A-Za-z0-9.:/_-]` — поле пусто. Строка уезжает в
  HTML, и полагаться на одно экранирование SSI здесь незачем.
- `retry` вне `1..2592000` (30 суток) — поле пусто. «Повторите через 4 года» — это «никогда»,
  сказанное семью цифрами.
- `scope` из `address` / `network` / `asn` без `subject` модуль не печатает вовсе: у SSI нет
  вложенных условий, и ветка «закрыта сеть» без сети дала бы клиенту «Закрыта сеть .».

Заполняет тройку тот, кто вынес отказ. Локальный слой заполняет из неё только `retry`, и только у
`waf_local_rate` с `list=`: это единственный срок, который он знает точно. Порог счёта не
заполняет ничего — сумма набрана несколькими инспекторами, и назвать одного виновника нечем.

### Секция rewrite

Объект обменника вместо того, что отдал бы модуль. Байты не едут в реплае никогда: инспектор кладёт
объект в обменник и присылает адрес. Принимает ли маршрут подмену и откуда отдаёт объект, решает
`waf_send` ([send.md](directives/list/send.md)): `store` — версия инспектора, `original` — как
пришёл, секция тогда не применяется и уезжает в запись с `applied:false`. Четыре точки применения:

- **фаза ответа, подмена тела.** Модуль в режиме `gate` держит и заголовки, и тело до вердикта,
  поэтому на разрешённом ответе он поднимает объект из обменника, подменяет им удержанную цепочку,
  переписывает `Content-Length` и только после этого отпускает ответ клиенту. Ключ — `<node>:<rid>:rsp:<суффикс>`;
- **фаза запроса при `allow`, подмена тела апстриму.** `rewrite.body` заменяет цепочку тела
  запроса и `Content-Length` перед прокси. Строка запроса объектом не ходит: её правит по именам
  секция `args` реплая ([секция args](#секция-args)). Ключ — `<node>:<rid>:req:<суффикс>`;
- **фаза запроса при `deny`, тело собственного отказа.** Инспектор положил страницу (форму входа,
  виджет капчи) и отвечает `deny` с секцией: модуль отдаёт объект телом ответа с кодом записи
  `response`, типом из `content_type` и `Cache-Control: no-store`, до апстрима не доходя. Так
  форма приходит на том же URI, без редиректа, без записи каталога и без прокси-локации. Не
  поднялся — обычный отказ страницей записи, со строкой WARN. Ключ — `<node>:<rid>:req:<суффикс>`;
  `waf_send` этой точки не касается — это ответ вместо запроса, а не отдача запроса;
- **фаза кадров, подмена полезной нагрузки.** Модуль держит кадр до вердикта, поднимает объект и
  собирает кадр заново с тем же опкодом и fin (у кадров клиента — с маской оригинала); подмена
  одна на кадр, кадр за кадром — без сборки фрагментов. Сорванный подъём закрывает соединение,
  когда `waf_exception <направление> body` стоит `deny` (`type=websocket`, иначе 1008 с
  кодом `REWRITE_FAILED`). Ключ —
  `<node>:<rid>:frm:<суффикс>`; секция `headers` на кадре не применяется.

**Право на подмену есть у любой декларации.** Флаг `mutate=on` в реестре снят: право выражается не
строкой конфигурации, а тем, что инспектор опубликовал новую ссылку. Кто может писать в обменник
объекты этого запроса, тот может и предложить свою версию.

**Актуальная версия и цепочка.** Приняв секцию, модуль переставляет локатор фазы на новый объект:
следующая волна получает в сообщении уже его, строит от него свой ключ и правит поверх правки.
Подмены складываются конвейером, а не спорят за один объект, и получателю уходит последняя
актуальная версия.

**Две подмены на одной волне — сбой.** Конвейера внутри волны нет: её инспекторы видели один и тот
же объект и правили его параллельно, поэтому «последняя» означала бы «молча потерянная чужая», а
«первая по объявлению» — тихо выбранную половину работы. Собрать версию модуль не может, и это
[исключение класса `body`](directives/list/deadline.md#waf_exception) фазы: `pass` — получателю
уходит объект, актуальный на начало волны (цепочка на ней и кончается), `deny` — отказ с записью
`response=`. В журнале — WARN с именами обеих деклараций, в записи — `applied:false` у обеих.
Тем же классом разрешается упёршаяся глубина цепочки: ключ версии — производная от предыдущего, и
после `NGX_HTTP_WAF_REWRITE_MAX_DEPTH` звеньев длина ключа росла бы волна за волной.

**Оригинал остаётся.** Локатор оригинала модуль держит отдельно от актуального: аудит и архив
показывают то, что пришло, а не то, что собрали инспекторы. Промежуточные версии удаляет модуль
при разрешении вердикта, вместе со своими объектами; отданная версия удаляется сразу после подъёма.

**Неполный снимок объект не поднимает.** Локатор помечен `truncated` — инспектор видел префикс, и
заменить целое куском значит сломать нагрузку. Опции «отдать кусок» нет: это сбой подъёма, как
пропавший ключ, исход решает `waf_exception <фаза> body` (отказ `REWRITE_FAILED` при `deny`,
оригинал при `pass`), в записи `applied:false, partial:true`, в логе WARN. Инспектору выгодно смотреть на `truncated` и
не класть объект зря — `rewrite` так и делает.

Пример подмены на фазе ответа:

```json
{
  "v": 2,
  "rid": "3f2a9c1e00000017",
  "inspector": "rewrite",
  "verdict": "allow",
  "headers": { "set": { "X-Frame-Options": "DENY" }, "unset": ["Server"] },
  "rewrite": {
    "body": { "key": "edge-01:3f2a9c1e00000017:rsp:out", "size": 12345, "sha256": "…" },
    "groups": ["mask_pii"]
  }
}
```

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `body.key` | с секцией `body` | Ключ объекта в обменнике: `<ключ тела фазы>:<суффикс>` — производная от локатора, который инспектор получил в сообщении (`<node>:<rid>:req` на фазе запроса, `<node>:<rid>:rsp` на фазе ответа, `<node>:<rid>:frm` на кадре), либо `<node>:<rid текущего слота>:<фаза>:<суффикс>` там, где тела не было (`req` у тела отказа). Иначе реплай не может адресовать чужой объект. На волне после принятой подмены полученный локатор — уже её объект, и ключ следующей версии наращивается на нём: `…:rsp:out:mask`. Суффикс — короткий токен `[a-z0-9_-]{1,32}`, по соглашению `out` у подмены и `form` у тела отказа |
| `body.size` | с секцией `body` | Точный размер объекта в байтах. Расхождение с прочитанным — отказ подмены |
| `body.sha256` | нет | Хеш содержимого hex-строкой; при наличии сверяется после чтения |
| `content_type` | нет | Тип содержимого для тела отказа фазы запроса, одна строка заголовка до 128 байт; умолчание `text/html; charset=utf-8`. На фазе ответа не читается — там тип правит секция `headers` |
| `groups` | нет | Имена применённых групп модификаторов, до 16, алфавит имён профилей. Информационные: модуль их не толкует, они уезжают в аудит и лог |

Секция валидна или нет целиком, как `headers`: битая форма отбраковывает весь ответ. Секция `body`
без `key` или без `size` — битый ответ. Подмена одна на волну: две секции на одной волне — сбой
класса `body`, см. выше.

Заголовки ответа при этом правит обычная секция `headers` того же реплая, с асимметрией по
направлению: `set Content-Type` разрешён и идёт в отдельное поле структуры (страница челленджа
вместо JSON — это ещё и `text/html` вместо `application/json`), `set Set-Cookie` запрещён (cookie
ходят своим каналом с форсированными атрибутами), а `unset Set-Cookie` разрешён — подменённая
страница не должна уносить клиенту сессию приложения, выданную непроверенному. `Location` и `Date`
закрыты в обе стороны, `Content-Length` чинит сам модуль.

Подмена возможна только когда снят весь объект (`waf_capture … body` без предела либо ответ в
пределах среза) и ответ не сжат апстримом; ответ, отпущенный переполнением `waf_body_limit`, не
подменяется — это тот же документированный fail-open. Неполный снимок и сжатие — сбои, ими
распоряжается `waf_exception <фаза> body`: своего распоряжения в реплае нет, потому что
несостоявшаяся подмена — ошибка обработки запроса, и решать её должна одна политика на все такие
ошибки, а не третий рычаг рядом с двумя существующими. Пассивный режим инспектора подмену не
применяет, как и остальные переопределения.

Аудит и архив хранят оригинал: снятое уехало в обменник до подмены. Расхождение помечено в записи
аудита секцией `rewrite` у автора подмены — `{"applied": true, "size": …, "groups": […]}`.

### Секция args

Правка строки запроса по именам поверх оригинала, зеркало `headers`: `set` меняет значение первой
пары с этим именем на месте и снимает её дубли, отсутствующее имя дописывает в конец; `unset`
снимает все пары имени. Сначала `unset`, потом `set`; реплаи ложатся в порядке объявления
деклараций, поздний `set` того же имени побеждает. Байты едут в проводном виде: модуль ничего не
декодирует, режет по `&` и сравнивает имена побайтно до `=`, поэтому `&` в имени или значении,
`=` в имени, пробел и управляющие символы — битая форма, и весь ответ отбраковывается. Кодирование —
дело инспектора.

```json
{
  "v": 2,
  "rid": "3f2a9c1e00000017",
  "inspector": "cleaner",
  "verdict": "allow",
  "args": { "set": { "page": "1" }, "unset": ["debug", "token"] }
}
```

Только фаза запроса при `allow` (на ответе и кадрах секция принимается и выбрасывается со строкой
INFO «not supported»: к ответу строка уже ушла апстриму, у кадра её нет). Принимает ли маршрут правку,
решает `waf_send request args=original|store` ([send.md](directives/list/send.md)), умолчание
`store`; при `original` секция пропускается со строкой INFO. Маски и срез снимка правке не мешают:
замаскированное имя можно снять или заменить, инспектор не видел значения, но имя знает. Через
обменник строка не ходит, правила неполного снимка у неё нет. Итог длиннее
`large_client_header_buffers` сервера (того, что nginx сам принял бы от клиента строкой запроса) —
сбой правки: оригинал остаётся, WARN в лог; тот же предел режет каждое значение `set` в кодеке. В записи у автора — `rewrite.args{applied,set,unset}`;
`applied:false` — маршрут правку не принял, исход не `allow` или строка не собралась.

### Секция sessions

Чьи сессии инспектор увидел на запросе. Это не решение и не переопределение: модуль ничего из
секции не применяет, а делает с ней две вещи. Переносит в запись аудита (`sessions[]` у
`kind=request`, [agent.schema.ts](messages/agent.schema.ts)), дописав к каждой записи имя
отправителя (`by`) и метку пассивности, — так журнал отвечает на вопрос «кто это был» независимо
от того, чья калитка стоит на маршруте: своя, разбор чужого токена или подсмотренная сессия
приложения. И возвращает соседям следующих волн и фаз секцией `sessions` сообщения
([модуль → инспектор](messages/module-inspectors.md#личности-секция-sessions)) — тем, кто ключует
свой счёт личностью, а не тем, что прислал клиент. Соседям, в отличие от аудита, пассивные записи
не едут.

```json
{
  "v": 2,
  "rid": "3f2a9c1e00000017",
  "inspector": "auth",
  "verdict": "allow",
  "headers": { "set": { "X-WAF-User": "alice" } },
  "sessions": [
    { "source": "corp", "kind": "own", "user": "alice", "id": "k7f3…",
      "verified": true, "issued": 1757232000, "expires": 1757260800, "groups": ["ops"] },
    { "source": "shop", "kind": "app", "user": "alice@example.com", "id": "sha256:ab12…",
      "verified": true }
  ]
}
```

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `source` | да | Имя источника у отправителя, до 64 байт: у калитки — источник входа |
| `kind` | да | Вид сессии, до 16 байт: `own` — выписал контур, `jwt` — чужой токен, `app` — кука приложения |
| `user` | нет | Логин, до 256 байт; пусто — сессия есть, а кто это, отправитель не знает |
| `id` | нет | Идентификатор сессии, до 128 байт. **Не сама кука**: у своей сессии — `sid`, у чужой — хеш. Сырой секрет сюда не кладут, запись живёт дольше запроса |
| `verified` | нет | Подпись сошлась. `false` у разбора без ключа: claims в такой записи написал клиент |
| `issued`, `expires` | нет | Unix-секунды выдачи и срока |
| `groups` | нет | Имена групп; в записи печатаются одной строкой через запятую, до 256 байт |

Массив живёт на запросе: записи разных инспекторов (две калитки на двух волнах) складываются,
повтор от того же отправителя с теми же `source` и `id` заменяет прежнюю запись, а не дублирует
её. Пределы формы: до четырёх записей в реплае и до восьми на запрос; строка длиннее своего
предела или с управляющим символом, пятая запись — порча реплая, он отбрасывается целиком.
Запись без `source` или `kind` пропускается со строкой WARN, как cookie без имени.

Пассивный отправитель в `sessions` попадает — с `passive: true`: заголовки личности приложению не
легли, но это единственное место, где видно, кого назвала бы калитка, будь она боевой. Кадры
WebSocket секцию не печатают: они лежат под `ray` рукопожатия, и сессии читаются из его записи.

### Вердикт error

Инспектор не смог проверить: перегружена очередь, вышел его бюджет, не знает профиля, разъехался с
версией схемы, не поднялся движок правил, не ответил обменник или Redis корзин, не прогрето зеркало
списка сессий, не разобрался адрес клиента. Это не вердикт, а признанное его отсутствие — то же, что
молчание, но названное вслух и сразу.

Правило одно: **всё, что мешает инспектору проверить, — `error`**. Если исход зависит от того, что
важнее на этом маршруте — пропустить непроверенное или закрыть за свою поломку, — выбор делает не
инспектор. Отсюда же и то, чего у инспекторов больше нет: ни отката на профиль `default` вместо
названного маршрутом, ни настроек процесса вроде `unknown_profile_policy`, ни тихого счёта в
собственной памяти при недоступном общем.

```json
{
  "v": 2, "rid": "3f2a9c1e00000017", "inspector": "modsec",
  "verdict": "error",
  "reason": { "code": "MODSEC_QUEUE_LIMIT" }
}
```

`reason.code` обязателен: без него событие неотличимо от молчания в журнале, а разбирают такие
случаи именно по коду.

`reason.class` необязателен, и слово в нём одно — `"overload"`. Им инспектор отделяет **сброс на
входе** (очередь полна либо бюджет протух до начала работы) от всего остального: сам он цел, через
минуту тот же запрос прошёл бы, и оператор вправе судить это иначе, чем поломку. Модуль выбирает по
классу директиву: `overload` — `waf_exception <фаза> overload`, всё прочее (и ответ без `class`) —
`waf_exception <фаза> inspector`. Незнакомое слово в `class` ответ не роняет: класс выбирает
политику, а не вердикт, и разъехавшаяся версия инспектора не должна ронять волну.

```json
{
  "v": 2, "rid": "3f2a9c1e00000018", "inspector": "modsec",
  "verdict": "error",
  "reason": { "code": "MODSEC_QUEUE_LIMIT", "class": "overload" }
}
```

Что происходит дальше:

- **обязательный инспектор срывает волну** с кодом `fail_inspector` — либо `fail_overload`, если
  ответ назвал класс `overload`, — и исход выбирает `waf_exception <фаза> inspector|overload
  pass|deny [response=]` маршрута ([deadline.md](directives/list/deadline.md)); дедлайна волна при
  этом не ждёт — ответ уже получен;
- **пассивный и совещательный не срывают ничего**: они не гейтят, и их поломка не должна ни
  блокировать запрос, ни занижать счёт. В журнале событие остаётся;
- **предохранитель считает `error` отказом** ([execution-model.md](execution-model.md#circuit-breaker)).
  Иначе появился бы способ быть сломанным и здоровым одновременно: отвечай `error` — и breaker
  никогда не откроется;
- **всё остальное в ответе выбрасывается**: счёт, `headers`, `args`, `rewrite`, `cookies`,
  `continue` и просьбы соседям. Инспектор, не выполнивший работу, не вправе и просить о чужой.
  Секция `sessions` остаётся: она ничего не применяет, а «кого видели» — правда и при сбое;
- **глаголы, которые исполняет модуль, остаются** — кроме `score`: вклада в сумму у ответа без
  вердикта нет. «Не вправе просить о чужой работе» — это про соседа, а о себе модулю сказать
  можно, и на сбросе по перегрузке инспектор этим пользуется: пометить запись
  ([`mark`](inspector-actions.md#маркеры)) или не звать себя до конца транзакции
  ([`off`](inspector-actions.md#управляющие-глаголы)). Без этой щели просьба с пути сброса не
  доехала бы никогда.

До `error` инспектору приходилось врать: `allow` означал «проверил, чисто» — и непроверенный запрос
уходил дальше неотличимым от проверенного; `deny` блокировал трафик за собственную поломку. Выбор
между этими двумя половинами был зашит в каждый инспектор по-своему и мимо маршрута.

Недоступность объекта, о которой сказал модуль (причина приехала в локаторе), — решение маршрута:
класс `body` у `waf_exception` уже сработал, и раз сообщение всё-таки дошло, оно было «продолжать».
Такую недоступность инспектор разбирает своей политикой — и политика «без объекта целиком проверки
нет» тоже честная: modsec отвечает `error` и на неё, и на префикс тела (`truncated: true`), потому что
движок на части объекта не проверяет, а лишь делает вид ([inspectors.md](inspectors.md#получение-тела)).
Вердиктом `error` **не** является `allow` там, где инспектору просто нечего делать: профиль выключен,
фаза выключена, просьба соседа сняла проверку, адрес запроса — его собственный.

### Вердикт allow

Инспектор ничего не нашёл. Запрос продолжает путь, вклад в счёт нулевой. Переопределения заголовков
применяются к запросу перед проксированием (фаза запроса), а на фазе ответа — к заголовкам ответа
перед отдачей. Секция `cookies` применяется здесь так же, как на отказе и редиректе: пропуск — это
основной исход у того, кто ставит куку, а не исключение из правил.

### Вердикт score

Инспектор нашёл что-то подозрительное, но не берёт на себя решение. Он сообщает уверенность числом от
0 до 100, а блокировать или нет — решает модуль, сложив вклады всех инспекторов и сравнив сумму с
порогом маршрута.

```json
{
  "v": 2, "rid": "3f2a9c1e00000017", "inspector": "sqli",
  "verdict": "score",
  "score": 90,
  "reason": { "code": "SQLI_TAUTOLOGY" }
}
```

Это основная форма ответа для сигнатурных и эвристических инспекторов. Одиночная находка редко
означает атаку: `' or 1=1` в поле поиска и `' or 1=1` в поле идентификатора — разные события, и
инспектор, видящий только свою часть картины, не должен выбирать между ложной блокировкой и
пропуском. Вердикт `score` снимает с него этот выбор: он отвечает за качество своей оценки, а
политику задаёт конфигурация nginx, где её видно целиком и где её можно менять без выкатки
инспекторов.

`deny` остаётся для случаев, где решение не зависит ни от чего внешнего: найден вирус, адрес в
списке блокировки, подпись не сошлась. Такой вердикт безоговорочен и пороги не смотрит вовсе.

Значение `score: 0` допустимо и равносильно `allow`; смысл его в том, чтобы отличить «проверил, чисто»
от «проверил, нашёл на ноль баллов» в аудите.

### Вердикт deny

Безоговорочная блокировка. Пороги счёта не проверяются, накопленная сумма роли не играет.
Формируется ответ отказа: код и страница берутся из каталога по имени в поле `response`; если поле
не задано, используется `waf_deny_response_default`.

```nginx
waf_deny_response blocked  status=403 page=@waf_blocked;
waf_deny_response av_found status=403 page=@waf_av;
waf_deny_response leak     status=502 page=@waf_leak;
```

Инспектор присылает только имя. Пути, URL и готовый HTML с провода не принимаются никогда, см.
[ограничения канала](#ограничения-канала). Единственное исключение — тело из обменника: инспектор
может приложить к `deny` [секцию rewrite](#секция-rewrite), и тогда модуль отдаёт объект
обменника телом ответа с кодом записи `response` (так калитка и капча показывают форму на том же URI).

Форма отказа зависит от протокола: HTML-страница с кодом 403 подходит для обычного HTTP, но для gRPC и
WebSocket она неотличима от сетевой ошибки. Поэтому запись каталога имеет тип:

```nginx
waf_deny_response grpc_denied type=grpc      status=7    "message=blocked by policy";
waf_deny_response ws_policy   type=websocket code=1008   "reason=policy violation";
```

Модуль выбирает запись подходящего типа по протоколу маршрута. Если инспектор прислал имя записи
неподходящего типа, применяется запись по умолчанию для этого протокола, а расхождение попадает в аудит.
Полная таблица форм отказа — в [streaming.md](streaming.md#формы-отказа-по-протоколам).

### Вердикт redirect

Клиент перенаправляется на присланный адрес, с необязательной установкой cookie. Основной сценарий —
челлендж: инспектор, который его ведёт, решил, что пора требовать доказательство, что клиент человек.

```json
{
  "v": 2, "rid": "3f2a9c1e00000017", "inspector": "challenge",
  "verdict": "redirect",
  "reason": { "code": "CHALLENGE_REQUIRED" },
  "redirect": { "url": "/waf/captcha?rd=%2Fapi%2Forders", "status": 303 },
  "cookies": [
    { "name": "waf_chal", "value": "eyJ0IjoxNzU1...",
      "path": "/", "max_age": 300 }
  ]
}
```

Здесь единственное место, где с провода принимается не имя, а адрес, и асимметрия с `deny`
намеренная. Ответ отказа отдаёт сам nginx, поэтому его форма обязана быть объявлена конфигурацией.
Цель редиректа — чужой адрес, и знать про жизненный цикл челленджа может только тот, кто его ведёт:
какой домен обслуживает проверку сейчас, что положить в параметр возврата, какую попытку клиент уже
исчерпал. Модуль вместо этого проверяет присланное по `waf_redirect_allow` маршрута.

Правила:

- Допустимые коды: `302`, `303`, `307`. По умолчанию `303`. Для не-идемпотентных методов `303` явно
  предписывает браузеру перейти на GET, тогда как трактовка `302` исторически неоднородна.
- Тело исходного POST при редиректе теряется безвозвратно, и это принятое ограничение продукта.
  Практически оно почти не проявляется: сервис челленджа опрашивается на каждом запросе, поэтому
  clearance обычно выдаётся на навигационном GET до отправки формы.
- Адрес обязателен и проверяется до применения, см.
  [ограничения канала](#ограничения-канала). Параметр возврата собирает инспектор: модуль к
  присланному адресу не дописывает ничего.
- Вердикт `redirect` запрещён в фазе ответа и в модели кадров.
- Модуль не выводит редирект ни из чего сам, поэтому и цикл редиректов разрывать ему нечем: это
  забота сервиса, см. [ниже](#челлендж-и-цикл-редиректов).

## Скоринг

### Накопление

Вклады инспекторов складываются в счёт фазы как присланы:

```
total = Σ  score(i)
        i
```

Суммирование идёт по обязательным инспекторам фазы, ответившим `score`, и по совещательным
(`mode=vote` на `waf_inspect`): у них в сумму идёт и `score`, и `deny` — как сто очков. Вердикты
`allow` дают ноль. Пассивные (`mode=passive`) в сумму не входят — их вклад пишется в теневую сумму
и в аудит, чтобы видеть, каким был бы счёт, не влияя на трафик.

Счёт накапливается в пределах одной фазы. У фазы запроса и фазы ответа отдельные суммы и отдельные
пороги: они измеряют разное, и складывать «подозрительность запроса» с «подозрительностью ответа»
означало бы блокировать ответ за грехи запроса, который уже пропущен.

**Веса нет.** Множитель `weight=` на вызове снят: число в аудите переставало совпадать с числом на
проводе, а объяснить итог без `nginx.conf` было нельзя. Шкалу 0–100 каждый инспектор держит сам, и
приводить её к общей — дело его профиля (у `modsec`, `json`, `vlai` и счётчика для этого есть `on:
score` и коэффициент `threshold` от соседей), а не строки маршрута.

Ответ на вопрос «может ли один инспектор заблокировать в одиночку» даёт порог и режим вызова:

```nginx
waf_score_deny request 200;
waf_inspect request sqli   wave=1 timeout=15ms   mode=vote;
waf_inspect request modsec wave=1 timeout=1000ms mode=vote;
waf_inspect request ml     wave=1 timeout=15ms   mode=passive;
```

Совещательный (`mode=vote`) не решает сам: его `deny` — сто очков, `score` — как прислан. При
пороге 200 отказ требует двух голосов; при пороге 100 один голос равносилен `deny`, и это осознанный
выбор оператора, а не умолчание.

### Порог

Порог задаётся на маршруте и наследуется вниз по контекстам.

```nginx
waf_score_deny 100;   # блокировать при сумме >= 100
```

Сравнение нестрогое: `total >= порог`. Значение `0` выключает порог. Выключенный `waf_score_deny`
означает, что вердикты `score` собираются в аудит, но никогда ни на что не влияют, — это рабочий
режим наблюдения, в котором порог подбирается по реальным данным до того, как он начнёт блокировать.

Порог один, и он единственное, что модуль выводит из счёта. Промежуточной ступени «похоже на бота,
но не доказано» в модуле нет, хотя сама градация никуда не делась: счёт едет инспекторам в секции
`score`, и сервис челленджа читает его ровно для того, чтобы на сумму 60 ответить требованием
доказать, что клиент человек.

Разница не в поведении контура, а в том, кто принимает решение. Порог челленджа в модуле означал бы,
что nginx назначает проверку, ничего не зная ни о том, есть ли на шине сервис, который её проведёт,
ни о том, сколько попыток клиент уже потратил, ни о том, работает ли она вообще для этого клиента.
Всё это знает сервис, поэтому решение принадлежит ему, а модуль остаётся тем, кто считает сумму,
отказывает по порогу и разрешает редирект только туда, куда разрешает `waf_redirect_allow`.

### Ограничения на значение

**Диапазон 0–100, целое.** Дробное, отрицательное или выходящее за границу значение — ответ
отбраковывается целиком со счётчиком `waf_inspector_invalid_total{reason="score_range"}`, а не
подрезается до допустимого: подрезка превращает ошибку инспектора в тихо неверное решение.

**Отрицательный вклад не поддерживается сознательно.** Возможность понизить счёт выглядит удобной —
репутационный сервис сказал бы «клиент известен и хорош», — но означает, что один скомпрометированный
или забагованный инспектор обнуляет находки всех остальных. Задача «пропустить известного клиента»
решается локальным белым списком (`waf_local_check ... action=allow`), где решение принимает
конфигурация, а не сообщение с провода.

**Неотрицательность даёт монотонность.** Счёт может только расти, поэтому пересечение порога
необратимо: ответ, пришедший позже, не может отменить уже принятое решение о блокировке. Из этого
следует, что раннее прекращение фазы по достижении порога не меняет итог, — свойство, на котором
держится короткое замыкание, см.
[execution-model.md](execution-model.md#короткое-замыкание-и-режимы-отказа).

## Разрешение конфликтов

Всё, что зависит от порядка прихода ответов, — это гонка. Резолюция детерминирована по конфигурации.

**Лестница решения.** Условия проверяются сверху вниз, первое сработавшее определяет исход.

| № | Условие | Исход |
| --- | --- | --- |
| 1 | Хотя бы один вердикт `deny` | `deny` по ответу этого инспектора |
| 2 | `total >= waf_score_deny` | `deny` с кодом `SCORE_THRESHOLD` и ответом из `waf_score_deny response=` |
| 3 | Хотя бы один вердикт `redirect` | `redirect` на адрес из ответа этого инспектора |
| 4 | Иначе | `allow` |

Ступень 2 пропускается, если порог выключен.

Порядок ступеней не произволен. Явный `deny` идёт выше порога, потому что он утверждает факт, а не
оценку: инспектор, нашедший вирус, не должен зависеть от того, набралось ли достаточно баллов у
остальных. Обе формы отказа идут выше редиректа, потому что предлагать разгадать капчу тому, кого мы
уже решили не пускать, — это подсказка атакующему и лишний трафик. Из этого же порядка следует, что
сервис челленджа не может увести клиента на проверку там, где вред уже доказан: его `redirect`
проиграет и явному `deny`, и порогу.

Пассивные инспекторы (`mode=passive`) не участвуют ни в одной ступени.

**Выбор ответа отказа.** Для ступени 1 в режиме `waf_deny_mode fast` берётся `response` инспектора,
ответившего первым; в режиме `deterministic` — с наивысшим приоритетом по порядку объявления
`waf_inspector`. Для ступени 2 инспектора-виновника нет, поэтому запись каталога берётся из
конфигурации маршрута, а в аудит пишутся `deny_code: SCORE_THRESHOLD`, полная раскладка счёта по
инспекторам и имя наибольшего вкладчика в поле `score_top` (при равенстве вкладов — первый по
порядку объявления).

**Переопределения заголовков.** Применяются в порядке объявления инспекторов в конфигурации,
последний выигрывает. Порядок прихода ответов не влияет ни на что. `unset` применяется перед `set`
в пределах одного инспектора. Ответы с вердиктом `score` в этом равноправны с остальными: инспектор,
не принявший решение, всё равно может пометить запрос заголовком для приложения.

**Cookie.** Складываются в порядке объявления инспекторов. Повторное имя cookie от инспектора с более
поздним объявлением перекрывает предыдущее. Применяются на любом исходе волны и на обеих фазах:
`Set-Cookie` уезжает и с пропущенным запросом, и со страницей отказа, и с редиректом челленджа.

**Счёт.** Суммируется независимо от порядка прихода ответов, поэтому от гонок не зависит вовсе.

**Частичный набор.** При таймауте решение принимается по той сумме, которая успела накопиться, и
применяются переопределения от успевших инспекторов. Это значит, что таймаут инспектора при
`waf_deadline ... pass` не просто пропускает его вердикт, а занижает счёт: замедлить один сервис —
рабочий способ уйти под порог. Если счёт несёт основную нагрузку по блокировке на маршруте,
`waf_deadline ... block` перестаёт быть перестраховкой.

## Ограничения канала

Инспектор, который может подставить произвольный заголовок, cookie и код ответа, — это удалённый
редактор вашего трафика. Скомпрометированный или просто забагованный инспектор в такой роли опаснее
той атаки, от которой он защищает. Модуль обязан валидировать всё, что приходит с провода.

**Заголовки.** Белого списка имён нет. Безусловно запрещены: `Host`, `Authorization`, `Cookie`,
`Content-Length`, `Transfer-Encoding`, `Content-Encoding`, `Connection`, `Upgrade`,
`Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`.

**Значения.** Отбраковываются значения, содержащие CR, LF или NUL: иначе получается расщепление
ответа. Проверяется и имя, и значение; ограничение длины задаётся `waf_header_value_max`.

**Коды ответа.** Код отказа с провода не принимается вовсе: он берётся из каталога
`waf_deny_response`, где 2xx и 3xx запрещены при загрузке конфигурации, иначе «отказ» превращался бы
в тихий пропуск. В вердикте `redirect` код принимается, но только из белого списка 302, 303, 307.

**Страницы.** Только символьное имя записи каталога. Ни путей, ни содержимого страницы с провода:
страницу отдаёт nginx.

**Цель редиректа.** Единственное исключение из предыдущего пункта, и поэтому проверяется отдельно и
подробно. Адрес обязан пройти по порядку:

- ни одного байта вне печатного ASCII: CR, LF и NUL здесь означают расщепление ответа, а остальному
  в URI место только в процентной записи;
- длина не больше `waf_header_value_max`;
- обратный слеш запрещён — браузеры нормализуют его в прямой, парсеры обычно нет, и на этом
  расхождении строится обход проверки хоста;
- форма `//host/path` запрещена: для браузера это абсолютный адрес без схемы, для наивной проверки
  пути — локальный путь;
- схема только `http` или `https`; `javascript:`, `data:` и прочее отбраковываются;
- `userinfo` в authority запрещён: `https://good.example.com@evil.example.com/` ведёт на evil, а
  невнимательная проверка видит good;
- адрес совпал хотя бы с одним шаблоном `waf_redirect_allow` маршрута. Пустой список означает, что
  редиректы здесь запрещены вовсе.

Непрохождение любой проверки или `redirect` без адреса — это битый ответ, а не отказ: он
отбраковывается целиком с записью в лог, как несовпадение `rid` и незнакомая версия схемы. Другого
вердикта у инспектора нет, поэтому волна продолжает его ждать, и исход определяет политика `waf_deadline`.
Так модуль и здесь ничего не решает за контур: у ответа, который нельзя применить, и у молчания
последствия одинаковые.

**Счёт.** Целое в диапазоне 0–100. Всё остальное — дробное, отрицательное, выходящее за границу,
нечисловое — приводит к отбраковке ответа целиком. Режим вызова и порог живут только в
конфигурации: инспектор не может ни перевести себя в боевые, ни изменить порог. Максимум, на что он
влияет, — собственный вклад, и верхняя граница этого влияния известна заранее и равна ста.

**Cookie.** Белого списка имён нет. С провода инспектор задаёт только `name`, `value`, `path` и
`max_age`. Атрибуты `secure`, `http_only` и
`same_site` разбираются строго — мусор в значении отбраковывает ответ, — но затем отбрасываются:
их целиком определяет `waf_cookie_defaults` маршрута. Поле `domain` отбрасывается так же, cookie
остаётся host-only, то есть привязанной к текущему `server_name`.

Присылать эти поля не запрещено и не бесполезно (ответ инспектора остаётся самодостаточным
документом), но полагаться на них нельзя: контур решает сам.

**Действия.** Модуль их не исполняет, но форму проверяет: `do` и `apply` только из словарей и только
допустимой парой, адресат — имя из реестра, повод в алфавите `[A-Z][A-Z0-9_]*` и не длиннее 64 байт,
`delta` — целое −1000…1000, `value` — целое 0…1000. Незнакомый глагол или ось отбраковывают ответ
целиком. Кто высказался и на какой фазе, проставляет модуль: с провода эти поля не принимаются, иначе
инспектор подписывался бы чужим именем. Число и размер ограничены `waf_actions_max` и
`waf_action_max`, потому что буфер сообщения считается до запроса. Подробности —
[inspector-actions.md](inspector-actions.md#ограничения-канала).

**Версия схемы.** Сообщение с незнакомым `v` отбрасывается со счётчиком и записью в лог ошибок.

**Размер ответа.** Ограничивается `waf_reply_max`, по умолчанию небольшое значение. Инспектор не
может передать тело страницы, поэтому большого ответа не требуется.

**Идентичность.** Ответ учитывается только если `rid` совпадает с ожидаемым, а `inspector` входит в
маску текущей волны. Это следует из модели масок и не требует отдельной проверки списков.

Транспортный уровень доверия — аккаунты и ограничения subject в NATS, см. [security.md](security.md).

## Челлендж и цикл редиректов

Сломанный или перегруженный сервис челленджа без защиты даёт бесконечный редирект для всех
пользователей. Это отдельный класс аварии, но разбираться с ним модулю нечем: он не знает ни что
такое капча, ни сколько попыток клиент сделал, ни валиден ли выданный маркер. Всё это состояние
принадлежит сервису, поэтому и защита живёт там же:

1. Сервис считает попытки — по своей cookie, по своему хранилищу, как ему удобно. Исчерпав предел, он
   перестаёт присылать `redirect` и присылает `deny`: у него есть и этот вердикт.
2. Сервис же проверяет предъявленный маркер и, если тот валиден, отвечает `allow`, а не повторным
   редиректом.
3. Со стороны конфигурации остаётся ровно два обязательства, и они наблюдаемы при `nginx -t` и в
   логе: location цели редиректа исключён из проверок (`waf off` внутри `location /waf/`), иначе
   челлендж получает челлендж; и цель входит в `waf_redirect_allow`, иначе редиректа не будет вовсе.

Модуль в этой схеме не участвует, и это его лучший вклад: он не может ни зациклить клиента
собственным решением, ни отменить решение сервиса.

## Версионирование

Версия схемы указывается в каждом сообщении в обе стороны. Правила совместимости:

- Добавление необязательного поля не увеличивает версию. Инспекторы обязаны игнорировать незнакомые
  поля.
- Удаление или переименование поля, изменение типа, изменение семантики существующего поля
  увеличивают версию.
- Модуль может быть настроен публиковать сразу две версии в переходный период
  (`waf_protocol_versions 1 2;`), тогда инспектор отвечает в той версии, в которой получил запрос.
- Несовместимость версии обрабатывается как отсутствие ответа, то есть по политике `waf_deadline`, и
  сопровождается отдельной метрикой и алертом.

Версия 2 меняет форму несовместимо: заголовки, строка запроса и тело сведены в одну секцию `store`
вместо `http.headers` и верхнего `body`, вместо `http.args` едет только `args_size`, добавлены
`needs` и `audit_subject`, а из ответа убраны `reason.text`, `reason.rule` и `audit`.
