# e2e

Сквозные прогоны контура. Живут в рабочем месте (`placitum-workspace`): клиенту они не нужны.

Статус на 13.09.2026: эталон, сброс и прогон набора между сбросами работают
(`e2e.sh baseline | reset | run | status`). Набор `logic` оживлён на стенде mvm: после правок
проходят все 15 кейсов (частями — одним прогоном целиком ещё не гонялся), разбор ниже. Остальные
наборы перенесены из `tests/` монорепы (`db0ea6a`) как есть.

## Правила

1. **Прогон идёт на стенде `placitum` и сбрасывает его.** Эталон — снимок томов стенда. Сброс
   стирает всё, что сделано на стенде после снимка, в том числе руками; во время прогона
   стендом не пользуются.
2. **Каждый набор начинается с эталона.** Перед набором стенд возвращается к снимку целиком:
   тома восстанавливаются из архивов, контейнеры создаются заново. Сбрасывается всё сразу:
   база и память контроллера, KV и потоки NATS, аудит ClickHouse, архив MinIO, Redis (томов у
   него нет, пустеет при пересоздании), поколение на крае, общая память модуля, память
   инспекторов. После набора стенд тоже возвращается к эталону.
3. **Внутри набора — журнал.** Кейсы заводят объекты через API и сносят их в обратном порядке
   (`lib/stand.mjs`, `ledger().unwind()`). Кейс, который нарочно ломает контур (роняет процесс,
   заливает очередь), помечается `reset: case` и получает эталон перед собой.
4. **Только публичные входы.** Всё заводится через API контроллера, трафик идёт через край,
   проверки читают API, ClickHouse, NATS и Redis. Монтировать профили и конфиги компонентов
   нельзя: на установке из репозиториев их на диске нет.
5. **Всё помечено прогоном.** У прогона свой адрес клиента (198.18/15) и свои логины; имена
   объектов — с префиксом `e2e-`.
6. **Один прогон за раз.** `e2e.sh` держит замок `.baseline/.lock`, раннеры — `lib/lock.mjs`.

Почему одного журнала мало: он не убирает аудит, архив, записи keeper, корзины капчи, память
инспекторов и мусор упавшего прогона — отсюда нынешний `--clean`.

## Команды

```sh
e2e/e2e.sh status                     # отпечаток образов, какие эталоны есть и какой подходит
e2e/e2e.sh baseline [--force]         # фикстуры, издание всех каналов, снимок томов
e2e/e2e.sh reset                      # вернуть стенд к эталону и дождаться его поколения
e2e/e2e.sh run logic                  # сброс → весь набор → сброс
e2e/e2e.sh run logic one-denies       # то же для названных кейсов
```

`run` передаёт раннеру адреса стенда: `WAF_CONTROLLER` — панель из `core/.env`, `WAF_E2E_EDGE` —
порт узла оттуда же (на mvm `:8000`; умолчание библиотеки — haproxy стенда Windows `:8081`). Код
возврата — код набора; второй сброс идёт и после упавшего набора.

**Упавший набор оставляет журналы всех контейнеров за время набора** в
`reports/<время>-<набор>/<сервис>.log` — до сброса. Сброс пересоздаёт контейнеры, и без этого
причина (отказ `nginx -t` на крае, ошибка инспектора) пропадает вместе с ними.

Все вызовы compose в `e2e.sh` идут с надстройкой `compose.yml`: без неё отпечаток не совпадёт
с поднятым стендом.

## Надстройка compose

`compose.yml` поверх `core/compose/waf.yml`:

- **`app`** — витрина `shop` (образ `placitum/testapp`, loopback `:8083`). Апстрим кейсов —
  `app:8080`.
- **`geo`** — кодер на учебной выгрузке `geo/testdata` из клона geo: страны ru, us, jp и ASN
  2516, 12389, 13335, 15169. Кейсы с записью подсетью и системой (`write: net | net_all | asn`)
  берут адреса из этих анонсов: без резолва анонса запись молча не случается. У установки
  каталог гео пуст.

## Эталон

- **Порядок снятия:** `compose up -d` (стенд приводится к текущей надстройке) → здоровье →
  фикстуры (`fixtures/stand.mjs`) → издание всех каналов и ожидание сходимости → остановка →
  архивы томов → подъём и проверка.
- **Каналы издаются после фикстур обязательно.** Фикстуры правят базу, и поколение, изданное
  до них, с базой уже не совпадает. После сброса внутренний Redis пуст, и такое поколение
  контроллер не дошлёт: `desired blobs expired and cannot be restored … source changed since
  publish`. Край остаётся без поколения (`apply null`), сброс не сходится.
- **Где:** `.baseline/<отпечаток>/<том>.tar`, рядом `meta` (поколение, число инспекторов, время,
  коммит core) и `images`. В git не едет.
- **Отпечаток:** sha256 от ID образов всех сервисов и отрисованного `docker compose config`.
  Сменился образ или надстройка — эталон снимается заново: старую базу под новый код не
  восстанавливаем.
- **Размер 13.09:** около 60 МБ: postgres около 50, clickhouse 2–22, nats до 6, остальное —
  килобайты. ФС под Docker — ext4 без снимков, поэтому архивы tar (busybox из `alpine`,
  владельцы по номерам).
- `vlai-checkpoint` в эталон не входит: это кеш весов модели, а не состояние.

## Фикстуры

`fixtures/stand.mjs` — то, на что опираются наборы и чего нет ни в поставке, ни в примере первой
инициализации. Через API, идемпотентно: расходящуюся запись приводит к нужной.

| Фикстура | Зачем |
| --- | --- |
| ответ отказа `error` (503, без `page`) | маршруты наборов пишут `waf_exception request deny response=error`, а в поставке такой записи нет |

`page=` у записи каталога — named location (`@…`), а не имя объекта «Страницы». Имя объекта
контроллер принимает и печатает как есть, а `nginx -t` на узле отвечает «page= expects a named
location», и узел не применяет поколение целиком. Поэтому фикстура — без `page`, как поставочные
записи.

## Сброс

1. `docker compose … down --remove-orphans` — контейнеры и сеть; тома остаются.
2. Каждый том очищается и разворачивается из архива эталона; тома проекта, которых в эталоне
   нет, снимаются.
3. `up -d`, затем своё ожидание здоровья: каждый контейнер healthy, а без пробы — просто Up.
   Не `up --wait`: тот сдаётся на первом unhealthy, а после рестарта процесс может провалить
   несколько проб, пока контроллер досылает поколение, и поправиться сам.
4. Ждать сходимости: все ноды во флоте отчитались поколением эталона с `apply ok`, инспекторов
   не меньше, чем при снимке.

**Замер 13.09 на mvm:** эталон снимается за 35 с, сброс — 39–68 с: снос и тома около 18,
подъём около 21, сходимость 0 или 27 — агент края перезапрашивает поколение раз в 30 с.

Не путать со `stand/preprod/stand.sh reset`: тот сносит тома, образы и секреты под установку
с нуля.

## Как устроен набор logic

Кейс — только данные (`logic/cases.mjs`): `needs` (что завести), `target` (сервер и путь),
`probes` (запросы и ожидания), по желанию `requires`, `identity`, `actors`, `socket`.
Прогон кейса (`logic/run.mjs`):

1. **Заведение.** `apply(ctx, needs)` из `lib/stand.mjs` создаёт через API наборы, профили,
   апстримы, объявления, серверы и маршруты в постоянном порядке и ведёт журнал.
2. **Издание.** `publish` шлёт `send` в каналы, которые выводятся из состава кейса, `converge`
   ждёт, пока потребители отчитаются поколением. Состояние `failed` при пустом списке ошибок
   черновика — отказ на узле: смотреть журнал края в `reports/`.
3. **Проверки.** `runProbes` из `lib/check.mjs` шлёт каждый запрос через край (`node:http`, чтобы
   не потерять `Host`) с адресом клиента в `X-Forwarded-For`, разбирает `X-WAF-Debug` и сверяет
   ожидания: `status` или `deny` (код из каталога ответов), `verdict`, `by`, `answers`,
   `asked`/`notAsked`, `bodyHas`/`bodyLacks`. Проверка повторяется до 15 с — между «канал
   сошёлся» и «инспектор применил» есть щель. Особые шаги: `solve` проходит виджет капчи (ответ
   картинки — из redis-internal), `list` смотрит записи набора и их сроки.
4. **Снос.** Журнал разматывается в обратном порядке, каналы издаются снова. Остатки после
   упавшей проверки называются, но не подменяют причину падения.

## Первый полный прогон logic (13.09)

С чистого стенда прошли 8 из 15. Все падения — расхождения стенда Windows с поставкой, ни одно не
про логику кейса:

| Кейсы | Причина | Чем закрыто |
| --- | --- | --- |
| `counter-user`, `-mask`, `-silent`, `-frames` | процесс калитки в кейсах назывался `auth2` — так строка каталога называлась до поставки 1.0; теперь `auth` | имя в `logic/cases.mjs` и `load/cases.mjs` |
| `action-list-scopes`, `captcha-ban-ladder` | кодер гео пуст: нет анонсов `1.1.1.0/24` и `8.8.8.0/24` | `geo/testdata` в надстройке |
| `shop-funnel-trap` | `nginx -t` на крае: два живых набора `in_nginx` с умолчательным лимитом 1 000 000 записей требуют 256 МБ, а поставочная зона `waf` — 8 МБ | явный `limit: 10000` у наборов кейса |

До этого прогона понадобились ещё две правки в контроллере (пример первой инициализации: сервер,
путь `/waf/captcha` и схема json для `default`) и фикстура `error`.

**Найдено в продукте и не закрыто:**

- контроллер не сверяет ёмкость общей зоны `waf` с лимитами наборов `in_nginx`: такой набор с
  умолчаниями ломает поколение узла целиком на чистой установке;
- контроллер принимает `page` ответа отказа не в виде named location — тот же исход;
- «Восстановить» у `default` капчи и json сбрасывает документ в `{}`, а он невалиден.
