# Нагрузочные кейсы

Прогон автономен. Начало — пустой стенд, конец — снова пустой стенд. Всё, что
нужно кейсу, заводится через API контроллера в начале и сносится в конце:
апстрим, сервер, слушатель, наборы адресов, составные наборы, профили,
объявления инспекторов и маршруты. Ручных правок конфигов, записей в базу и
отдельно поднятых процессов нет нигде.

```
node tests/load/run.mjs                 # все кейсы по очереди
node tests/load/run.mjs ip-lists        # только названные
node tests/load/run.mjs --keep          # не сносить, оставить для разбора
node tests/load/run.mjs --setup-only    # завести, издать и остановиться
node tests/load/run.mjs --steps 200,400 # свои ступени вместо кейсовых
node tests/load/run.mjs --clean         # снести остатки e2e- и выйти
node tests/load/run.mjs --no-swap       # отсчёт: та же нагрузка без смен
```

`--clean` нужен после `--keep` и после аварийно оборванного прогона: журнала у
него нет, единственная защита — префикс имени.

Код возврата 0, если все кейсы чистые. Нужен поднятый `deploy/` целиком:
контроллер, края, шина, генератор и витрина (`docker compose up -d --wait`).

## Предполёт

Прогон против промежуточной сборки ничего не доказывает: зелёный результат может
значить «код исправен», а может — «стенд не знает о правке». Поэтому каждый
прогон начинается с приведения стенда в соответствие с исходниками
(`tests/lib/bootstrap.mjs`).

| Что | Как |
| --- | --- |
| Миграции | Журнал `waf_schema_log` в самой базе; применяется всё, чего в нём нет, файлом изнутри контейнера. Основание называется один раз: `WAF_SCHEMA_BASE=090`. |
| Сборка | Только те сервисы, у которых самая свежая правка в контексте новее образа. Пачками по три; сорвавшаяся пачка пересобирается по одному, до трёх попыток на сервис. |
| Раскатка | Волнами: инспекторы, служебные, контроллер, края. Обратный порядок ломает рассылку — новый контроллер считает хеш по-новому, старый инспектор его отвергает, и перестают доезжать даже правки профилей. |
| Сверка | `GET /api/actions` против словаря глаголов в `controller/src/model/actions.ts`. Расхождение останавливает прогон, а не пишет предупреждение. |

Флаги: `--no-bootstrap` пропускает предполёт целиком, `--reset-db`
пересоздаёт том базы, накатывая схему и гео-сид заново. Данные стенда при этом
теряются, поэтому это отдельный явный шаг, а не часть обычного прогона.

Сборка образов и раскатка на этом стенде занимают минуты, когда правок много,
и секунды, когда всё свежее.

## Порядок прогона

| Шаг | Что происходит |
| --- | --- |
| Предполёт | Приводит стенд в соответствие с исходниками: миграции, сборка изменившегося, раскатка по волнам, сверка реестра глаголов. Пропускается только явно. |
| Заведение | Сущности кейса через API, в порядке зависимостей. Каждая записывается в журнал. |
| Издание | `send` названных кейсом каналов, затем ожидание сходимости флота. |
| Пул адресов | Если кейс просит, раннер достаёт настоящие префиксы стран, ASN и своих списков и складывает пул заданного размера. |
| Проверки | Одиночные запросы через край, по одному на правило: код, вердикт, кого спросили. Повторяются до 15 с — канал сошёлся раньше, чем инспектор сменил набор. |
| Нагрузка | План уезжает в генератор через контроллер (`/api/load`), раннер ждёт конца. |
| Смены | Только у кейса с блоком `swap`: пока идёт нагрузка, раннер правит конфигурацию и следит за краем и флотом. См. «Правка под нагрузкой». |
| Горячий список | Только у кейса с блоком `hot`: затравка до нагрузки, планы подряд до цели, наблюдение за keeper, зеркалами и памятью, схождение и проверки после. См. «Горячий список». |
| Суд | Генератор размечает ступени порогами кейса; потолок — последняя чистая. |
| Снос | Журнал разматывается задом наперёд, потом каналы издаются снова, чтобы края сошлись на конфигурации без наших маршрутов. |

Снос идёт в `finally`: сорвавшийся прогон всё равно убирает за собой.
Не снятое перечисляется поимённо и роняет код возврата.

## Устройство

| Файл | Кто читает | Что несёт |
| --- | --- | --- |
| `cases.mjs` | раннер, генератор, панель | каталог: `needs` (что завести), `traffic` (пресет формы), `clean` (пороги чистой ступени) |
| `run.mjs` | оператор | полный цикл: завести, издать, нагрузить, рассудить, снести |
| `../lib/api.mjs` | обе секции e2e | клиент API контроллера, ничего кроме HTTP |
| `../lib/stand.mjs` | обе секции e2e | заведение по описанию, журнал созданного, издание и сходимость |
| `../lib/hot.mjs` | кейс горячего списка | то, чего через API не видно: счётчики keeper по его HTTP, `docker stats`, журнал краёв, полный каталог для кодера гео |

`cases.mjs` — **только данные и чистые функции, без импортов**. Его читает не
только раннер, но и генератор внутри контейнера, где `tests/lib` не смонтирован.
Генератор перечитывает файл по mtime и не возит `needs` в панель: форме нужен
только `traffic`.

## Имена и чужой стенд

Все заводимые сущности начинаются с `e2e-`. Занятое имя — отказ заведения, а не
молчаливое переиспользование: иначе снос в конце убрал бы чужое. Поэтому прогон
безопасен и на стенде, где живёт что-то ещё, но собственное пространство имён
кейс обязан соблюдать.

Сервер кейса привязывается к слушателю **без** `default_server`: умолчательным
на этом порту может владеть чужой сервер, а второй такой же — отказ сборки.
Различение идёт по имени хоста, которое генератор шлёт заголовком `Host`.

## Чистая ступень и потолок

Ступень чистая, когда выполнены все условия. Пороги задаёт `clean` кейса, без
них работают умолчания генератора.

| Порог | Умолчание | Что считает |
| --- | --- | --- |
| `unexpected_pct` | 1 | доля ответов с кодом не `traffic.expect` |
| `fails` | 0 | ответов с `fail=` в `X-WAF-Debug` (timeout, bus, absent, body, inspector) |
| `sockets` | 0 | ошибки сокета и таймауты самого wrk |
| `p99_ms` | не проверяется | p99 задержки клиента |

Потолок — последняя чистая ступень до первой грязной: цифры после неё про
перегрузку, а не про предел.

Ступени внутри одного прогона идут подряд, и это занижает поздние: открытый
ранней ступенью предохранитель инспектора живёт секунды. Для аккуратных цифр
ступени гоняются порознь (`--steps` по одной) и по три повтора на точку.

## Флаги трафика

- `ip_walk` — обход списка вместо случайных адресов, ради повторяемости. Кейс
  описывает источники в блоке `pool` (`{country: "de", limit: 200}`,
  `{asn: 3320}`, `{list: "имя"}`, `{cidrs: [...]}`), раннер достаёт настоящие
  префиксы через API и складывает пул заданного размера, генератор обходит его
  по порядку. Один прогон — один и тот же набор адресов; чередование между
  потоками зависит от их числа.
- `random_ip` — `X-Forwarded-For` новый на каждый запрос: `public` (любой
  незарезервированный IPv4), `private` (RFC 1918), `testnet` (TEST-NET-1..3).
  Не используется, когда задан обход.
- `unique` — `?_n=<поток>-<номер>` в строке запроса: мимо кешей, с разными
  параметрами.
- `sizes` — добор тела (`_pad` в JSON или форме), заголовков (`X-Load-Pad`) и
  параметров (`&_pad=`) до корзины; `orig` — как в пресете.

### Личности прогона

Кейсу с калиткой нужен токен, а токен не запишешь в файл: он живёт один запуск.
Кейс объявляет `identity: { logins: ["alice"] }` и ставит имя там, где нужно
значение, — `"@jwt.public"` в документе источника входа, `"@bearer.alice"` в
заголовке трафика. Пару ключей RSA и токены делает `../lib/identity.mjs`,
подставляет их раннер (в `needs`, в `probes` и в `traffic`). Логин каждого
запуска свой, поэтому корзины прошлого прогона этому не мешают. Панель на
странице «Трафик» покажет имя как есть: значение подставляется только в план,
уезжающий генератору.

### Правка под нагрузкой

Кейс с блоком `swap` меняет конфигурацию, пока идёт нагрузка. Это единственный
род кейсов, где стенд не стоит на месте от начала прогона до конца.

Расписание раннер считает сам, по ступеням трафика: середина каждой ступени,
начиная с `fromStep`. Числами в кейсе оно не пишется намеренно — `--steps`
двигает лестницу и расписание разом, а удар всегда приходится в середину
ступени, а не в шов между двумя запусками wrk, где мерить нечего.

Одна смена — это правка файла правил тем же `PUT`, которым правит панель, плюс
`POST /rules/send`. Дальше раннер щупает край с частотой `sampleMs` двумя
запросами и одновременно смотрит пульс (`GET /api/fleet`):

| Что меряется | Как |
| --- | --- |
| `правка`, `издание` | сколько заняли сами вызовы API |
| `отказ`, `устойчиво` | от правки до первого и до `stable` подряд отказов по новому правилу через край |
| `первая`, `все` | от правки до отпечатка нового поколения у первой и у последней живой копии инспектора **в пульсе** |
| `сторож` | пробы, в которых **старое** правило не сработало. Обязан быть ноль |
| `сбои` | пробы с `fail=` в отладочном заголовке |

Сторож — главное в кейсе. Правило с этой меткой стоит во всех поколениях, и
пока новый набор собирается, отказывать обязан старый. Одна проскочившая проба
означает окно, в котором маршрут не проверялся ничем.

Щупается он только в окне смены — от правки до подтверждения плюс `tailMs`, —
а не весь прогон: дыра, если она есть, живёт именно там. Промежутки между
сменами закрывает сама нагрузка: её запросы благонамеренны и обязаны отвечать
`200`, и «не тот код» в таблице ступеней тоже ноль.

Край и пульс меряют разное, и путать их нельзя.

Край — правда для клиента. Проба попадает в случайную копию (подписка
групповая), поэтому `отказ` означает «хоть одна копия сменила набор», а
`устойчиво` — «отказывают подряд `stable` раз». В `устойчиво` вдобавок зашито
`stable × sampleMs` мёртвого времени по построению: это цена подтверждения, а
не замены.

Пульс — то, что **знает контроллер**, и он отстаёт на такт heartbeat
(`WAF_HEARTBEAT_EVERY`, умолчание 4 с) плюс ingest. Поэтому столбцы `первая` и
`все` почти всегда показывают около такта, и читать их как время замены нельзя:
по журналу самого инспектора (`desired applied`) пять копий укладываются в
десятки миллисекунд друг от друга. Годятся они для другого — увидеть копию,
которая поколение **не** взяла: отставшая так и останется со старым отпечатком.

Кейс со сменами судится строже обычного: чистыми обязаны быть **все** ступени,
а не последняя перед первой грязной. Потолок здесь ни при чём — темп ровный, и
просадка ищется сравнением ступеней между собой.

Сравнивать ступени внутри одного прогона мало: они разнятся и сами по себе.
Отсчёт даёт `--no-swap` — тот же кейс, тот же темп, конфигурацию никто не
трогает. Просадка от замены — это разница между двумя прогонами, а не между
первой и четвёртой ступенью одного.

### Горячий список

Кейс с блоком `hot` меряет не потолок конвейера, а раскидку одного активного
набора по всем, кто его читает. Капча банит каждый новый адрес — инспектор
действий наливает её корзину доверху одной просьбой `note`, `bucket_ban`
пишет запись на час, — и список растёт со скоростью трафика: адреса
случайные и не повторяются. Читают его keeper (истина и дельты), три копии
инспектора адреса (зеркало в памяти, `deny` по набору на волне 0), края
(зеркало в общей памяти, `in_nginx`, локальная проверка до инспекторов) и
две капчи (память о том, кого уже записали).

Порядок: **затравка** — раннер сам заходит с адресов `hot.samples`, первый
визит обязан пройти, второй, через секунду, получить отказ: так до нагрузки
видно, что бан вообще работает. Потом **планы подряд** (`hot.rounds`): у
генератора один план не длиннее десяти минут, а цель (`hot.target`, потолок
набора) за него может не набраться; между планами размер спрашивается у
keeper — контроллер у активного набора считает только своё, а пишет сюда не
он. Всё это время **наблюдение** раз в `hot.sampleMs`: счётчики keeper по его
HTTP (`WAF_KEEPER`, умолчание `http://127.0.0.1:8098`) — записи, отказы,
дельты, снапшоты, хвосты, время склада; зеркала инспектора адреса из пульса
(`live` в строке инспектора: uuid набора, seq, база плюс точечные, прогрет
ли); темп и 5xx краёв; память контейнеров через `docker stats` на каждом
втором такте. После нагрузки — **схождение**: ждём, пока каждое зеркало
сравняется с keeper, но не дольше `hot.settleMs`; **проверки**: контрольный
адрес (`hot.control`, из бенчмарочного диапазона, генератор его не выдаёт)
обязан пройти, затравка — получить отказ по три пробы на адрес через
балансировщик, и видно, кто отказал: край (`by=local`) или инспектор адреса;
**журнал краёв** по набору с начала прогона: снапшоты, хвосты, «нет места в
зоне», предупреждения, ошибки.

Смертью считается любое из: отказы или ошибки склада у keeper; зеркало, не
сошедшееся с keeper; край без места в зоне или с ошибками по набору;
контейнер у предела памяти (пик выше 900 МиБ из 1024); грязная ступень;
контроль не прошёл; затравка прошла хоть раз — ранняя запись не дожила.

Флаги прогона: `--write addr|net|net_all|asn` — режим записи капчи, значение
подставляется в правило профиля (`"@hot.write"`); `--geo full` — полный
каталог ASN у кодера гео на время прогона: выгрузка из базы контроллера
(IPv4, ~660 тысяч префиксов) ложится в `geo/testdata/asn/e2e-full.tsv`,
кодер перечитывает каталог сам по отпечатку, после прогона файл снимается и
раннер ждёт, пока кодер вернётся к учебному набору; без него `net` и дальше
почти всё пропустят — учебный каталог знает пять сетей; `--no-edge` — набор
без `in_nginx` и маршрут без локальной проверки, края не зеркалят;
`--target N`, `--rounds N` — своя цель и число планов.

### Бан инспектором адреса

Кейс с блоком `ban` меряет не цену поиска, а **цену бана**: сколько времени
проходит от запроса, который поставил бан, до отказа тому же адресу, сколько
такой контур держит и во что обходится по памяти.

Три эндпоинта на одном сервере, у каждого свой профиль инспектора адреса и своё
объявление. Профиль — шестнадцать терминальных строк подряд: четыре белых
статических списка (`allow`), четыре чёрных (`deny`), восемь активных (`deny`).
Списки у всех трёх профилей одни и те же, поэтому бан, поставленный на одном
эндпоинте, закрывает адрес и на двух других.

Банит **сам инспектор адреса** — строкой по исходу `on: none`: «не нашёлся ни в
одном списке» → внести в свой активный список на пять секунд. Охват записи у
каждого эндпоинта свой: `/addr` пишет адрес, `/net` — эффективный анонс,
`/asn` — систему целиком, пачкой всех её префиксов. Модуль в бане не участвует:
у наборов нет `in_nginx`, у маршрутов нет локальной проверки — отказ выносит
инспектор.

Порядок прогона:

1. **загрузка** — по 20 000 записей в каждый из восьми активных списков (прямо
   в keeper пачками, `fillLive`) и по 20 000 подсетей /24 в каждый статический
   (телом пака). Всего 320 000 записей до первого запроса;
2. **реакция на покое** — пять раундов на эндпоинт: запрос, ставящий бан, потом
   опрос края без пауз до первого отказа и до пятнадцати отказов подряд;
3. **нагрузка** — ступени кейса, пробы реакции повторяются в середине рабочей
   ступени;
4. **оседание** — записи истекают, списки возвращаются к загруженному размеру.

Загруженный состав лежит там, куда генератор не ходит (`reserved()` в
wrk/script.lua): статика в 240.0.0.0/4, активные списки в 10.0.0.0/8. Поэтому
все шестнадцать проверок честно промахиваются — меряется промах, а не попадание.

Адреса проб — бенчмарочные 198.18.0.0/15 и 198.19.0.0/16: генератор их не
выдаёт, в загруженном составе их нет, и чужой бан попасть туда не может. Чтобы
`net` и `asn` было что писать, прогон дописывает кодеру свои системы под эти же
адреса (`probeGeo` в tests/lib/ban.mjs): по одному анонсу на систему и одна
система из 250 анонсов — на ней видно, что размер пачки на время реакции не
влияет.

**Полный каталог ASN обязателен** (`ban.geo: "full"`): на учебном каталоге
случайный адрес кодеру неизвестен, и `net`/`asn` не пишут ничего — инспектор
пишет `list write skipped: coder knows nothing about the address` и идёт дальше.

Порог «не тот код» у кейса снят (`unexpected_pct: 100`): отказ в трафике здесь —
предмет, а не грязь. `net` и `asn` закрывают не адрес, а анонс и систему, и уже
на 300 rps через десять секунд 40 % случайного потока получает отказ.

### Проверки кейса

Блок `probes` — список одиночных запросов с ожиданиями. Поддерживаются:

| Ожидание | Что значит |
| --- | --- |
| `status` | код ответа числом |
| `deny` | код берётся из каталога отказов по имени записи, а не пишется числом: у `blocked` на разных стендах разный статус |
| `verdict` | `v=` из отладочного заголовка |
| `asked` | инспектор присутствует в заголовке |
| `notAsked` | инспектора в заголовке нет — так выглядит выключенный просьбой `off`, модуль его не печатает вовсе |

### Чего пока нет

`score` на маршруте от строки профиля адреса. Контроллер, поднятый на стенде,
отвергает такую строку (`invalid_rule`), хотя в исходниках запрета не видно:
это расхождение непересобранного контроллера. Строка в кейсе закомментирована,
вернуть её — после пересборки.

Сообщения между инспекторами (`note` соседу с корзиной) требуют принимающей
стороны: профиля счётчика с правилом приёма и общей корзины. Ни того, ни
другого библиотека пока не заводит.

### Что нашёл горячий список (10.09)

Цифры двух прогонов подряд, до и после правок, темп 1500 rps, запись `addr`.

| | до | после |
| --- | --- | --- |
| темп, который держим | ~400 записей/с, 57 % ответов 500 (`fail_timeout` на волне капчи) | ~950/с, 5xx единицы |
| зеркала краёв | **пусты**: 408 запросов снапшота, применён 1, на ноль записей | весь состав, 138–143 МиБ на край |
| «расхождений» у края | 13 000 в минуту на край, 216 000 за прогон | 0–1 в минуту |
| снапшотов у keeper | 1131 | 15–17 |
| память keeper | 630 МиБ пик на 349 тыс. (~1.8 КБ на запись) | 148 МиБ на 408 тыс. (**~370 Б**) |
| склад keeper | до 199 мс | 4–9 мс |
| зеркала инспектора адреса | точны, сходятся за 4 с | так же, отставание сотни записей |

Четыре находки, все починены здесь же:

1. **Новый активный набор молчал на краях.** Подписка несла номер слота в
   общей памяти, а приём брал позицию в конфиге — кадры уезжали в поток
   соседа (`dataset message names "e2e-hot", expected "shop_banned"`).
   Лечилось только полным рестартом краёв; теперь на проводе позиция.
2. **Потолок overlay был константой 10 000** (`NGX_HTTP_WAF_DS_LIVE_MAX`), а
   `live_max=` в конфиге запрещён. Записи со сроком живут именно в overlay,
   поэтому список бана выше десяти тысяч молча обрезался по LRU: край держал
   последние 10 000, на остальных отвечал «записи нет» и расходился с keeper
   хешем навсегда. Теперь потолок берётся из `limit=`, живое не вытесняется,
   а **зона проверяется на `nginx -t`**: объявленное обязано влезать, иначе
   конфигурация не грузится (`zone "waf" of 8388608 bytes does not fit the
   declared datasets: they need about 128262144 bytes`). Оценка — 128 байт на
   запись плюс 256 КБ запаса.
3. **Сверка хеша у дельты шла вне мьютекса** и без проверки, что слот всё ещё
   на своём seq. Кадр приходит каждому воркеру, слот у них общий — сосед
   успевал поставить следующую дельту, и край объявлял расхождение там, где
   его нет, а каждое расхождение стоит снапшота всего набора. Тик сверял
   правильно; теперь и дельта.
4. **Путь записи упирается в пул воркеров капчи.** Воркеров столько, сколько
   ядер по квоте (два), а работа сетевая: корзина в Redis плюс запись в
   keeper с ответом. Пропускная способность = воркеры / время сообщения;
   очередь (256 на копию) стояла дольше дедлайна маршрута. Восемь копий
   вместо двух подняли потолок примерно втрое. Keeper при этом не при чём: у
   него на набор своя горутина и неблокирующий сбор пачки, отказов ноль на
   429 тыс. записей.

Отдельно: **контроллер показывает у активного набора ноль записей** — размер
он считает по своей таблице, а пишет туда keeper. В панели горячий список
выглядит пустым; прогон печатает это отдельной строкой, но смертью не считает.
(Закрыто 11.09: панель читает состав и размер из Redis keeper.)

### Горячий список после переделки провода (11.09)

Состояние keeper переехало во внутренний Redis, дельты стали двоичными
пакетами `waf:diff:<набор>:<seq>`, снапшот -- объектом, по шине едут только
указатели, `since` снят; край держит активный набор целиком в overlay по

| | 200 тыс. (227 442 записи, 10 мин) | 1 млн (1 000 000 записей, 50 мин) |
| --- | --- | --- |
| задержка на маршруте капчи | p50 14–16 мс, p99 25–40 мс | p50 13–14 мс, p99 22–24 мс -- миллион в overlay края на задержке не виден |

Затравка: пять адресов после первого визита закрыты на всех трёх краях
(405), контрольный проходит. Проба «префикс со сроком» (`203.0.113.0/24` на
час) -- ноль `diverged`, ноль лишних снапшотов; раньше это была тысяча

Что нашлось:

1. **Панель роняла контроллер листингом горячего списка.** `GET
   …/addresses` активного набора читал состав одним `ZRANGE 0 -1` (сотня
   мегабайт), а разбор ответа по кускам сокета был квадратичным: контроллер

   записей, идентификаторы строк запоминаются только у обозримого списка.
   Листинг миллиона всё равно тяжёл для панели -- это вопрос UX, не провода.
2. Прогон помечает ступени «грязными» из-за единиц «не тот код» на границе
   бана (запрос, попавший между решением капчи и записью в overlay) --
   критерий чистой ступени к горячему списку не подходит, цифры выше
   считаются как есть.

### Что нашёл ip-ban (12.09)

Стенд: три края, keeper один (2 CPU, 1 ГиБ), кодер гео с полным каталогом
(664 558 префиксов IPv4), внутренний Redis 512 МиБ. Загружено до прогона —
160 000 записей в восьми активных списках и 160 000 подсетей в восьми
статических. Прогон сделан с `--no-bootstrap`: образы инспекторов, контроллера
и keeper собраны 11.09 вечером, модуль в контуре не участвует.

**Реакция на покое — 12–34 мс до первого отказа.** Пять раундов на эндпоинт:

| охват | копий ip | первый отказ, p50 / макс | пятнадцать отказов подряд, p50 |
| --- | --- | --- | --- |
| `addr` | 3 | 12 / 14 мс | 57 мс |
| `net` | 3 | 14 / 15 мс | 61 мс |
| `asn` | 3 | 14 / 26 мс | 61 мс |
| `addr` | 8 | 14 / 15 мс | 67 мс |
| `net` | 8 | 17 / 21 мс | 70 мс |
| `asn` | 8 | 22 / 34 мс | 84 мс |

«Пятнадцать подряд» — это первый отказ плюс пятнадцать запросов по 3 мс:
разрыва между копиями не видно, столько стоит сам опрос. Размер пачки на
реакцию не влияет: система из 250 анонсов закрывается за те же 16–22 мс, что и
адрес /32. Восемь копий отвечают на 3–10 мс медленнее трёх — столько стоит
раздать дельту вдвое большему числу зеркал.

**Потолок — не rps, а записей в секунду.** Те же три эндпоинта, 1000 rps,
трафик со случайных публичных адресов:

| копий ip | факт | p50 | p99 | отказы модуля | ступень |
| --- | --- | --- | --- | --- | --- |
| 3 | 723 rps | 605 мс | 1610 мс | 183 | грязная |
| 8 | 576 rps | 764 мс | 2010 мс | 948 | грязная |

300 rps держат обе раскладки чисто (p50 3–4 мс, p99 40–50 мс, ноль отказов).
**Восемь копий инспектора адреса потолок не подняли — опустили**: инспектор не
был узким местом, а вдвое больше писателей быстрее топят keeper.

Кто сколько пишет, видно по спискам: за 150 с нагрузки `/asn` уложил в свой
список 3,14 млн записей, `/net` — 9 700, `/addr` — 12 600. Каждый запрос на
`/asn` — это вся система целиком, в среднем около 580 префиксов на пачку.

**Цена охвата поодиночке** (1000 rps на один эндпоинт, 60 с, восемь копий ip):

| охват | факт | p50 / p99 | 5xx | записей в keeper | keeper на пике |
| --- | --- | --- | --- | --- | --- |
| `addr` | 981 rps | 5 / 732 мс | 25 | 989/с | 85 МиБ, 35 % CPU |
| `net` | 937 rps | 173 / 1020 мс | 0 | 597/с | 87 МиБ, 30 % CPU |
| `asn` | 471 rps | 893 / 2020 мс | 8 093 | 9 820/с | 1023 МиБ, 206 % CPU |

Автобан адресом на тысяче в секунду стоит keeper треть процессора и 85 МиБ.
Тот же темп с охватом `asn` пишет в двадцать раз больше записей, и контур
складывается: инспектор ждёт keeper, доходит до дедлайна маршрута (2 с) и
отвечает 500 на каждый четвёртый запрос.

**Память.** По измерениям внутреннего Redis (`MEMORY USAGE` по ключам) и
`docker stats`:

| что | на запись | 160 000 записей |
| --- | --- | --- |
| `redis-internal` (ZSET состава + хеш поводов) | ~190 Б | ~30 МиБ |
| копия инспектора адреса | ~70 Б | +11 МиБ (все 320 000 -- +22 МиБ к 114 МиБ пустой) |
| keeper в покое | ~0,5 КиБ | 88 → 172 МиБ |

Под нагрузкой память keeper определяется **темпом записи, а не размером
списков**: записей в наборах держалось 160–380 тыс., а keeper упирался в свой
предел 1 ГиБ. Копия инспектора под тем же темпом растёт со 136 до ~200 МиБ,
внутренний Redis — до 143 МиБ (в основном пакеты дельт, `waf:diff:*`, срок 90 с:
до 4 500 ключей). Края к этим спискам не подключены (`in_nginx` нет) и выросли
на 40–55 МиБ на всех трёх.

Кодер гео с полным каталогом ASN держит 1024 МиБ при `mem_limit: 1g` — свой
предел — и до 147 % процессора на запись `net`/`asn`. Это не артефакт прогона:
каталог настоящий.

#### Четыре дефекта

1. **Бан теряется молча.** На перегрузке инспектор адреса получил 31 165
   `live dataset write failed … nats: timeout` — это WARN в журнале, без
   повтора и без следа в ответе. Клиент прошёл, бана нет, и узнать об этом
   можно только из журнала копии.
2. **keeper выпадает из шины как медленный потребитель.** NATS: `Slow Consumer
   Detected: MaxPending of 67108864 Exceeded`, следом `WriteDeadline of 10s
   exceeded with 520 chunks of 27151797 total bytes` — и разрыв (`bus
   disconnected: EOF`, четыре раза за пять минут). После разрыва все запросы
   записи в полёте отваливаются по таймауту (см. дефект 1). Сам keeper в
   журнале молчит: ни отказа записи (`store_unavailable` он отдаёт ответом), ни
   слова о разрыве темпа.
3. **Контроллер наливает активный набор по одной записи.**
   `POST /datasets/<uuid>/addresses` у активного набора шлёт keeper по событию
   на адрес и ждёт ответа на каждое (`state/thunks/datasets.ts`, цикл по
   `unique`): 100 адресов — 1,2 с, 1000 — 11,6 с, 5000 — 58 с (**86 записей в
   секунду**). Та же тысяча записей одним кадром `values[]` — те же 11 мс на
   всю пачку, 142 000 записей в секунду. Вставка списка на десять тысяч
   адресов из панели упирается в таймаут клиента, а запись продолжает идти.
4. **Ступень от минуты считалась несостоявшейся.** `parse.mjs` читал строку
   итога wrk по шаблону `requests in ([\d.]+)s`, а от минуты wrk печатает
   `1.00m`: запросов 0, суд `no_requests`, а прогон из одной такой ступени
   целиком объявлялся `error` (`status = ok ? "done" : "error"` по `reqs > 0`).
   Починено разбором единицы; в таблицах выше пометка `no_requests` — этот
   дефект, а не поведение стенда.

#### Второй заход 12.09: что починено и что стало

Владелец: «keeper валяется на 10к записей в секунду -- это мало; он у нас
единственный». Разбор кода показал, что конвейер keeper не медленный (налив
пачками -- 140-460 тыс. записей/с), медленной была перегрузка: очередь без
дна (горутина на сообщение, канал на 4096 кадров по 580 записей), работа для
писателей, которые давно ушли по таймауту, и сборщик, голодящий чтение шины.
Сделано в keeper: очередь конечна и меряется записями
(`WAF_KEEPER_QUEUE_MAX`, сверх -- `overloaded` сразу), просроченные кадры
выбрасываются, планировщик и коммитер разделены (Redis вне критического
пути, `WAF_KEEPER_PIPELINE` пачек впереди), хеш и префикс считаются один раз,
пачка до 10 000, квота 4 CPU / 2 ГиБ. Подробно -- docs/keeper.md, «Запись».

Заодно нашлось, кто ел стенд в тишине: восемь копий инспектора адреса по
50-86 % CPU и кодер geo на 120 % **без единого запроса** -- оба сравнивали
отпечаток файлов после полной пересборки данных, раз в секунду; логгер лил
журнал в ClickHouse по одной строке (265 частей в минуту), а сам ClickHouse вёл
десять гигабайт собственных системных журналов. Всё это снято; стенд в покое
-- 0,6 ядра вместо ~8.

Те же охваты поодиночке, 1000 rps × 60 с, восемь копий ip по два воркера:

| охват | было | стало |
| --- | --- | --- |
| `addr` | 981 rps, p50 5 / p99 732 мс, 25 × 500; keeper 989 зап/с, 85 МиБ, 35 % | 991 rps, p50 9 / p99 762 мс, 0 × 500; keeper 993 зап/с, 228 МиБ, 49 % |
| `asn` | 471 rps, p50 893 / p99 2020 мс, **8 093 × 500**; keeper 9 820 зап/с, **1023 МиБ, 206 %**, склад 2,3 с, 31 тыс. потерянных банов | 960-981 rps, p50 5-137 / p99 840-1530 мс, **0 × 500**; keeper **41-57 тыс. зап/с**, 409-495 МиБ, 254-292 % (из 400), склад 1-3 мс, 0 разрывов шины |

`asn` на входе keeper отказывает быстро и честно: 4-18 тыс. кадров за минуту
получили `overloaded` вместо таймаута через пять секунд -- это и есть
предел одного владельца на этом стенде, ~50 тыс. записей в секунду с
истечением той же силы. Всё, что прошло, доехало: ни одного `nats: timeout`,
ни одного `DeadlineExceeded` от кодера. Оставшийся p99 у `asn` -- очередь
инспектора: два воркера на копию и синхронный поход в кодер до 500 мс на
каждый запрос с новой системой.

Два разброса, которые видно в таблице, -- не контур: p50 `addr` 9 против 234
мс и `asn` 5 против 137 мс между повторами при p50 инспектора 2-6 мс -- это
хост, на котором в одном из повторов шла сборка образа контроллера.

Не сделано: пачка на стороне писателя (per-set outbox у инспектора адреса) и
аренда набора в redis-internal (failover и шардирование по наборам); оба --
отдельные заходы.

**2000 rps, по охвату, 60 с.** Никто не упал: ни одной 500, ни отказа модуля,
ни разрыва шины. Но стенд отдал 1 230 (`addr`), 1 280 (`net`) и 1 070 (`asn`)
rps при p50 750-900 мс на клиенте и **p50 инспектора 2-3 мс**: потолок не в WAF.
Во время `addr` на 2000 rps haproxy ел 269 % CPU (12 потоков на квоте 6,
`tune.bufsize 1048576` -- мегабайтный буфер на каждое соединение, журнал
дважды: stdout и сокет агента), NATS 106 %, витрина 79 %, края по 56 % (из них
32 % sys -- новое соединение к апстриму на каждый запрос: в upstream нет
`keepalive`), keeper 44 %, копия ip 19 %. Журнал при этом -- около двух тысяч
строк в секунду (nginx 1 200/с, ip и haproxy по 500/с) через агента, NATS,
логгер и ClickHouse. keeper на `asn`: 38 тыс. записей/с, 552 МиБ, 313 %,
`overloaded` 9 087 кадров, склад 12 мс.
