# Логические кейсы

Соглашение то же, что у [нагрузочных](../load/README.md),
и оно главное: **прогон автономен**. Начало — пустой стенд, конец — снова
пустой. Всё, что нужно кейсу, заводится через API контроллера и сносится
журналом в обратном порядке. Ручных правок конфигов, записей в базу и отдельно
поднятых инспекторов нет.

Общее с нагрузочной секцией берётся готовым:

| Что | Откуда |
| --- | --- |
| Клиент API контроллера | `../lib/api.mjs` |
| Заведение по описанию, журнал, издание, сходимость | `../lib/stand.mjs` |
| Проверки одиночными запросами | `../lib/check.mjs` |
| Личности прогона: пара ключей и токены | `../lib/identity.mjs` |
| Кадры WebSocket: рукопожатие и шаги | `../lib/socket.mjs` |
| Блок `needs` в кейсе | тот же формат, что в `../load/cases.mjs` |

Что умеет заводить `needs`, в порядке заведения (снос — задом наперёд):
`datasets`, `ruleFiles`, `ruleSets`, `ipSets`, `ipProfiles`, `actionProfiles`,
`counterShared` (объявления счётчиков — общая секция инспектора, правится, а не
создаётся), `counterProfiles`, `rewriteProfiles`, `authSources`, `authProfiles`,
`upstreams`, `declarations`, `servers`, `routes`, `captchaProfiles`.

Профиль капчи заводится **последним**, и это не прихоть порядка, а круг: ему
нужны `server_id` и уже существующая локация виджета, а маршруты требуют
объявлений, которые называют профиль. Круг рвётся тем, что объявление зовёт
профиль по имени (`profile:`, а не `profileFrom:`) — наличия профиля при записи
объявлений никто не проверяет, а к изданию он уже есть. Снос из-за этого идёт в
два прохода: строгий обратный порядок такую связь не разматывает.

Источник входа заводится только внешний (`jwt`, `app`) — у своей формы входа
есть маршрут, а маршрут требует объявления, профиля и источника, и круг этот
прогон не разрывает.

Отличие в том, что проверяется. У нагрузочного кейса это потолок, поэтому
трафик гонит генератор, а результат — таблица ступеней. У логического это
поведение на конкретных запросах: код ответа, заголовки приложению, запись в
журнале, состояние набора после. Поэтому вместо `traffic` и `clean` у кейса
список шагов с ожиданиями, а запросы шлёт сам прогон.

## Предполёт

Прогон против промежуточной сборки ничего не доказывает: зелёный результат может
значить «код исправен», а может — «стенд не знает о правке». Поэтому каждый
прогон начинается с приведения стенда в соответствие с исходниками
(`tests/lib/bootstrap.mjs`).

| Что | Как |
| --- | --- |
| Миграции | Журнал `waf_schema_log` в самой базе; применяется всё, чего в нём нет, файлом изнутри контейнера. Основание называется один раз: `WAF_SCHEMA_BASE=090`. |
| Сборка | Только те сервисы, у которых самая свежая правка в контексте новее образа. Пачками по три; сорвавшаяся пачка пересобирается по одному, до трёх попыток на сервис. |
| Раскатка | Волнами: инспекторы, служебные, контроллер, края. Обратный порядок ломает рассылку — новый контроллер считает хеш по-новому, старый инспектор его отвергает, и перестают доезжать даже правки профилей. |
| Сверка | `GET /api/actions` против словаря глаголов в `controller/src/model/actions.ts`. Расхождение останавливает прогон, а не пишет предупреждение. |

Флаги: `--no-bootstrap` пропускает предполёт целиком, `--reset-db`
пересоздаёт том базы, накатывая схему и гео-сид заново. Данные стенда при этом
теряются, поэтому это отдельный явный шаг, а не часть обычного прогона.

Сборка образов и раскатка на этом стенде занимают минуты, когда правок много,
и секунды, когда всё свежее.

## Кейсы

```
node tests/logic/run.mjs             # все по очереди
node tests/logic/run.mjs off-saves   # только названные
node tests/logic/run.mjs --keep      # не сносить, оставить для разбора
node tests/logic/run.mjs --clean     # снести остатки e2e- и выйти
```

| id | Что проверяет |
| --- | --- |
| `one-denies` | Пять проверок адреса подряд: четыре всегда согласны, пятая отказывает по своему списку. Согласия не перевешивают отказ, и в отладочном заголовке виден ответ каждого. |
| `off-saves` | Первый инспектор находит адрес в списке исключений и просит модуль выключить пятого — того, который по своему списку отказал бы. Список исключений вложен в список отказа, поэтому на таком адресе истинны оба правила. Проверяется разница между «отказ не сработал» и «отказавшего не спросили»: выключенного модуль в заголовке не печатает вовсе. |
| `score-blocks` | Никто не отказывает; отказ выносит маршрут по сумме очков. Инспектор действий на нужном префиксе просит начислить ровно порог, на соседнем молчит. Пометка `by=score` отличает отказ по сумме от отказа инспектора. |
| `cond-asks` | Инспектор действий просит очки по условию: `unless` «ключ из заголовка в активном наборе» и `if` «аргумент debug равен 1». Заголовок берётся из снимка маршрута, набор — из зеркала keeper, аргумент — из строки запроса; без ключа и с чужим ключом отказ по сумме, с ключом из набора проход, с ключом и `debug=1` снова отказ. |
| `cond-logic` | Условия по ИЛИ, по И и ссылками: «доверенный» — ИЛИ из заголовка в наборе, аргумента равного тексту, адреса из X-Forwarded-For в наборе сетей и cookie в наборе с `hash=md5`; «опасный» — ИЛИ из «доверенный ложно» и «debug истинно». Каждая ветка ИЛИ проходит, чужие значения во всех ветках и `debug=1` поверх доверия — отказ по сумме. |
| `counter-user` | Корзина счётчика на **человека**, а не на адрес: калитка первой волной называет личность, счётчик второй берёт её из секции `sessions`. Фаза ответа считает объекты в теле, фаза запроса судит уровень; двадцать объектов наполняют корзину, и следующий запрос того же логина отказан **с другого адреса**. Сосед по маршруту — другой человек, чужого отказа не наследует; гость до счётчика не доходит вовсе. |
| `counter-user-mask` | Тот же счёт, другой исход: дойдя до половины корзины, счётчик просит модификатора включить группу `mask` (`do: mutate`), и метки в ответе замаскированы. Просьба высказана на фазе запроса, а исполняет её инспектор фазы ответа — проверяется сквозной `prior`. Группа выключена по умолчанию, грант в правиле приёма поимённый; соседу маска не включается. |
| `counter-user-silent` | Четыре способа остаться без субъекта, и все дают одно: правило по оси `user` **молчит**. Калитки на маршруте нет; калитка есть, но `mode=passive` (записи пассивного соседям не доставляются); калитка стоит **позже** счётчика; калитка приняла токен, не проверяя подписи (`alg: none` → `verified: false`). Контроль — тот же человек на правильном маршруте: там отказ приходит, до и после серии. |
| `captcha-degrade` | Деградация вместо отказа. Один маршрут; капча и модификатор объявлены в `off`, включает их инспектор действий по пути: на `/page/` капча получает `active` и гейтит, на `/api/` — `vote`, а модификатор `active`. Счётчик считает отданные объекты на адрес и за половиной корзины наливает корзину капчи; дальше маску держит сама капча — её порог срабатывает на каждом запросе и просит модификатора включить группу, клиент получает `200` без меток. Прогон проходит виджет на `/page/` (ответ картинки читается в Redis); на запросе с клиренсом капча шлёт обе просьбы одной пачкой — порог `on`, клиренс `off` — и побеждает последняя. Без куки маска возвращается. |
| `captcha-ban-ladder` | Лестница капчи целиком: от 60 выдача замаскирована, на 100 — три записи в три живых набора с тремя сроками (адрес 10 с, эффективный анонс 30 с, состав системы 60 с; анонсы и состав — у кодера гео, синхронно, одним кадром keeper). Инспектор адреса нулевой волной режет по наборам, забаненный не греет корзины, и код отказа сменяется по мере протухания: `E2E_BAN_IP → E2E_BAN_NET → E2E_BAN_ASN`, через минуту — проход с целой выдачей. Сосед из чужой системы не задет. Записи и их сроки читаются через API. |
| `captcha-uncleared` | Маска тем, кто не проходил капчу, — с первого запроса, без корзин и без счётчика. Раскладка `captcha-degrade` (капча и модификатор в `off`, включает их инспектор действий по пути; на `/page/` капча `active`, `when: always`, на `/api/` — `vote`), но маску держит событие `uncleared` — запрос без действующего клиренса, на каждом таком запросе, что бы капча ни решила дальше. Без куки выдача замаскирована, на `/page/` — виджет; прогон проходит виджет, и с клиренсом выдача целая: капче нечего просить, группа выключена по умолчанию. Без куки маска возвращается. |
| `captcha-widget-price` | Цена показа виджета — уточнение `next` у `uncleared`. Капча боевая на всём маршруте (`when: always`), инспектор адреса нулевой волной режет по живому набору. На `/free/` инспектор действий просит капчу `skip`: шесть запросов без клиренса пропущены, правило `next: allow` начислило очки, а правило `next: challenge` (адресу +30%) молчит — набор бана пуст. На `/page/` каждый показ виджета стоит 30%: после четвёртого корзина за `ban_at` 90, порог пишет адрес в набор, и следующий запрос отказан инспектором адреса (`E2E_BAN_IP`); запись в наборе со сроком 30 с. |
| `shop-funnel-trap` | Три маршрута одного магазина связаны общим состоянием: корзиной кредита счётчика, набором подозреваемых и баном подсети. Витрина копит кредит (страница — единица) и вставляет в тело скрытую ссылку-приманку — приложение не трогается, ссылка встаёт перед `</body>`; касса тратит кредит (заказ — две) и отказывает по сумме тому, кто пришёл без него, а кто витрину не открывал вовсе — уезжает в подозреваемые; ловушка молча пишет туда обходчика, ответ — обычный 404. Капча зовётся только для подозреваемых, условием вызова по набору; прошедший виджет проходит кассу без кредита — капча просит счётчик не судить (`skip`). Пятый провал заказа банит весь анонс адреса, и узел режет подсеть локальной проверкой: соседа тоже, покупателя из другой сети — нет. Попутно тот же модификатор маскирует номер карты в ответе кассы. |
| `counter-user-frames` | То же на сокете. Калитка на рукопожатии, счётчик и модификатор на кадрах клиента; лестница из двух корзин на человека: вторая по счёту корзина включает маску (эхо приложения возвращает `masked-`), пятый кадр переливает корзину закрытия, и соединение закрывается кадром Close. Учёт и суд на кадрах живут на одном кадре — отказ получает тот, кто перелил. |

## Что впереди

Кейсы на связки между инспекторами — счётчик гонит на капчу, капча снимает
маску, контракт ответа наказывает следующий запрос, непрошедшему виджет вместо
отказа вставляют всплывашку со ссылкой на форму — собраны планом в
[cross-cases.md](cross-cases.md): двадцать шесть штук с разбором того, чем
каждая связка выражается на проводе, и списком того, чего для них не хватает
библиотеке. Написанный кейс уезжает в таблицу выше и вычёркивается оттуда.

Там же короткая справка «кто что умеет просить и кто что принимает»: половина
правдоподобных связок словарём не выражается, и узнавать об этом лучше до, а
не на середине кейса.

## Пропуск по неподдержке

У кейса бывает поле `requires`. Раннер спрашивает контроллер делом — заводит
временный профиль с нужным глаголом — и, если тот его не принимает, помечает
кейс **пропущенным**, а не упавшим: код возврата остаётся нулевым.

Так сейчас с `score-blocks`. Глагол `score` есть в исходниках (`GET /api/actions`
из свежей сборки отдаёт 14 глаголов) и в панели, но контроллер, поднятый на
стенде, отдаёт 12 и этого глагола не знает. Кейс написан целиком и заработает
после пересборки контроллера, без правок.

## Ожидания проверки

| Ожидание | Что значит |
| --- | --- |
| `status` | код ответа числом |
| `deny` | код берётся из каталога отказов по имени записи |
| `verdict` | `v=` из отладочного заголовка |
| `by` | кто решил: `score` — сумма очков маршрута, `local` — локальный слой |
| `asked` | инспектор (или список) присутствует в заголовке |
| `notAsked` | инспектора в заголовке нет: так выглядит выключенный просьбой `off` |
| `answers` | что ответил названный инспектор: `{"e2e-lg-05": "deny"}`. Токен — `вердикт[/очки][/повод]/мс[/profile=…]`, сравнение по началу. У запроса с фазой ответа отладочных заголовков два (модуль пишет на каждой фазе), и у имени, стоящего на обеих, прав токен фазы запроса |
| `bodyHas` / `bodyLacks` | подстрока в теле ответа: так видно работу модификатора и число отданных объектов |

Проверка повторяется до 15 секунд: канал сходится раньше, чем инспектор меняет
набор, и одиночный запрос сразу после издания попадает в эту щель.

Поле `times` шлёт запрос несколько раз и проверяет последний ответ:
поведенческому инспектору одного запроса мало — корзину сперва надо наполнить,
и наполняет её тот же запрос, которым потом проверяют. Повтор после
несовпадения шлёт один запрос, а не всю пачку.

## Личности: калитка и токены прогона

Кейсу, который считает «на человека», нужна живая калитка: без неё в сообщении
нет секции `sessions`, а без неё — оси `user` у счётчика. Поднимать ради этого
форму входа, набор учёток и живые сессии значит завести полстенда, поэтому
прогон берёт внешнего провайдера `jwt`: пара ключей RSA рождается в
`../lib/identity.mjs` на один запуск, подпись проверяет калитка, токены
выписывает сам прогон.

Кейс — данные, поэтому ключа и токенов в нём нет: он называет их именами, а
значения подставляет прогон.

| Имя | Чем становится |
| --- | --- |
| `"@jwt.public"` | PEM открытого ключа — в документ источника входа |
| `"@bearer.alice"` | заголовок `Authorization` подписанного токена |
| `"@bearer-unsigned.alice"` | то же без подписи: калитка примет, но пометит `verified: false` |
| `"@login.alice"` | логин с меткой запуска |

Логин у каждого запуска свой (`alice-mtv0hvxg`), и это не косметика: корзины
счётчика живут в Redis и переживают прогон, а доступа к Redis у автономного
прогона нет и быть не должно. Свежий логин — свежая корзина.

## Кадры

Кейс с блоком `socket` открывает своё соединение через край и идёт по шагам:
кадр клиенту в сторону приложения — что вернулось. Рукопожатие повторяется до
срока (оно ничего не заряжает), сами шаги — нет: кадр меняет состояние, а
корзина ключуется личностью и переживает соединение.

| Поле шага | Что значит |
| --- | --- |
| `send` | текст кадра; без него шаг только читает (приложение здоровается само) |
| `echoHas` / `echoLacks` | подстрока в том, что вернулось |
| `closed` | ждём закрытия: кадры с данными по дороге пропускаются |
| `waitMs` | свой срок ожидания вместо трёх секунд |

## Несколько клиентов и тело запроса

Кейсу, который проверяет, как состояние одного клиента задевает (или не
задевает) другого, одного `@run.ip` мало. Поле `actors` называет роли, и у
каждой свой свежий адрес на запуск — пробы зовут его `@ip.<роль>`. Адреса
различны; `within` — префикс, внутри которого брать хост (нужен, когда запись
в набор идёт подсетью и кодер гео обязан знать сеть). Так устроен
`shop-funnel-trap`: шесть ролей, двое из них соседи по одной `/24`.

Проба шлёт не только GET: `method` и `body` — объект уезжает JSON-ом,
строка — как есть, длина проставляется сама.

## Набросок формы для новых кейсов

```js
{
  id: "counter-ban",
  title: "…",
  about: "…",
  needs: { /* см. таблицу выше: от datasets до routes, плюс publish */ },
  requires: { verb: "score" },          // необязательно: пропустить, если контроллер не умеет
  identity: { logins: ["alice"] },      // необязательно: калитка и токены прогона
  actors: { buyer: {}, carder: { within: "1.1.1.0/24" } }, // необязательно: адреса @ip.<роль>
  target: { host: "e2e-logic.waf.test", path: "/logic/…/" },
  probes: [
    { name: "…", ip: "203.0.113.7", expect: { deny: "blocked", verdict: "deny" } },
    { name: "…", path: "/logic/иначе/", expect: { status: 200, notAsked: "e2e-lg-05" } },
    { name: "…", path: "/api/orders", method: "POST", body: { itemId: 7 }, ip: "@ip.buyer", expect: { status: 201 } },
  ],
  socket: {                             // необязательно: шаги по кадрам
    path: "/socket/chat",
    headers: { Authorization: "@bearer.alice" },
    steps: [{ name: "…", send: "…", expect: { echoHas: "…" } }],
  },
}
```

Чего логическому прогону всё ещё не хватает: **чтения состояния после
трафика** — наборов, записей журнала, содержимого обменника. Библиотека умеет
заводить, сносить и спрашивать через край, но не смотреть, что осталось внутри.
Для поведенческих кейсов это чувствуется сильнее всего: уровень корзины виден
только через её последствия.
